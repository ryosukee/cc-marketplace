# セッションを跨ぐ議題では decision-record を持つ

decision-record は次のセッションの自分が読む保管庫。読みやすさではなく、誤読されないことに最適化する。
要約にまとめない。必要な情報が落ちることがある。
分量を削る理由は無い。

## decision-record を持つ対象

decision-record を持つのは、議題・取り組みのうち次を両方満たすものだけ。以降は議題と書く。

- 1 セッションでは終わらず、セッションを跨いで続く
- 聞き取りや要件のすり合わせを複数回行う

そのセッションのうちに対応が終わることは書かない。決めてすぐ rule・skill・コード・設定を直すなら、
直したファイルと commit が記録になる。

decision-record は議題ごとに作り、その議題の内容だけを書く。他の議題の決定を混ぜない。

判定基準: いま議論している議題が、次のセッションでも続くか。続かないなら decision-record を作らない。

## 置き場

プロジェクトに適した置き場（既存の設計ドキュメント・決定記録・issue・wiki・チケット 等）があればそれを使う。
無いときは notes 形式を既定案としてユーザーに提案し、承認を得てから作る。承認前に作らない。
形式・場所にユーザーの希望があればそちらに従う。
`.handover/` をメモ置き場にしない（session plugin の専用 skill が扱う引き継ぎ用ディレクトリ）。

置き場が notes 形式でなくても、何を記録するか（確定項目の 5 項目と、出典の実文を repo 内に持つこと）は
[notes の書き方](./notes-authoring.md) の「decision-record に入れるもの」と「出典」の節に従う。
この rule は `notes/**` を読んだときだけ載るので、notes 以外の置き場を使うときと、
`notes/` に最初のファイルを作るときは、書く前に Read する。

## notes 形式

repo 直下 `notes/` の 3 層。

- `notes/README.md`: decision-record の一覧（ファイル / 対象 / 状態の表）と、運用の規定である rule への
  ファイル名での言及だけを置く
- `notes/{slug}.md`: 1 議題 1 ファイル。他の議題の内容を混ぜない
- `notes/artifacts/`: decision-record が参照する明細（生データ・作業明細・出典の実文）の置き場

作るときにすることが 2 つある。

- 作成はユーザーの承認後
- プロジェクト固有の書き方（重複を確認する正式な文書のディレクトリ、チケット番号の形式など）を
  project rule として作るかをユーザーに問う。固有分が無ければ作らない

## 数値は合意の内容であるときだけ書く

行数・差分の増減・ファイル数・所要時間のような数値を書かない。
読んだ側の行動が変わらないうえ、書いた瞬間から古くなり、突合のたびにずれが見つかって直す手間だけが増える。

例外は、その数値そのものが合意の内容になっているとき。閾値、レート制限、選んだ個数が該当する。
これらは変わったら決め直しになるので、そのまま引ける。

- 自分が過去に計算した推定値を、出典のある値として引かない。
  出典を示せない数値は「未算出」と書くか、その場で算出の根拠ごと示す
- 例外に当たる数値でも、対象が変わりうるものは引用する前に測り直し、違っていたら decision-record 側も直す

判定基準: その数値を読んで、次のセッションの行動が変わるか。変わらないなら書かない。

## why

要約資料は読みやすさのために情報を落とすので、「そこに書かれていない = まだ決めていない」とは言えない。
decision-record が無いと、後のセッションが確定済みの事項を未確定と誤認して再設計を始める。

判定基準: 「これは決まっていないから決めよう」と書く前に decision-record を引く。
引いた確定を設計の前提に使うときは、その確定を成立させた条件が今も成立するかを確認する
（条件は失効条件でもある。崩れていたら再検討をユーザーに提案する）。
