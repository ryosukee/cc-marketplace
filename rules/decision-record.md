# セッションを跨ぐ議題では decision-record を持つ

decision-record は、合意や決定の一時的な記録。実装・計画・設計・ドキュメンテーションのような後続のタスクに
必要な情報を後から参照できるようにするために書く。decision-record そのものを永続的に repo に保存して管理したいわけではない。
後続のタスクで消費され、その decision-record を参照する予定のタスクが全て無くなった時点で保存する価値が無くなる。
そのために decision-record ごとに生存期間を定める。

次のセッションの自分が読む保管庫なので、読みやすさではなく、誤読されないことに最適化する。
要約にまとめない。必要な情報が落ちることがある。分量を削る理由は無い。

## decision-record を持つ対象

合意や決定を、それを参照するタスクが使うまでにタイムラグがあるときに持つ。決めたその場で使い切るなら要らない。

decision-record を持つのは、議題・取り組みのうち次のどれかに当たるものだけ。以降は議題と書く。

- 合意や決定を参照するタスクが、複数のセッションを跨いだ先にある
- 合意や決定を参照するタスクの前に他のタスクや依存が複数あり、すぐには着手できない
- 聞き取りや要件のすり合わせを複数回行い、決定が積み上がる

以下のようなケースでは decision-record は必要ない。

- そのセッションのうちに対応が終わること。決めてすぐ rule・skill・コード・設定を直すなら、
  直したファイルと commit が記録になる
- 次のセッションが続きをやるだけで済むこと。セッションの引き継ぎ資料で足りる

decision-record は議題ごとに作り、その議題の内容だけを書く。他の議題の決定を混ぜない。

判定基準: この合意や決定を使うタスクは、いつ・どのセッションで動くか。
次のセッションへの引き継ぎで届く範囲を超えるなら decision-record を作る。届くなら作らない。

## 置き場

プロジェクトに適した置き場（既存の設計ドキュメント・決定記録・issue・wiki・チケット 等）があればそれを使う。
無いときは notes 形式を既定案としてユーザーに提案し、承認を得てから作る。承認前に作らない。
形式・場所にユーザーの希望があればそちらに従う。
`.handover/` をメモ置き場にしない（session plugin の専用 skill が扱う引き継ぎ用ディレクトリ）。

置き場が notes 形式でなくても、何を記録するか（確定項目の 5 項目と、出典の実文を repo 内に持つこと）は
[notes の書き方](./notes-authoring.md) の「decision-record に入れるもの」と「出典」の節に従う。
この rule は `notes/**` を読んだときだけ載るので、notes 以外の置き場を使うときと、
`notes/` に最初のファイルを作るときは、書く前に Read する。

## notes 形式

repo 直下 `notes/` の 3 層。この 3 層以外のファイル（計画・手順・下書き・試作コード）を `notes/` に置かない。

- `notes/README.md`: decision-record の一覧（ファイル / 対象 / 状態の表）と、運用の規定である rule への
  ファイル名での言及だけを置く
- `notes/{slug}.md`: 1 議題 1 ファイル。他の議題の内容を混ぜない
- `notes/artifacts/`: artifacts（decision-record が参照する付随ファイル。生データ・作業の一覧・出典の実文の写し）の置き場

作るときにすることが 2 つある。

- 作成はユーザーの承認後
- プロジェクト固有の書き方（重複を確認する正式な文書のディレクトリ、チケット番号の形式など）を
  project rule として作るかをユーザーに問う。固有分が無ければ作らない

## why

合意や決定を利用・消費するタスクは、決めたときとは別のセッションの Claude が実行する。
そのセッションは、決めたときの会話を持っていない。decision-record が無いと、決めた内容と、
その決定が成り立つ条件を知る手段が、引き継ぎ資料の要約と過去の transcript だけになる。
要約は必要な情報を落とすことがあるので、読み手は書かれていない事項を未決定と読んで決め直す。
条件を知らないまま、決定を前提にして進めることもある。

判定基準（decision-record を引くかどうか）: 「まだ決まっていない」と扱って決めようとしている事項が
decision-record に無いことを、引いて確かめたか。確かめていないなら、決める前に引く。
引いた決定を前提に使うときは、その決定が成り立つ条件がいま成立しているかを確かめ、
成立していなければユーザーに再検討を提案する。
