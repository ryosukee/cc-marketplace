# notes の書き方

decision-record として運用する `notes/` にだけ適用する。
decision-record 以外の目的で `notes/` を使っているプロジェクトには適用しない。
「decision-record に入れるもの」と「出典」の節だけは置き場を問わず、notes 形式以外の decision-record にも当てる。

## 冒頭に目的・生存期間・対象議題を書く

各ファイルの本文より前に、目的・生存期間・対象議題の表を書く。

| 項目 | 書く内容 |
| --- | --- |
| 目的 | このファイルが何のために存在するか。1 文 |
| 生存期間 | いつまで残すか。終わりの条件と、この記録を利用・消費する予定のタスク（タスク群・エピック・マイルストーンのような広い範囲でもよい） |
| 対象議題 | チケット番号・PR 番号・プロジェクト名など、辿れる識別子 |

生存期間は日付ではなく条件で書く。日付を書くと、その日が来ても条件が満たされていないときに
消してよいか判定できない。利用・消費する予定のタスクを併記するのは、対象議題だけでは
この記録がどのタスクで消費されるかが分からないため。

- OK: `ADR-0002 が確定し、内容を ADR へ移すまで。利用するのは ADR-0002 の起草と、それを実装する PR`
- NG: `2026-09 まで`
- NG: `不要になるまで`（条件になっていない）

判定基準: そのファイルを見た別の人が、消してよいかと、どのタスクがまだ利用するかを自分で判定できるか。

artifacts は、decision-record が参照する付随ファイル。生データ、作業の一覧、出典の実文の写しがこれに当たり、
`notes/artifacts/` に置く。

本体のファイルが参照する artifacts を別ファイルに置くときは、
その artifacts に目的・生存期間・対象議題の表を置かず、冒頭に本体へのリンクを 1 行置く。
artifacts の生存期間は本体と同じで、本体の表がそれを持つ。

本体の側は、参照している artifacts の一覧を持つ。一覧が無いと、artifacts から本体へ辿っても
自分が何のために残っているかに行き当たらず、本体を消すときに artifacts が孤児になる。

判定基準: artifacts だけを開いた人が、リンクを 1 つ辿って生存期間に到達できるか。

## ファイルの構成

確定項目を積む decision-record は、上から次の順で並べる。ほかの節を作らない。
`notes/` には decision-record と、それが参照する artifacts 以外を置かない。
計画・手順・下書き・試作コードは、役割に合った別の置き場にする。

| 位置 | 持つもの | 無いとき |
| --- | --- | --- |
| H1 | 議題名 | 省かない |
| 表 | 目的 / 生存期間 / 対象議題 | 省かない |
| `## この decision-record が参照する artifacts` | artifacts へのリンクと、それぞれの目的 | 省く |
| `## 確定事項` | 確定項目。追記専用 | 省かない |
| `## 未解決課題` | 決まっていない論点を 1 件 1 行 | 省く |
| `## 作業メモ` | 調査の途中経過、確定していない仮説、資料の整理 | 省く |

作業メモの中で事実が確定したら、確定事項へ確定項目を起こす。作業メモ側は残しても消してもよい。

節に入らない書き足しは、置き場が無いという合図なので、4 つのどれかへ入れるか消す。

冒頭の表の直後を見出しから始めることは、`notes/` のどのファイルでも守る。
ただし、その文書が何であるかを述べる導入の 2〜3 文は表の直後に置いてよい。

判定基準: 表の次にある空行でない行は、見出しか。見出しは上の 4 つのどれかか。

## decision-record に入れるもの

確定 1 件につき 1 つの確定項目として記録する。確定項目に書くのは次の 5 つ。

- 何が決まったか（結論）
- 何を決めなかったか（保留にした範囲・対象外にした範囲）
- なぜそう決まったか（選択があったなら、選んだ側が満たしていた条件）
- 出典（決定した回・フォーム・issue へのリンク）
- 出典の実文（下記）

選択のない確定項目（調査で判明した事実）には、なぜそう決まったかが当てはまらない。その場合は書かない。

## 参照

参照は読み手が主張の裏を取れる形にする。形は都度選ぶ。

- 名前・版・通称で指さない。読み手がその文字列で対象へ到達できることが条件になる
- 実文を引けば辿る必要が消えるので、短いものは引く
- 書いた時点で、指した先に主張どおりの内容があることを確かめる

## 出典

出典は確定項目を成立させたものの実文を残す。残し方は 2 つだけで、別の形式へ写し直さない。
出典の種類を分類して当てはめない。

- 実文を書き写す。これが基本
- 原本のファイルをそのままコピーする。実文では残せないものがあるときだけ

対象は形式を問わない。フォーム・issue・PR のコメント・コミット・会話のすべて。

出典が、掃除や上書きの運用を持つ場所にあるときは、その場所自体を出典にしない。
確定項目を書いた時点で、実文を repo 内へ写す。

- 残すのは確定した時点の内容。実際に読まれた内容と、参照先がいま持っている内容が食い違うときは、
  読まれた側を残す
- 持つのは、その確定を生んだ問いと、選ばれた答え。設問文・選択肢・回答者の補足を、要約せずそのまま引く
- 実文が長くなっても削らない
- 別ファイルに置いた実文は、確定項目からその箇所へアンカー付きのリンクで辿れるようにする
- 原本が失われている、または原本にあたる資料が無いときは、実文の代わりに「原本なし」と書き、
  失われた事実だけで終わらせない。何が失われたか、文脈、参考にできるもの、書き換わった箇所を注釈する

判定基準: その確定項目と実文だけを読んだ人が、何を問われて何を選んだかを再構成できるか。

why: 出典がリンクだけだと、指した先が消えた時点で確定の根拠が復元できなくなる。
指した先が最初から存在しなくても、誰も気づけない。

## 数値は合意の内容であるときだけ書く

行数・差分の増減・ファイル数・所要時間のような数値を書かない。
読んだ側の行動が変わらないうえ、書いた瞬間から古くなり、突合のたびにずれが見つかって直す手間だけが増える。

例外は、その数値そのものが合意の内容になっているとき。閾値、レート制限、選んだ個数が該当する。
これらは変わったら決め直しになるので、そのまま引ける。

- 自分が過去に計算した推定値を、出典のある値として引かない。
  出典を示せない数値は「未算出」と書くか、その場で算出の根拠ごと示す
- 例外に当たる数値でも、対象が変わりうるものは引用する前に測り直し、違っていたら decision-record 側も直す

判定基準: その数値を読んで、次のセッションの行動が変わるか。変わらないなら書かない。

## 定義のある欄へ書き足す前に、その欄の定義を読む

冒頭の表、確定項目の各項目、一覧のエントリのように、何を書くかが定められている欄がある。
そこへ書き足すときは、手を動かす前にその欄の定義を読む。

「実態に合わせる」「最新化する」型の指示は、足す内容を探す合図ではなく、
その欄が何を持つ欄かを先に確かめる合図として読む。
指示の側が欄を読み違えていることがあり、そのまま従うと読み違えを実装することになる。

判定基準: いま足そうとしている値は、その欄の定義が挙げている種類のものか。
定義を見ずにこれへ答えられるなら、まだ読んでいない。

why: 欄の定義は書く側の記憶の外にあり、書き足す場面では既に載っている値だけが目に入る。
既にある値に形を合わせると、その値が間違っていたときに間違いのほうが増える。

## 確定項目は記録として正しければよい

decision-record は議事録と同じで、書かれた時点の記録として正しいことだけを求める。

一度書いた確定項目は、その時点の記録として正しい限り書き換えない。
議論の末に結論や方針が変わったからといって、過去の記録を最新の情報で上書きしない。
どちらへ進んでなぜ向きを変えたかは、その議題の経緯として価値がある。

- 覆す側は、どの確定項目の何をどう変えたかを書く。「置き換え」のような曖昧な語で済ませない
- 覆された側にも 1 行足す
- 手を入れてよいのは、記録として間違っているか足りないときだけ（事実の誤り、出典の所在の取り違え、
  書き落とし）。書き落としを埋めてよいのは、書いた時点で決まっていたのに落としたものだけ。
  後から決まったことは新しい確定項目にする
- decision-record を直した履歴そのものは残さない。
  decision-record が持つのは議題の経緯で、decision-record への操作の経緯ではない

判定基準は 2 つ。その記述は、書かれた時点の記録として正しいか。
その内容は、その確定項目を書いた日に決まっていたか。

## 既存の文書が扱うテーマを notes で運用しない

書く前に、プロジェクトの正式な文書（設計書・調査記録・ADR など）に同じテーマを扱う
ファイルが無いかを確認する。あれば notes には書かず、その文書を直接更新する。
正式な文書へ清書するまでの一時的な decision-record として notes を使うなら、
生存期間を「その文書へ昇格するまで」と定める。

判定基準: そのテーマで検索したときに、notes と正式な文書の両方が出てくる状態になるか。
なるなら重複している。

## 消すとき

生存期間の条件が満たされたら、次のどれにするかをプロジェクトの慣行に従って判断し、ユーザーの承認を得てから実行する。
移す作業も削除も、承認の前に行わない。

- 正式な文書へ昇格させる。移した先を確定事項の確定項目に追記してから消す
- チケット等へ記録する。記録した先を確定項目に追記してから消す
- 不要と判断してそのまま削除する。判断の理由を残す必要があれば、その置き場を決めてから消す

消すときは一緒に消すものが 2 つある。

- `notes/README.md` の一覧の行。ファイルだけ消して一覧に残すと、次に見た人が
  ファイルの消失を異常として調べることになる
- そのファイルの確定項目が出典として参照している実文ファイル。本体が消えた後に
  実文だけが残ると、何の出典だったかを辿れない
