# Claude 向け文書の書き方

Claude が指示として読む文書の、種別の選び方と、種別を問わず共通する命名・frontmatter・指示項目・参照・why・改訂を定める。
新規作成と改訂の両方でこの規範に従う。

## 種別を選ぶ

上から順に判定し、最初に当たった種別で作る。

1. 特定のファイルパターンに対する宣言的な制約・判定基準か → rule。
   どのプロジェクトでも効かせるなら user global rule、そのプロジェクトだけなら project rule
2. ファイルパターンに絞れない知識・規約か → 参照知識 skill
3. モデルの判断を挟まず必ず実行される必要があるか → hook。
   rule と skill はモデルへの指示なので従われない可能性が残り、強制は hook だけができる
4. 独立したコンテキスト・tool 制限・model 指定で実行させたい specialist か → agent
5. 手順と参照資材を伴う作業か → 作業手順 skill
6. どれにも当たらないプロジェクト全体への指示 → CLAUDE.md

知識・規約は、paths で絞れるなら rule に置く。rule は paths の一致で確実に載るのに対し、
参照知識 skill は description のセマンティックマッチに依存するので発動が不確実で、適用範囲も曖昧になりやすい。

## 種別の付け替え

種別のあいだに上下関係はない。内容がどの発動条件に合うかが変わったら付け替える。

- 参照知識 skill → rule: 内容が特定の paths パターンに対応づけられると判明したとき
- rule → 参照知識 skill: paths パターンでは広すぎるか狭すぎるとき、
  またはファイルを触らない作業（調査など）でも必要なとき
- 付け替えたら元の種別から該当部分を削除する。両方に残すと片方だけが更新される

## 命名

- ファイル名は内容を表す kebab-case の名詞句にする (例: `markdown-formatting.md`)。
  分類コード・略号を新設しない

## frontmatter

- 書けるフィールドは公式の一覧を引いてから決める。手元で動いているという理由だけで書かない
- 値に依存する挙動があるフィールドは明示する。無いフィールドは書かない。
  明示した値は既定が変わっても効き続け、書かなかったフィールドは既定に追従する。
  どちらが欲しいかで決める。「いまの既定と同じ値だから」は、書く・書かないのどちらの理由にもならない

## 指示項目の書き方

- 指示項目を足す・直すきっかけは、レビューの指摘か実際に起きた失敗であることが多い。
  指示項目にするのは、そのきっかけになった表面の行動ではなく、その行動を生んだ判断の構造にする。
  「X をした → X するな」の形は、場面の形が変わると適用できない
- 適用範囲を「本当にそれを必要とする対象」に絞る。広い対象へひとまとめに適用しない
- 書いた指示項目に反する書き方を 1 つ挙げてみる。挙げられないなら、
  その指示項目は何にでも当てはまるだけで読み手の行動を変えないので、対象か基準を絞り直す
- 補足説明は、消しても適用範囲と判断が変わらないなら消す。
  残っているのはきっかけになった場面の語り直しで、指示項目そのものではない
- 指示項目に「判定基準」の行を添えるのは、読み手がその場で真偽を判定できる形に書けるときだけ。
  その形にできないなら添えない
- 具体事例を書いてよいのは、抽象的な指示項目の例として列挙する場合と、
  致命的で具体的な禁止指示が必要な場合の 2 つだけ。
  why: 具体事例をそのまま書くと、その事例にしか効かない。
  同じ根本原因の別パターンが来たときに指示項目が機能せず、事例の側の状況が変われば
  そこだけ古くなる。事例の分だけ文書も長くなり、読ませたい指示項目が薄まる

## what と why を pair で書く

指示項目には「何をする / しない」と「なぜそうするか」を pair で書く。
what だけでは、指示項目が想定していない場面で判断材料が足りなくなる。
why があれば指示項目の本質を理解した上で、未知のケースにも適用できる。

why の書き方:

- その指示項目が無いと何が壊れるかという本質的な理由を書く
- 現在形で書く。いま何が成り立つかだけを述べ、何があったかは書かない
- 主語を指示項目の対象に取る。書き手や過去のセッションを主語にしない
- 日付付きの具体事例を書かない。事例は書いた時点の場面に縛られ、場面の形が変わると
  指示項目を支えなくなる。事例から抽出した構造だけを理由として残す

判定基準: 書いた why を過去形にできるか。できるなら経緯が混ざっている。
「〜が起きた」「〜していた」「〜に変えた」と書ける文は why ではなく履歴で、
git 履歴と commit message の担当になる。

## 書かないもの

指示でない文は、読み込まれた分だけコンテキストを消費し、指示項目の密度を下げる。次のものを書かない。

- 実際のコードやディレクトリを見れば分かる情報。ディレクトリ構成の転写、
  関数のシグネチャ一覧、ファイル数、コード行数、実コードのコピーが対象。
  二重管理はメンテ負荷と乖離リスクを生む
- 特定インシデントの調査状況や修正進捗（「root cause 未特定」「次回検証予定」「暫定 workaround」等）。
  状態の追跡は、進捗の記録を目的とする文書で行う

見本（記述例・コマンド・コード）を載せてよいのは、指示項目の文だけでは読み手が正しい形を作れない場合に限る。
載せるのは形が伝わる最小限にとどめる。

実物（実装・設定ファイル・別の文書）から写した見本は、写し元がこちらと関係なく変わるので、
見本の側だけが古くなる。載せるなら写し元との同期を保つ義務を負う。
負いたくないなら、実物を写さず形だけを示す最小の例にするか、載せない。

workaround を手順に組み込む場合は、一時的であることを示す注記ではなく手順として完結させ、
状態が変わったら手順ごと削除する。

## 失敗したときに何をさせるかを書く

「失敗したらリトライせず停止」「タイムアウトしたらスキップ」のように、
うまくいかなかったら諦めるような指示を書くときは、諦める前に何をさせるかを一緒に書く。

既定は報告させること。何をしたら何が返ってきたか、再現する条件は何かを書いて止まる指示にする。
報告先を持たせずに諦めさせると、解ける問題が失敗のまま隠れ、同じ失敗が何度も繰り返される。

調査させる指示を書くのは、その文書が定める作業の性質が調査を含むときだけ。
原因を突き止めないと次の手順へ進めない作業（実装・テスト・不具合の切り分け）がこれに当たる。
その場合は、どこまで調べさせるかと、調べても分からなかったときの止まり方まで書く。
書かないと、調査が終わらないまま時間だけが伸びる。

## 文体

定義形で書く。「〜する」「〜を読む」「〜しない」の形にし、依頼形（「〜してください」）を使わない。
依頼形は丁寧さの分だけ語が増え、守るべき内容と依頼の言い回しが混ざる。
どこまでが定義でどこからが言い方かの境目も曖昧になる。

## アンチパターン節の書式

アンチパターンを列挙するときは 2 カラム表で書き、両カラムとも肯定文（例: 「〜する」）で統一する。
否定文と肯定文が混在すると、どちらが推奨か解釈が曖昧になる。
カラム名が役割を分けているので、中身は肯定文だけで伝わる。

```markdown
| アンチパターン | 代わりにどうするか |
| --- | --- |
| 太字見出しで段落を区切る | サブセクションか箇条書きのネストにする |
```

## 参照

- 自動ロードで既に載る文書に言及しない。paths が一致する rule と常時ロードの rule は、
  対象ファイルの編集時点で読み込まれているので、言及は重複になる
- 外側の構造に言及しない。「この文書は X から参照される」「Y から起動される」のような呼ばれ方も、
  「共通原則の上にこれを重ねる」のような層の関係も書かない。
  どの文書を読ませるかの誘導は、入口・呼び出す側が持つ
- 読み手を辿らせる責任がその文書にあるとき（入口 rule、呼び出す側の skill）は、
  自動ロードされない参照先への参照を書く

## 改訂

- 文書自身を書き直すとき、その文書の既存記述を書き直しの根拠に使わない。
  判断根拠は実態（コード・実測・一般原則）から取る。
  既存記述に誤りがあるとき、それを根拠にすると誤りが「そう書いてある」という権威で固定化する。
  why: 書き直しの対象になっている時点で、その文書には実態に合わない記述が
  含まれている疑いがある。直すモードでは、まず文書の側を疑う
