# 状態変更と復旧を 1 つのコマンドに連結しない

作業ツリー・プロセス・環境の状態を変える操作とその復旧操作を、
失敗やタイムアウトしうる処理と同一のシェルコマンドに連結しない。
git stash に限らず、環境変数の一時変更・サービスの一時停止・設定の書き換えなど、
「後で元に戻す」前提の操作すべてに適用する。

- 状態変更 → 本処理 → 復旧を、それぞれ別の Bash 呼び出しに分ける
- 復旧の直後に状態確認（`git status` / `git stash list` 等）をセットで実行する
- 「まとめれば速い」という効率より、「途中で切れたら復旧が走らない」という
  シェル連結の性質と、その操作の失敗時被害を優先して評価する。
  判定基準: このコマンドが途中で死んだとき、次に打つコマンドから見えている状態は安全か

## 1 回の呼び出しに複数の文を置くなら、先頭の失敗で止まるようにする

改行で文を並べると、前の文が失敗しても後続が走る。`&&` で繋いだ文の後ろに
改行で別の文を足すと、守られた文と守られていない文が同居する。

- 全体を `&&` で繋ぐか、先頭に `set -e` を置く。どちらもしないなら 1 呼び出し 1 文にする
- 判定基準: 先頭の文が失敗したとき、後続が走って困るか。困るなら止まる形にする
- 失敗を握り潰さない。`cd` や `mkdir` の失敗が見えないまま後続のファイル操作が走ると、
  意図しない場所へ書き込む

## 元に戻せない操作は、それ単独で実行する

`rm` / `mv` / `>` によるファイルの削除・上書き・移動は、1 回の呼び出しにその操作だけを置く。
同じ呼び出しに `ls` / `grep` / `echo` のような確認や表示を混ぜない。

- 判定基準: そのコマンドの目的は確認か、変更か。両方だと答えたなら分ける
- 出力の文言を副作用の代わりにしない。`echo "削除しない"` と書いても、
  同じ行の `rm` は実行される
- 対象を確認してから消すなら、確認だけのコマンドを先に実行し、結果を見てから削除を書く

why: 確認の意図を echo の文言で表しても、同じ行の `rm` は実行される。
確認と変更を同じ呼び出しに置くと、確認の結果を見る前に変更が走る。

## 変更と commit を連結するなら、変更の結果を commit の条件にする

スクリプトで編集した結果を同じ呼び出しで commit するときは、編集の成否ではなく、
意図した差分が入っていることを commit の条件にする。`set -e` は関数越しやヒアドキュメントで
効かないことがあり、編集が失敗しても commit が走る。

- 編集の後に、触るはずのファイル全部に差分があることを確かめる（`git diff --quiet -- <file>` が非ゼロ）。
  無ければ commit しない
- 確かめる手段が無いなら、編集と commit を別の呼び出しにし、差分を見てから commit を書く

判定基準: 編集が途中で止まったとき、この呼び出しは commit を作るか。作るなら条件が足りない。

## why

シェル連結（`&&` / `;`）は途中で打ち切られると後続が実行されず、復旧だけが失われる。
タイムアウトや失敗で退避されたままの作業ツリーは、差分が空のまま検証・レビュー・コミットへ
進んでも検知されにくい。
