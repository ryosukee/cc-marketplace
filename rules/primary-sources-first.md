# 調査は一次情報から始める

技術調査・設計判断の裏取りは、Web 検索より先に手元の一次情報を当たる。

## 適用場面

「調査」と銘打った作業だけでなく、環境・ツール・ライブラリの仕様を述べるすべての場面が対象。
設計案の説明、提案の根拠、質問への回答の中で仕様を断定するときも、先に一次情報を当たる。

判定基準: その記述を「たぶんこうだ」と思って書いたなら、まだ裏を取っていない。
既存実装・公式ドキュメント・変更履歴のどれかで確認してから書く。
確認できないものは「未確認」と明示する。

## 探索順序

1. 手元の repo (ghq_root 配下): 対象そのものの実装・docs・git 履歴
2. registry・台帳類: dotclaude registry (`~/.claude/plugins/data/dotclaude-cc-tools/registry.json`) 等の参照 repo リスト
3. 過去セッションの成果物: handover、設計ドキュメント、transcript
4. ここまでで足りないものだけ Web 検索・公式ドキュメントで調べる

git 履歴も一次情報に含める。過去にどう判断してなぜ変えたかの記録は、
現 HEAD に無いドキュメントでも `git show <rev>:<path>` で読める。

## 自分の記述を出典の代わりにしない

一度自分で書いた要約・説明・判定を、次に同じことを書くときの根拠にしない。
そのつど原文を開き直す。

- 判定基準は「たぶんこうだ」と思ったかではなく、いま手元に原文があるか。
  確信があっても、原文を見ずに書いているなら裏を取っていない
- 要約は限定・条件・例外を落とす。落ちたことは要約の側からは分からないので、
  「さっき確認した」を根拠にできない
- 自分の文書に規定・仕様・記録への参照を書くときは、参照先の実在を確かめてから書く。
  「そういう規定があるはずだ」で書かない

## why

手元の一次情報には、Web 検索では得られない判断の経緯（移行の理由、既にある台帳）が残っている。
推測で議論を進めると、既に決まっていることを再設計し、既にあるものを再発明する。
手元の探索は Web 検索より速い。
