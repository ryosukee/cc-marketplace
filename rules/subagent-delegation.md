# subagent への委譲

作業を subagent に委譲するかの判断、委譲先とモデルの選び方、依頼文の書き方、成果物の検算を定める。
いま Claude Code と Codex のどちらで動いているかで分かれる手順は、末尾の小節に置く。

## subagent の起動は依頼を待たずに行ってよい

ユーザーは、subagent の起動・委譲・並列での作業を、この rule で明示的に求める。
作業のたびにユーザーから起動の依頼が来るのを待たずに、subagent を起動してよい。

## 判断の基準はコンテキストの節約

まとまった作業を渡して結論だけを受け取れるなら委譲する。
探索の過程・読んだファイルの中身・試行錯誤がメインセッションに残らないほうが、
セッション全体としては得になる。

ためらう理由になるのは、結論だけでは足りず、
過程そのものをメインセッションに残す必要がある場合だけ。

- 対象のファイルが分かっている単発の読み取りは直接読む。委譲を挟むほうが遅い
- 会話の文脈が要る作業でも、過程をメインセッションに残したくないなら、会話を引き継ぐ起動（fork）で委譲する。
  会話を持たない subagent に渡すと、文脈を依頼文へ書き写す手間がかかり、写し漏れた前提で作業される

## 委譲先とモデルは、起動のたびに用途で選ぶ

委譲先は、Claude がメインのセッションなら Claude の subagent と Codex の 2 系統、
Codex がメインのセッションなら Codex の subagent だけにする。Codex から Claude へは委譲しない。
subagent を起動するたびに、作業の範囲、検算の方法、途中で必要になる判断からモデルを選ぶ。
会話の文脈を引き継がなくてよい場合は、Claude の使用量を抑えるため Codex を優先する。
文脈を引き継ぐ必要がある場合は、メインセッションと同じ系統の subagent に fork で渡す。
モデル指定と fork の制約は、末尾の CodingAgent 別の節に従う。

| 作業 | Claude の候補 | Codex の候補 |
| --- | --- | --- |
| 抽出・分類・定型変換 | Haiku 5.5 | `gpt-6-luna` / low |
| 範囲が明確な調査・実装・文書作成 | Sonnet 5.5 | `gpt-6.1-sol` / medium |
| 複雑な判断・長時間の実装・監査 | Opus 5.5 | `gpt-6.1-sol` / high |
| 通常候補が要件を満たせない問題 | Fable 5.1 | `gpt-6-astra` / medium |

※ 表 1 作業ごとの開始候補。Codex の `/` の後ろは reasoning effort。同じ行のモデルが同等性能という意味ではない

- 抽出・分類・定型変換は、対象と判定条件を指定でき、原文または機械検査で結果を確かめられる作業に限る。
  ファイル列挙、根拠箇所の抽出、決められた分類、要約、整形、既知のコマンドの実行が該当する。
  探索範囲や分類基準を作る判断まで渡す場合は、次の候補から選ぶ
- 範囲が明確な調査・実装・文書作成には、局所的な不具合修正、複数資料の突合、受け入れ条件が明確なレビューを含める。
  資料が長いことやファイルが多いことだけを理由に Opus・Fable・Astra を選ばない
- 複雑な判断・長時間の実装・監査は、矛盾する要件の整理、設計上の取捨、広範囲の改修、例外や規範の欠落を探すレビューに使う。
  誤りを検算で見つけにくい作業や、途中で方針を立て直す必要がある作業もここから始める
- Fable・Astra は、通常候補で満たせない要件を説明できる場合に選ぶ。
  Claude では Opus の高 effort でも足りない高度な推論や長時間の作業、Codex では Sol の高 effort でも品質を満たせない問題が該当する。
  Astra は、同じ種類の作業の測定で Sol より早く完了すると確かめられた場合に、所要時間の要件を満たす候補としても選べる。
  最初からその不足を予測できる根拠がある場合は、失敗する起動を先に挟む必要はない

why: 委譲の費用と所要時間には、モデルの実行だけでなく、やり直しと親の検算も含まれる。
作業を分割し、品質を満たす候補を選ぶことで、定型作業の使用量を抑えながら判断が必要な箇所に性能を使える。

### effort とモデルを切り替える

- Codex の単純な抽出は `low`、診断・比較・実装は `medium` から始める。
  複数の制約を同時に扱う作業では `high` を使う。
  `xhigh`・`max` は、代表的な作業で品質の改善を確かめた場合に使う。Luna を一律に `high` にしない
- Claude の effort は、使う起動方法で指定できる場合に選ぶ。
  Haiku・Sonnet・Opus は `medium`、Fable は `high` を開始候補とし、例外の検証や難しい不具合の診断には `high` 以上を検討する。
  指定方法は[Claude Code では](#claude-code-では)に従う
- 要件を満たさなかったら、入力や依頼文の不足を先に確かめる。
  判断の深さが足りない場合は同じモデルの effort を上げ、方針の維持や例外の発見が足りない場合はモデルを切り替える。
  同じ条件での再起動を繰り返さない
- 切り替えるときは、失敗した要件と検算結果を次の依頼に渡す。
  前のモデルの結論だけを引き継がない

why: effort は推論に使う量を変える設定であり、モデル間の能力を揃える尺度ではない。
入力不足を直さずにモデルや effort を変えると、誤った前提のまま使用量だけが増える。

### モデルの更新・利用不可が分かった場合

通常の委譲では、表 1 と用途・effort の基準で選び、モデルの詳細情報を調べ直さない。
表の候補を利用できないことが分かった場合や、新しい版の公開を知った場合に限り、
該当するモデルと状況をユーザーに伝え、候補と選定基準を見直すか確認する。
承認を得るまで、代替モデルを独自に選んだり選定基準を変更したりしない。

why: モデルの更新や利用可否の変化は、作業への割り当てを見直す理由になる。
通常の委譲と区別せずに扱うと、ユーザーの確認なしに選定基準が変わる。

## 起動したら報告する

subagent を起動したら、結果と一緒に次を伝える。黙って並列に投げない。

- 起動した subagent の数
- それぞれに任せた作業
- それぞれの委譲先（Claude か Codex か）、モデル、指定した effort。継承した場合は継承と書く
- Fable・Astra を選んだ場合は、通常候補では要件を満たせない理由

## Fable・Astra と高 effort の起動前に使用量を確かめる

Fable・Astra、または `xhigh`・`max` の subagent を起動する前に、週の上限に対する残りと、
1 日あたりの目安に対する今日の消費を確かめる。起動を重ねるたびに、残量を取り直す。

- 起動すると今日の消費が 1 日の目安を超える見込みなら、起動する前に消費の見込みと残りを伝え、
  続けるか、ペースを落とすかを確認する
- 残量や消費の見込みを取得できないときは、分からない項目を伝え、該当する起動を 1 回ずつに区切る
- API の token 単価を、Claude Code・Codex の契約枠の消費率として扱わない。
  fork の入力、出力、推論、再試行を含む作業全体で評価する

why: 高い effort や複数の同時起動は、結果を受け取る前に使用量を増やす。
残量と作業全体の消費を見ずに起動を重ねると、他の作業に使う分まで使い切る。

## 待っている間に、結果に依存しない作業を進める

subagent とバックグラウンド処理の完了を待つ間、その結果に依存しない作業は先に進める。

- 着手前に、残りの作業を「結果に依存する」「依存しない」で分ける。依存しないものから片付ける
- 待機の報告だけのターンを作らない。ツールを 1 つも呼ばないターンは、
  ユーザーから見ると停止と区別がつかない
- 依存しない作業が本当に無いときだけ、待っていることを 1 行で伝える

判定基準: いま返そうとしているメッセージに、待っていること以外の中身があるか。
無いなら、先に進められる作業が残っていないかを数え直す。

## 依頼文の条件は、絞る意図があるものだけにする

依頼文に書いた条件は、渡した先が探す範囲を限る。
その範囲へ本当に絞りたいのかを、条件ごとに確かめてから書く。

- 条件を 1 つずつ読み、絞る意図があるものと、状況の説明として書いたものを分ける。
  後者は消すか、絞る条件ではないと明示する
- 絞る意図があるなら、絞ることを書く。判定してほしい条件なら、判定してほしいと書く
- 判定基準: その条件を外したら、返ってくる候補が増えるか。増えるなら絞っている

why: 絞る条件と状況の説明は、依頼文の中で同じ形をしている。渡した先は区別できないので、
絞る意図の無い条件も範囲を限るものとして扱われる。範囲内では正しい結論が返るため、
絞ったことは成果物からは分からない。

## 「結果の返し方」と「委譲先での作業のスコープ」を依頼文で明示的に限定する

fork でない委譲先は起動した側の会話を持たず、依頼文と、自分に見える skill の説明だけで動き方を決める。
fork した委譲先は会話を持つので、会話の中で話題になった作業まで自分の範囲と受け取りうる。
どちらの場合も、依頼文に次の 4 つを書く。

- 結果の返し方: 返答のテキストで返すのか、ファイルに書くのか。テキストで返させるなら、
  報告用のページやファイルを作る skill を使わないことも書く
- skill の使用: 調べもの・検算のように skill の手順が要らない依頼では、skill を使わないと書く
- 入れ子の起動: さらに subagent を起動してよいか。起動してよいなら、起動できる subagent の数の上限とモデルを書く
- 書き込みの範囲: 書き込みを伴う作業なら、書き換えてよいファイルまたはディレクトリと、それ以外を変えないことを書く。
  委譲先を問わず、範囲を書けば書き込みも委譲してよい

判定基準: 依頼文だけを読んだ委譲先が、何を返せば終わりか、どこまで作業を広げてよいか、
どのファイルなら書き換えてよいかを答えられるか。

why: skill の説明の多くはメインのセッションに向けて書かれていて、報告や調査の依頼文に当たりやすい。
依頼文が返し方と作業の広さを限らないと、委譲先は skill を使って成果物の形を変え、
さらに subagent を並べて使用量を増やす。書き込みの範囲が無いと、目的に近いと判断したファイルまで書き換える。
起動した側は、結果が返ってくるまでそれに気づけない。

## 受け取った成果物は依頼時の要件で検算する

起動時に出した要件は、そのまま受け入れ基準になる。返ってきた成果物が要件を満たしているかを
確認してから使う。委譲先は要件と反する結論を、根拠を添えて返すことがある。

- 判定基準: 依頼文に書いた「〜が要件」「〜してはいけない」の各項目について、
  成果物のどこで満たされているかを指せるか。指せないものは満たされていない
- 書き込みを委譲したときは差分を読み、書き換えてよい範囲の外が変わっていないことを確かめる
- 根拠の厚みと要件の充足は別の軸。調査量で品質を測らない
- 要件と反する結論が返ったときは、要件の側が誤っていたのか成果物が誤っているのかを
  切り分けてから採否を決める

## Claude Code では

- Claude の subagent は Agent ツールで起動し、`model` 引数でモデルを指定する。
  `model` 引数が無い場合は、agent 定義の `model`、`CLAUDE_CODE_SUBAGENT_MODEL`、親のモデルの順に使う。
  `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` が有効な場合やモデルの利用制限がある場合は、指定値どおりに動くとは限らないため実際のモデルを確認する
- Agent ツールの `model` 引数は、`haiku`・`sonnet`・`opus`・`fable` の alias だけを受け付ける。
  `claude-sonnet-5-5` のような版名を渡すと、入力の検証で拒否されて起動しない。
  alias は、接続先や親のモデルによって別の版を指すことがある
- 表 1 の公開版に固定する場合は、agent 定義の `model` frontmatter に
  `claude-haiku-5-5`、`claude-sonnet-5-5`、`claude-opus-5-5`、`claude-fable-5-1` を書く。
  frontmatter は版名を受け付ける（[Subagents の Choose a model](https://code.claude.com/docs/en/sub-agents)）。
  Haiku 5.5 は Claude Code v2.1.293 以降で使う
- effort は subagent 定義の `effort` frontmatter で指定できるが、環境変数や契約・組織の上限が優先される場合がある。
  起動ツールに effort の指定欄が無い場合は、定義またはセッションから引き継いだ値を確認する。
  依頼文に effort を書くだけでは設定したことにしない。委譲のために永続設定を自動変更しない
- fork（`subagent_type: fork`）は `model` を無視して親のモデルを継承する。
  fork を使うのは、会話の文脈をそのまま渡す必要があるときだけにする
- Workflow ツールと deep research は依頼のたびに確認する。起動数とコストの桁が subagent と違う

### Codex への委譲

Bash で `codex exec` を呼ぶ。依頼文は引数で渡し、結果は `-o` のファイルから読む。
`-p dotfiles` はユーザーが普段使う Codex の設定で、付けないと既定のモデルなどが変わる。

```bash
codex exec -p dotfiles -s read-only -C <作業ディレクトリの絶対パス> \
  -m gpt-6.1-sol -c model_reasoning_effort="medium" \
  -o <scratchpad>/codex-<名前>.txt "<依頼文>" < /dev/null
```

- `-s` は必ず書く。読み取りだけなら `read-only`、書き込みを委譲するなら `workspace-write` にし、
  書き換えてよい範囲を依頼文に書く
- 依頼文の冒頭に、`codex exec` で委譲された作業であることと、さらに `codex exec` を呼ばないことを書く
- 数分かかりうる依頼は `run_in_background` で起動する
- 終了コードが 0 以外なら、stderr を読んで報告し、同じ依頼を Claude の subagent に渡す

why: `codex exec` で起動した Codex にも、この rule が読み込まれる。
委譲された側だと書かなければ、Codex がこの節に従ってさらに `codex exec` を呼ぶ。

## Codex では

- subagent は `spawn_agent` で起動し、`model` と `reasoning_effort` の引数でモデルを指定する。
  この rule は、用途に合わせたモデルの指定をユーザーが求めるものとして扱う
- 会話の履歴を渡す起動（`fork_turns` が `all` か直近のターン数）は、会話の文脈をそのまま渡す必要があるときだけにする
- モデルを選んで渡すときは、`fork_turns: "none"` で必要な前提を依頼文に書く。
  `fork_turns: "all"` は親のモデルと effort を継承するため、`model` と `reasoning_effort` の上書き指定を併用しない。
  直近のターン数を渡す場合は、そのセッションのツール定義で上書き可否を確かめる
- `codex exec` で委譲されたセッションでは、`codex exec` を呼ばない
- `claude -p` などで Claude に作業を委譲しない。表 1 の Claude の列は、Claude がメインのセッションのときだけ使う

## why

コンテキストの残量はセッションの寿命そのもので、subagent の起動コストより失うものが大きい。
起動を渋るほど、メインセッションが中間生成物で埋まる。
