# subagent への委譲

作業を subagent に委譲するかの判断、委譲先とモデルの選び方、依頼文の書き方、成果物の検算を定める。
いま Claude Code と Codex のどちらで動いているかで分かれる手順は、末尾の小節に置く。

## subagent の起動は依頼を待たずに行ってよい

ユーザーは、subagent の起動・委譲・並列での作業を、この rule で明示的に求める。
作業のたびにユーザーから起動の依頼が来るのを待たずに、subagent を起動してよい。

## 判断の基準はコンテキストの節約

まとまった作業を渡して結論だけを受け取れるなら委譲する。
探索の過程・読んだファイルの中身・試行錯誤がメインセッションに残らないほうが、
セッション全体としては得になる。

ためらう理由になるのは、結論だけでは足りず、
過程そのものをメインセッションに残す必要がある場合だけ。

- 対象のファイルが分かっている単発の読み取りは直接読む。委譲を挟むほうが遅い
- 会話の文脈が要る作業でも、過程をメインセッションに残したくないなら、会話を引き継ぐ起動（fork）で委譲する。
  会話を持たない subagent に渡すと、文脈を依頼文へ書き写す手間がかかり、写し漏れた前提で作業される

## 委譲先とモデルは、起動のたびに用途で選ぶ

委譲先は、Claude がメインのセッションなら Claude の subagent と Codex の 2 系統、
Codex がメインのセッションなら Codex の subagent だけにする。Codex から Claude へは委譲しない。
subagent を起動するたびに、用途からモデルを選んで指定する。

| 推論性能 | 用途 | Claude | Codex |
| --- | --- | --- | --- |
| 弱 | 手順が決まっている作業。原文との突合、行番号の確認、ファイルの列挙、書式の検査、スクリプトの実行と結果の整形 | sonnet | gpt-6-luna（effort high） |
| 中 | 判断を伴う作業。長い資料の分類・要約、複数の資料の食い違いの発見、規範に照らした文の判定、成果物の本文 | opus | gpt-6-sol（effort medium） |
| 強 | 中性能のモデルでは足りない高度な判断 | fable | gpt-6-astra（effort low から） |

※ 表 1 推論性能と用途ごとの委譲先のモデル

- 強性能のモデルは基本的には使わない。判定基準: 中性能のモデルでは足りない理由を、依頼の報告に 1 行で書けるか。
  書けないなら中性能のモデルにする
- メインのセッションの文脈を引き継がなくてよい場合は、Codex を選ぶ。
  Codex を選べば、Claude のトークン使用を抑えられる
- 文脈を引き継ぐ必要がある作業は、メインのセッションと同じ系統の subagent に fork で渡す。
  fork でのモデルの扱いは、末尾の小節にある

why: 手順が決まっている作業は、どのモデルに渡しても成果物が変わらない。
判断を伴う作業も、メインセッションが要件で検算する前提なら中性能のモデルで足りる。

## 起動したら報告する

subagent を起動したら、結果と一緒に次を伝える。黙って並列に投げない。

- 起動した subagent の数
- それぞれに任せた作業
- それぞれの委譲先（Claude か Codex か）とモデル
- 強性能のモデルを選んだ subagent については、中性能のモデルでは足りない理由

## 待っている間に、結果に依存しない作業を進める

subagent とバックグラウンド処理の完了を待つ間、その結果に依存しない作業は先に進める。

- 着手前に、残りの作業を「結果に依存する」「依存しない」で分ける。依存しないものから片付ける
- 待機の報告だけのターンを作らない。ツールを 1 つも呼ばないターンは、
  ユーザーから見ると停止と区別がつかない
- 依存しない作業が本当に無いときだけ、待っていることを 1 行で伝える

判定基準: いま返そうとしているメッセージに、待っていること以外の中身があるか。
無いなら、先に進められる作業が残っていないかを数え直す。

## 依頼文の条件は、絞る意図があるものだけにする

依頼文に書いた条件は、渡した先が探す範囲を限る。
その範囲へ本当に絞りたいのかを、条件ごとに確かめてから書く。

- 条件を 1 つずつ読み、絞る意図があるものと、状況の説明として書いたものを分ける。
  後者は消すか、絞る条件ではないと明示する
- 絞る意図があるなら、絞ることを書く。判定してほしい条件なら、判定してほしいと書く
- 判定基準: その条件を外したら、返ってくる候補が増えるか。増えるなら絞っている

why: 絞る条件と状況の説明は、依頼文の中で同じ形をしている。渡した先は区別できないので、
絞る意図の無い条件も範囲を限るものとして扱われる。範囲内では正しい結論が返るため、
絞ったことは成果物からは分からない。

## 「結果の返し方」と「委譲先での作業のスコープ」を依頼文で明示的に限定する

fork でない委譲先は起動した側の会話を持たず、依頼文と、自分に見える skill の説明だけで動き方を決める。
fork した委譲先は会話を持つので、会話の中で話題になった作業まで自分の範囲と受け取りうる。
どちらの場合も、依頼文に次の 4 つを書く。

- 結果の返し方: 返答のテキストで返すのか、ファイルに書くのか。テキストで返させるなら、
  報告用のページやファイルを作る skill を使わないことも書く
- skill の使用: 調べもの・検算のように skill の手順が要らない依頼では、skill を使わないと書く
- 入れ子の起動: さらに subagent を起動してよいか。起動してよいなら、起動できる subagent の数の上限とモデルを書く
- 書き込みの範囲: 書き込みを伴う作業なら、書き換えてよいファイルまたはディレクトリと、それ以外を変えないことを書く。
  委譲先を問わず、範囲を書けば書き込みも委譲してよい

判定基準: 依頼文だけを読んだ委譲先が、何を返せば終わりか、どこまで作業を広げてよいか、
どのファイルなら書き換えてよいかを答えられるか。

why: skill の説明の多くはメインのセッションに向けて書かれていて、報告や調査の依頼文に当たりやすい。
依頼文が返し方と作業の広さを限らないと、委譲先は skill を使って成果物の形を変え、
さらに subagent を並べて使用量を増やす。書き込みの範囲が無いと、目的に近いと判断したファイルまで書き換える。
起動した側は、結果が返ってくるまでそれに気づけない。

## 受け取った成果物は依頼時の要件で検算する

起動時に出した要件は、そのまま受け入れ基準になる。返ってきた成果物が要件を満たしているかを
確認してから使う。委譲先は要件と反する結論を、根拠を添えて返すことがある。

- 判定基準: 依頼文に書いた「〜が要件」「〜してはいけない」の各項目について、
  成果物のどこで満たされているかを指せるか。指せないものは満たされていない
- 書き込みを委譲したときは差分を読み、書き換えてよい範囲の外が変わっていないことを確かめる
- 根拠の厚みと要件の充足は別の軸。調査量で品質を測らない
- 要件と反する結論が返ったときは、要件の側が誤っていたのか成果物が誤っているのかを
  切り分けてから採否を決める

## Claude Code では

- Claude の subagent は Agent ツールで起動し、`model` 引数でモデルを指定する。
  指定しないとメインセッションのモデルを継承する。agent 定義の frontmatter に `model` があればそれが既定になるが、
  `model` 引数はその既定より優先される
- fork（`subagent_type: fork`）は `model` を無視して親のモデルを継承する。
  fork を使うのは、会話の文脈をそのまま渡す必要があるときだけにする
- Workflow ツールと deep research は依頼のたびに確認する。起動数とコストの桁が subagent と違う

### Codex への委譲

Bash で `codex exec` を呼ぶ。依頼文は引数で渡し、結果は `-o` のファイルから読む。
`-p dotfiles` はユーザーが普段使う Codex の設定で、付けないと既定のモデルなどが変わる。

```bash
codex exec -p dotfiles -s read-only -C <作業ディレクトリの絶対パス> \
  -m gpt-6-sol -c model_reasoning_effort="medium" \
  -o <scratchpad>/codex-<名前>.txt "<依頼文>" < /dev/null
```

- `-s` は必ず書く。読み取りだけなら `read-only`、書き込みを委譲するなら `workspace-write` にし、
  書き換えてよい範囲を依頼文に書く
- 依頼文の冒頭に、`codex exec` で委譲された作業であることと、さらに `codex exec` を呼ばないことを書く
- 数分かかりうる依頼は `run_in_background` で起動する
- 終了コードが 0 以外なら、stderr を読んで報告し、同じ依頼を Claude の subagent に渡す

why: `codex exec` で起動した Codex にも、この rule が読み込まれる。
委譲された側だと書かなければ、Codex がこの節に従ってさらに `codex exec` を呼ぶ。

## Codex では

- subagent は `spawn_agent` で起動し、`model` と `reasoning_effort` の引数でモデルを指定する。
  この rule は、用途に合わせたモデルの指定をユーザーが求めるものとして扱う
- 会話の履歴を渡す起動（`fork_turns` が `all` か直近のターン数）は、会話の文脈をそのまま渡す必要があるときだけにする
- `codex exec` で委譲されたセッションでは、`codex exec` を呼ばない
- `claude -p` などで Claude に作業を委譲しない。表 1 の Claude の列は、Claude がメインのセッションのときだけ使う

## why

コンテキストの残量はセッションの寿命そのもので、subagent の起動コストより失うものが大きい。
起動を渋るほど、メインセッションが中間生成物で埋まる。
