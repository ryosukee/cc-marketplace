# skill の書き方

SKILL.md の種別の判定・frontmatter・本文の構成と文体を定める。
新規作成と改訂の両方でこの規範に従う。

## 種別を判定してから書く

skill には 2 種別ある。書き始める前にどちらかを決める。
判定基準: 読み手にさせたいことが作業の実行なら作業手順 skill、知識の参照なら参照知識 skill。
公式のドキュメントでは、参照知識 skill が Reference content、作業手順 skill が Task content にあたる。

参照知識 skill の名前には `ref-` prefix を付け、参照資材は skill ディレクトリの `references/` 配下に置く。
どちらも公式の仕様ではなく、この規範が定める慣習。

## frontmatter

- 参照知識 skill は `user-invocable: false` にする。ユーザーが直接呼ぶ入口ではなく、
  description による自動発動だけで使われるため、ユーザー向けのコマンド一覧から外す
- 作業手順 skill は `user-invocable` を指定しない。既定のままユーザーが呼べる

description は skill が発動するかを決める。次の 4 つを守る。

- 「〜に関する skill」のような受け身の要約ではなく、発動条件を能動的に書く
- 対象 skill の機能だけを書く。他 skill との関係や補完関係を含めない
- 自動で発動させたい skill は、発動点（どの作業のどの時点で読むか）と、
  発動させたい場面の言い回しを書く。読み飛ばされない強さで書く
- 用途を特定の操作（レビュー・実装等）に限定しない。同じ知識はどの操作でも参照される

## 決定論的な手続きはスクリプトに出す

作業手順 skill の中で、入力から出力が一意に決まる手続きは、本文に手順として書かずにスクリプトへ出し、
SKILL.md からはその実行を指示する。

判定基準: その手順を 2 回実行したとき、判断で結果が変わりうるか。変わらないならスクリプトにできる。

- 対象になるもの: ファイルの収集・整形・集計、決まった順序でのコマンド実行、形式が決まった出力の生成
- 対象にならないもの: 読んで判断する、案を出す、優先順位を決める

why: 決定論的な手続きを自然言語で書くと、実行のたびに解釈の揺れが入り、結果が再現しない。
トークンも毎回消費する。

## 呼び出し元を問わず動かす

作業手順 skill は、ユーザーが直接呼ぶ場面と、別の skill やセッションが呼ぶ場面のどちらからも起動する。
どちらでも動く形にする。

- 呼び出し側に固有の概念（工程名・直前の工程の成果物等）を前提にしない。
  「前工程の成果物」のような呼び出し元前提の語を避け、呼び出し元を問わない表現にする
- 入力は最小限の必須項目と、任意のコンテキスト情報で構成する
- 任意項目が無くても基本機能は動くようにする。精度は下がってよい

## 文体

作業手順 skill は、H1 直後の導入文も各ステップも定義形で書く。
導入文は skill 全体が何をするものかを述べ、ステップはその中の 1 手順を述べる。役割は違うが文体は同じ。

- OK: 「与えられた調査対象を調査し、構造化されたレポートを生成する」（導入文）
- OK: 「Read で調査対象を読む」（ステップ）
- NG: 「この skill は調査作業を支援します」（skill 自身を語っていて、何をするかの定義になっていない）

参照知識 skill の本文は宣言的に知識を書く。指示形や手順のステップを持たない。
