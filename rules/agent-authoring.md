# agent の書き方

agent（独立したコンテキストで動く subagent）の定義ファイルの、ファイル形式・frontmatter・
冒頭に書く責務・入出力の書き方を定める。新規作成と改訂の両方でこの規範に従う。

## ファイル形式

1 agent 1 ファイル。ファイル名は agent 名と一致させる（agent `code-review` なら `code-review.md`）。

## frontmatter

- 書けるフィールドは公式の一覧を引いてから決める。手元で動いているという理由だけで書かない
- `tools` は責務の遂行に必要なものから逆算して選ぶ。
  必要な tool が無いと、agent は下位の手段へ黙ってフォールバックし、指示した調べ方が効かない

## 冒頭に責務を書く

agent 定義の冒頭に、次の 6 つを書く。節に分けても地の文でもよく、節名は固定しない。
6 つのどれかが書かれていない定義を作らない。

- ゴール: この agent が達成すべきこと。達成できたかを読み手が判定できる形にする。
  description は発動条件を書く場所なので、ゴールの代わりにはならない
- やること: 具体的な作業内容
- やらないこと: 責務外の作業を why 付きで列挙する。
  「やりたくなるが踏み込むべきでない」操作を明示する
- 詰まった場合: 問題に当たったときの行動（差し戻す / 報告する）。
  判定を偽らない。沈黙して成功と紛れる報告をしない
- 完了報告: 「プロセスが完了した」と「成果物が期待を満たしている」は別の判断で、両方を分けて書く
    - プロセス結果: 検査が通った、対象を全件読んだ、といった事実
    - 品質判断: 成果物が期待する基準を満たしているかの評価
    - NG: 「検査が全件通ったので完了」（プロセス結果を品質判断にすり替えている）
    - OK: 「検査は全件 PASS。ただし 2 件は基準が対象を捉えておらず、品質は確認できていない」
- 確かめた範囲: 報告のうち、実際に確かめたことと確かめていないことを分けて書く。
  判定基準: 報告の各文について、何をどう確かめたかを 1 文で書き出せるか。書き出せないものは確かめていない

why: 冒頭に責務の全体像が無いと、手順の途中で責務を拡大解釈する。
「やらないこと」が無いと、関連する作業に踏み込んでコンテキストとターンを浪費し、本来の責務がおろそかになる。
プロセスの完了を成果の品質と混同すると、壊れた成果物が「完了」として報告される。

## 入力と出力を明示する

- どんな情報を受け取り、何を返すかを書く
- 手順は具体的に書く。実行するコマンド、読むファイル、判断基準を書く
