# rule の書き方

rule ファイルの命名・冒頭・参照・改訂と、ロード方式の使い分けを定める。
新規作成と改訂の両方でこの規範に従う。

## 命名

- ファイル名は kebab-case の名詞句にする (例: `markdown-formatting.md`)

## 冒頭

- 冒頭に、この rule が何を定めるかを 1〜3 行で書く。適用範囲は paths が表すので本文で言い直さない。
  paths で表現できない条件（担い手・場面）だけを冒頭に書く

## ロード方式の使い分け

ロード方式は 3 つある。その規範を届けたい場面で選ぶ。

- 常時ロード (frontmatter に paths を書かない): セッション開始時に無条件で読み込まれる。
  どの作業でも効かせたい規範だけに使う。全セッションのコンテキストを消費する
- 条件ロード (paths に対象パターンを書く): 一致するファイルを読んだときだけ載る。
  特定の種類のファイルを編集する場面の規範はこちらに置く
- 参照専用 (paths にどのファイルにも一致しない値を置く。例: `never-match-reference-only`):
  自動ロードから外し、他の文書からの参照経由の Read だけで読ませる。
  サブディレクトリに置くだけでは外れない（`rules/` は subdir まで再帰的に常時ロードされる）

rule はセッション開始時に一度だけ読まれる。セッション中に追加・変更した rule は、
そのセッションでは効かない。commit した直後に「効いている」と扱わず、次のセッションで確認する。

## 参照

- 自動ロードで既に載る文書に言及しない。paths が一致する rule と常時ロードの rule は、
  対象ファイルの編集時点で読み込まれているので、言及は重複になる
- 外側の構造に言及しない。「この rule は X から参照される」のような呼ばれ方も、
  「共通原則の上にこれを重ねる」のような層の関係も書かない。
  どの文書を読ませるかの誘導は、入口・呼び出す側が持つ
- 読み手を辿らせる責任がその文書にあるとき（入口 rule、呼び出す側の skill）は、
  自動ロードされない参照先への参照を書く

## アンチパターン節の書式

アンチパターンを列挙するときは 2 カラム表で書き、両カラムとも肯定文（「〜する」）で統一する。
否定文と肯定文が混在すると、どちらが推奨か解釈が曖昧になる。
カラム名が役割を分けているので、中身は肯定文だけで伝わる。

```markdown
| アンチパターン | 代わりにどうするか |
| --- | --- |
| 太字見出しで段落を区切る | サブセクションか箇条書きのネストにする |
```

## why の書き方

- why には、その条項が無いと何が壊れるかという本質的な理由を書く
- 日付付きの具体事例を書かない。事例は書いた時点の場面に縛られ、場面の形が変わると
  条項を支えなくなる。事例から抽出した構造だけを理由として残す

## 改訂

- rule 自身を書き直すとき、その rule の既存記述を書き直しの根拠に使わない。
  判断根拠は実態（コード・実測・一般原則）から取る。
  既存記述に誤りがあるとき、それを根拠にすると誤りが「rule に書いてある」という権威で固定化する。
  why: 書き直しの対象になっている時点で、その rule には実態に合わない記述が
  含まれている疑いがある。rule を直すモードでは、まず rule の側を疑う
