# 判断文書の規範

読者に判断か行動をさせる文書に適用する。例: 設計書、ADR、RFC、提案書、
技術調査・検証レポート、障害報告・進捗報告、PR 説明、Issue、コミットメッセージ、
チャットやターミナルでの報告・返答。結論と根拠の距離を最短にする。

## 構成

- 文書・節・段落のどれも、読者が最初に知りたい答え（文書なら結論・推奨）から始める（重点先行）。
  「A を推奨する。理由は 2 点」から始め、調査の経緯は後ろへ送る
- 冒頭に地図を置く: 目的 / 決めること
- 「読み方」の節は書かない。どこから読むか・どこを飛ばしてよいかの案内を置かず、
  構成と見出しで分かるようにする。案内が要る時点で構成が悪い
- 調査や参照で読んだ資料の節順・出来事の時系列をなぞらない。節ごとの要約や
  発生順の羅列にせず、テーマごとに整理し直す
- 調査は方法と結果を分けて書き、再現条件（環境・バージョン・手順）を残す
- 調べたことを報告するかは、読者の判断に効くかで決める。対象の現状（何がどこにあるか）、
  既にできている部分、関連する既存のパターン、未確定事項は判断に効くので示す。
  本題に入る前の下調べで把握しただけのことは効かないので報告せず、内部に保持して以降の判断に使う
- 後で参照する必要のない固有名（ファイル名・関数名・識別子）を本文に出さず、
  一般的な言い方で済ませる

## 選択肢と推奨

案を提示する場面に適用する。

- 候補は、まず種別（どんな型の手段がありうるか）を全件並べてから絞る。
  落とした種別と落とした理由を残し、残った候補だけを最初から並べたように書かない
- 選択肢の比較は観点を揃える（列 = 選択肢、行 = 観点）
- 推奨には根拠を併記し、推奨以外も選べること（覆せること）を明示する。
  採らない選択肢にも、落とした理由を 1 文添える
- 推奨の根拠は、他案を排除する理由で書く。推奨案の利点だけでは根拠にならない。
  「A は速い」ではなく「B は速いが復旧手段が無い」を書く
- 管理する対象（ファイル・仕組み）を増やす提案には、増える対象と減る対象の差し引きと、
  維持コストを書く

## 関心事

- 判断の前提・経緯・再現条件と、調査・検証の結果は、この文書では分離の対象ではなく
  本体として残す

## 事実の扱い

- 事実と解釈は「ログに X が出ている（事実）。原因は Y と考える（解釈）」の形で書き分ける
- 複数の要因がある事象を単一の原因に還元しない。どの根拠がどの主張を支えるかを対応づける
- 数値には出典・エビデンスへのリンクを添え、参照先のどこを根拠にしているかを本文に書く
- 未確認の項目は、本文へ散らさず未確認と明示した一覧にまとめる
- 判断の前提にした制約（期限・リソース・既存構成）を本文に残す。前提が変われば結論が変わるため
- 「調べたが問題なかった」「変更なし」の類は、読者の行動を変えない記述でも、
  読者がその点を疑いうるなら残す
- 前回から変えた箇所を「変更なし」「〜のまま」と書かない
- 実行して得た結果を書くときは、誰が実行したかを明示する
- 原因を述べるときは、読者が自然に疑う別の原因を先回りして排除する。
  「疑われた側は正しかった」と明示し、疑いを残したまま結論へ進まない
- 現状と理想を対比するときは、理想の側を何が定めているのかを明示する。
  主語が無いと、扱っている対象自身の話なのか外部の仕様の話なのかが読み取れない。
  対比そのものは「本来 X / 実際 Y」の短い形で足りる

## 指摘と応答を書くとき

自分が、他者の成果物への指摘や、他者の記述への返信を書く場面に適用する。

- 指摘ごとに 2 点を書く。何が問題か（該当箇所の引用）と、なぜそう言えるか
  （根拠にした実物の所在。無いなら「疑い」と明記する）
- 矛盾を見つけたら、どちらが正かは決めない。両方の該当箇所を引用して並べる
- 他者の記述を受けて書くときは、自分がそれをどう読んだかを明示する。
  解釈を書いておくと、相手が認識のずれを早い段階で検出できる

## 報告の短縮形

報告・返答は判断文書の圧縮版として書く。

- 縮約（要約・報告）に、元の本文・元の調査結果にない主張を入れない
- 長い経緯は参照先へ逃し、本文は読者が次の行動を決めるのに必要な分だけにする
- 次のアクション（誰が・何を・いつまでに）を明示して終える
