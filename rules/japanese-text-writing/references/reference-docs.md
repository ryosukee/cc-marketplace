# 参照ドキュメントの規範

対象: README、API リファレンス、設定ガイド、運用手順、セットアップ手順。
読者はこれを通読せず「使う」。必要な箇所へ最短で到達でき、読んだとおりに実行できることを最優先する。

## 到達性

- 文書・節・段落のどれも、読者が最初に知りたい答えから始める（重点先行）。
  背景や経緯は結論の後ろに置く
- 冒頭に地図を置く: このドキュメントが何で、誰が、いつ使うものかを 3 行以内で書く。
  範囲の宣言（対象読者・扱う範囲・扱わない範囲・前提知識）も冒頭に残す
- 見出しだけを拾って目的の節に到達できる構成にする
- 1 節 1 トピック。同じ情報を複数の節に書かない（変更時に矛盾の原因になる）
- 主題は 1 フレーズで言い切り、詳細は下位の階層へ送る。
  一つの項目に複数の情報（何を・なぜ・どう）を詰めない
- 概要と詳細で抽象レベルを分ける。概要には方針レベルのことだけを書き、
  個別の要素名・手順・実装の詳細は詳細側に置く
- まだ読んでいない後続の内容を前提にした条件を、判断材料として書かない。
  読者はその時点でその条件を判定できない
- 読者が自力で補える中間段階の説明は書かない。
  数文にわたる議論を一文に圧縮できるなら、圧縮した一文だけを残す
- 節として立つ内容なら、行頭のラベルではなく見出しにする。
  ラベルが無くても内容が分かるなら、ラベルごと消して地の文にする
- 再開・再現を目的とする文書では、識別子（ファイル名・パス・コミット ID）そのものが情報にあたる。
  省略せずそのまま書く
- 記述を変えたら、同じ事実を書いている他の箇所へ反映が行き渡っているかを確認する

## 手順

- 1 手順 1 操作。1 つの番号の中で 2 つの操作をさせない
- 手順の前に前提（必要な権限・環境・バージョン）、後に完了確認（何が確認できれば成功か）を書く
- コマンド・設定値は実行して確認済みのものを書く。未検証なら未検証と明示する
- 環境による分岐（OS 別など）は手順の途中で分岐させず、節を分ける

## 関心事の分離

- 運用 rule・手順書には運用の規範だけを書く。一度きりのセットアップ手順、環境固有の事情、
  導入の経緯や日付は、環境側の文書（dotfiles の docs 等）や設計記録に分離する
- 汎用 rule に固有事例を書くのは why の実例として最小限に留め、例と分かる形にする

why: 「この rule を読めば必要な情報が全部揃うべき」という自己完結バイアスが、
rule の関心事ではないセットアップ手順や移行日の混入を繰り返し生んだ（差し戻しの実例あり）。

## rule を書くとき

対象は rule・CLAUDE.md・skill などの規範文書。

- rule にするのは表面の行動ではなく、その行動を生んだ判断の構造にする。
  「X をした → X するな」の形は、場面の形が変わると適用できない
- 適用範囲を「本当にそれを必要とする対象」に絞る。広い対象へひとまとめに適用しない
- 何にでも当てはまって判断基準にならない rule になっていないか確かめる。
  誰でも同意するが行動を変える基準にならないなら広すぎる
- 補足説明が、元になった場面の再説明に化けていないか確かめる

## 参照

- 別の記述・文書を参照するときは、参照先へ辿れるリンクにする。名前をテキストで書くだけにしない
- リンクの文字列には参照先のタイトルをそのまま使う。ファイル名や識別子で代用しない
- 目次のリンクも見出しの文字列をそのまま複製する。別の文言へ要約しない
- 参照はインラインリンクで地の文に組み込むのが基本。
  組み込めないときだけ、支える記述の直後に別立てで置く
- タイトルを変えたときは、そのタイトルを指しているリンクの文字列をすべて更新する
- 参照の一覧表は、本文で触れた参照の集約インデックスとして使う。
  本文で一度も触れていない参照を、一覧表にだけ置かない

## 文体

だ体で書く。状態の表記は体言止めでよい（「デフォルト: 無効」）。
手順の指示文はですます調か命令形のどちらかに文書内で統一する。
