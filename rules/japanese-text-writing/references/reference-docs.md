# 参照ドキュメントの規範

読者に再現・実行をさせる文書に適用する。例: README、API リファレンス、設定ガイド、
運用手順、セットアップ手順、rule・CLAUDE.md・skill などの規範・運用文書。
読者はこれを通読せず「使う」。必要な箇所へ最短で到達でき、読んだとおりに実行できることを最優先する。

## 到達性

- 文書・節・段落のどれも、読者が最初に知りたい答えから始める（重点先行）。
  背景や経緯は結論の後ろに置く
- 冒頭に、このドキュメントが何で、誰が、いつ使うものかを 3 行以内で書く
- 見出しだけを拾って目的の節に到達できる構成にする
- 再開・再現を目的とする文書では、識別子（ファイル名・パス・コミット ID）そのものが
  情報にあたり、常に言及する側になる
- 記述を変えたら、同じ事実を書いている他の箇所へ反映が行き渡っているかを確認する

## 手順

- 1 手順 1 操作。1 つの番号の中で 2 つの操作をさせない
- 手順の前に前提（必要な権限・環境・バージョン）、後に完了確認（何が確認できれば成功か）を書く
- コマンド・設定値は実行して確認済みのものを書く。未実行なら未実行と明示する
- 環境による分岐（OS 別など）は手順の途中で分岐させず、節を分ける

## rule・手順書の関心事

- 運用 rule・手順書には運用の規範だけを書く。一度きりのセットアップ手順、環境固有の事情、
  導入の経緯や日付は、環境側の文書や設計記録に分離する
- 汎用 rule に固有事例を書くのは why の実例として最小限に留め、例と分かる形にする

why: 「この rule を読めば必要な情報が全部揃うべき」という自己完結バイアスが、
rule の関心事ではないセットアップ手順や導入の日付の混入を繰り返し生んだ（差し戻しの実例あり）。

## rule を書くとき

対象は rule・CLAUDE.md・skill などの規範文書。

- rule にするのは表面の行動ではなく、その行動を生んだ判断の構造にする。
  「X をした → X するな」の形は、場面の形が変わると適用できない
- 適用範囲を「本当にそれを必要とする対象」に絞る。広い対象へひとまとめに適用しない
- 何にでも当てはまって判断基準にならない rule になっていないか確かめる。
  誰でも同意するが行動を変える基準にならないなら広すぎる
- 補足説明を消しても rule の適用範囲と判断が変わらないなら、元になった場面の再説明なので消す

## 文体

だ体で書く。状態の表記は体言止めでよい（「デフォルト: 無効」）。
手順の指示文はですます調か命令形のどちらかに文書内で統一する。
