norm-refit（執筆規範の全条項監査と再配置）の進行中にだけ効かせる運用 rule。
norm-refit の段階 5 が完了したらこのファイルごと削除する。

## 正典と着手手順

- 確定事項の台帳は `notes/norm-refit.md`、実装計画の正典は `notes/norm-refit-plan.md`。
  実装に着手する前に計画の該当節を読む
- 確定は 1 件 1 エントリで台帳へ積む（結論 / 決めなかった範囲 / 決め手 / 出典 / 反映先）。
  反映先は「rules のどのファイルのどの節 / どの plugin / 反映なし」のいずれかを必ず書く。
  HTML skill 側で決めた規範でも、媒体を問わない内容なら共通規範を反映先に含める
  （書かないと実装時に拾われない。2026-08-25 の観測エントリ）
- 作業明細（条項の一覧、横展開の対象リスト）は scratchpad に置かず `notes/artifacts/` に残す。
  scratchpad はセッションとともに消え、後から照合できなくなる
  確定を変えるときは、元のエントリを書き換えず新しいエントリで上書きの経緯を残す
- idea-hub へ伝えるべきことが出たら `notes/idea-hub-handoff.md` へ追記する。
  既存エントリが古くなっていたら消すか書き直し、常に現状を正しく伝える状態を保つ。
  idea-hub 側は norm-refit の全完了後に着手する

## 節目ごとの最新化

節目（PR を出した・マージした・判断が決着した・確定を変えた・段階が動いた）のたびに、
次の 2 つをその場で最新化する。作業を積んでからまとめて直さない。

1. `notes/norm-refit-plan.md` の現在地と該当節
2. 計画を反映している進捗レポート `ccm-r003`（共通ページディレクトリ。
   html-communication skill の運用で改稿する）

台帳への確定の記録（上記）とこの 2 つで、正典 → 計画 → レポートの 3 層が同じ状態を指す。
どれかだけ直すと、次のセッションが古い層を正として読む

## PR の出し方

- 実装は必ず PR にする。main へ直接入れない。PR に notes を混ぜない。
  notes の更新は main へ直接入れる
- PR を出す前に、台帳の直近の確定（前回の PR 以降に積んだエントリ全件）を列挙し、
  反映先ごとに実装と突合する。反映済み / 未反映 / 担当 PR が別、を 1 件ずつ記録する
- PR を出す前のセルフレビューを飛ばさない: 機械で確かめられるもの（lint・リンク解決・
  発火の検証）→ review agent（観点は規範の欠落と実文の改変）→ 指摘を直す → PR
- レビューは PR ごとにゼロベースで行い、前の PR のレビュー結果を前提にしない
- レビュー指摘に対応するとき、その指摘を一般化して規範（core / 分類別 / rule-authoring）へ
  取り込めるかを毎回検討する。取り込むなら同じ PR で、指摘箇所の修正とは別 commit にする。
  文レベルの指摘は `notes/artifacts/sentence-level-review-cases.md` へ逐語で追記する

## 作業ブランチの注意

- PR ブランチと main で `rules/` の構成が違う。`rules/` は symlink で user global に
  配布されるため、checkout しているブランチで自分のセッションに載る規範が変わる
- ユーザーへの判断の確認は、決めなければならない判断を洗い出して 1 つのフォームにまとめる。
  1 件ずつ小分けに問わない
