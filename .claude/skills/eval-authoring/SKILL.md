# plugin の eval を作る

ケースの書式・実行方法・子セッションの制約は [eval ハーネス](../../../evals/README.md) にある。
この skill は作る順序と、ケースの中身の決め方を定める。

## 2 つの評価を分ける

- **description の評価**: 依頼文を入力にして、発動してほしい skill が発動するか
- **動作の評価**: 発動した後に、SKILL.md に書いた規則どおりに動くか

同じケースに混ぜない。混ぜると、落ちたときにどちらが原因かがスコアから読めない。
動作の評価が無い eval は、SKILL.md の本文がいまの実装と合っているかを judge できない。

## 手順

1. `plugins/{plugin}/evals/README.md` にケースの一覧を書く。ここで何を測るかを決める
2. 一覧を人に見せて合意を取る。ケースのファイルを書くのはその後
3. 一覧のとおりにケースを実装する。前準備は `evals/lib/seed.sh` のような共通の関数にまとめる
4. 1 ケースを `--runs 1` で回し、load と grader が動くことを確かめる
5. 文脈を知らない subagent か別の CodingAgent にレビューさせ、指摘を直す
6. 全件の実行の費用と時間を見積もって人に確認し、承認を得てから回す
7. 落ちたケースは、skill の問題か、ケースの作りの問題かを切り分けてから直す

## 一覧に書くこと

ケースごとに次の 3 つを書く。これが決まらないケースは、実装しても何も測れない。

- 依頼文の要点（何を頼むか）
- 期待（どの skill が発動するか / どの規則を守るか）
- 合格の条件（どの記録のどの形を見るか）

動作の評価では、測る規則を SKILL.md から起こす。1 ケース 1 規則にする。

## ケースの中身の決め方

- **依頼文のリーク**: description の評価では skill 名もトリガー語も書かない。
  書くと発動して当たり前になり、description を変えても結果が動かない。
  動作の評価では逆に skill を名指しする。発動を変数にしないため
- **負例**: トリガー条件に隣接する依頼だけを作る。無関係な依頼は、description を
  書き換えても結果が動かないので情報にならない
- **モデルの判断が入らない処理を測らない**: スクリプトが必ず行うこと（label の付与など）は、
  測っても skill の記述の良し悪しが分からない
- **落ちようがない grader を入れない**。判定基準: その grader が不合格になる経路を 1 つ挙げられるか。
  挙げられないなら、正例のスコアを底上げするだけの検査になる
- **枠**: 依頼の作業量に合わせて `max_turns` と `timeout_seconds` を決める。
  打ち切られた実行は run error になり、スコアと判定を歪める
- **満点が続くスイートを疑う**: 弁別できていない状態。間接的な正例と、隣接する負例を足す

## 外部サービスを呼ぶ skill

子セッションは外部へ通信できず、`HOME` も差し替わる。本物のサービスを呼ぶ skill は stub を用意する。

- stub は plugin の下で eval のディレクトリの外に置く（eval のディレクトリは子セッションから読めない）
- `plugins/{plugin}/evals/env.sh` が stub のディレクトリを PATH の先頭に入れる。
  `evals/run.sh` は env.sh があればそれ経由で `claude plugin eval` を呼ぶ
- stub は呼び出しを作業ディレクトリのファイルに記録し、動作の評価の grader がそれを読む
- 認証のコマンド（`security` など）を stub に差し替えるときは、対象の service 以外を本物へ渡す。
  渡さないと `claude plugin eval` 自身が認証できなくなる
