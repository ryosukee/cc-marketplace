# 統合と完了確認

合意した挙動を、html-communication の生成元・生成器・共通操作へ取り込む。
試作の完成、実装の完成、公開と手元への反映を分けて確認する。

## 実装箇所と説明の対応を決める

合意した挙動ごとに、必要な生成元の指定・共通実装・条件付き参照・表現見本を対応づける。
固定した操作と、用途に応じて選ぶ表現を区別して、変更箇所を決める。
共通化できない対象があれば、試作へ戻って必要な追加指定や方式を決める。
試作の実装をそのまま写すと、ページ固有の操作が共通機能の外に残ってしまう。

skill 本文には入口と条件付き参照を置く。
形式や機能を選んだ後に、使わない形式・機能の詳しい手順を読ませない。
生成元やテンプレートの既定で保証できる内容を、毎回の生成指示へ重複させない。
機能が増えても必要な指示へ到達でき、生成ごとのばらつきを抑えられるようにする。

## 変更の影響に合わせて検証する

合意した挙動を、実装箇所と検証方法へ対応づける。
入力や操作を変える場合は、未回答・初期表示・入力途中・下書き復元・コピー・リセット・回答済み表示などから、変更が影響する状態と操作を選んで確認する。
すべての変更で全機能を試すのではなく、影響する経路と守るべき既存挙動を選ぶ。
正常な操作だけを見ると、保存や回答の扱いの変化を見落とす。

更新した説明とスクリーンショットが、合意した挙動と一致するか照合する。
参考資料を SKILL.md の frontmatter の sources に記録する場合は、参考元から取った点と、利用者との試作で選んだ点を区別する。
機能紹介と参考元の説明が、現在の実装と合うようにする。

検証結果とレビュー結果は、変更した挙動に対応づけて記録する。
利用者が人によるレビューを省略した場合は、その範囲を記録する。
省略の許可とレビュー承認を区別することで、行っていない確認を完了したと報告するのを防ぐ。

## 公開と手元反映を確認する

候補版の検証、公開、手元反映の各工程で、対象の版・commit・client を記録する。
公開の操作手順をこの skill へ複製せず、記録した対象が実際の配布物と一致するか確かめる。
候補版の成功を公開版の検証へ流用すると、利用者の手元で使う機能の確認が抜ける。

最初の候補一覧と追加要求を照合し、採用機能の到達点、保留、今回は取り込まないもの、未完了事項を示す。
実装・公開・手元反映のどこまで済んだかを、確認した証拠に合わせて報告する。
直近の機能だけを見て、取り組み全体を完了と扱わない。
