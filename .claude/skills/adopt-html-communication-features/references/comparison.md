# 比較と選定

採否を決められる粒度で、参考資料の機能と現行 html-communication との差を調べる。
利用者が関心を示した機能だけに絞らず、同じ機能の細かな操作差も確認する。

## 資料を取得して確かさを分ける

投稿だけで分からない場合は、投稿のリンク先、作者の公開記事・リポジトリ・公式説明、動画を調べる。
公開コードを使うときは commit を固定し、動画や画像の根拠は該当箇所が分かる形で残す。
後で参照元が変わっても、比較時に確認した挙動を照合できるようにする。

コードで確認した実装、動画で観察できた挙動、見た目からの推測を区別する。
例えば、動画で補足が開いても、クリック・ホバー・フォーカスのどれで開いたかは映像だけでは確定しない。
推測した操作を参考元の仕様として説明しない。

深掘りしても取得できない場合は、取得できた範囲と、欠けている原本・操作・出力を具体的に示す。
利用者が持っていれば、該当部分のコピペやファイルの提供を依頼する。
利用者も持っていない有料資料を繰り返し要求せず、公開範囲で進められる比較を進める。
不明な点を残すことで、取得できなかった資料から仕様を作り上げるのを防ぐ。

## 現行機能との違いを調べる

現行の skill 本文だけでなく、条件付き参照、生成元の書式、生成器、テンプレート、ギャラリー、テストを調べる。
名前が違っても同じ体験を提供する機能と、名前が同じでも操作が異なる機能を分ける。
公開版と作業中の変更を区別し、比較した基準の commit または版を残す。

各候補について、利用目的・参考元の根拠・現行でできること・追加する差分を記録する。
操作差は対象に応じて、次の観点から調べる。

- どこを操作すると、どこに何が表示されるか。
- 一時表示・固定・解除・閉じる操作がどう違うか。
- 初期値・選択値・現在値が何を意味し、リセットでどこへ戻るか。
- 履歴・下書き・回答へ何を残すか。
- マウス、キーボード、タッチ、狭い画面で何が変わるか。
- 動きを止めた表示や印刷で、何を読めるか。

全候補に無関係な観点を埋める必要はない。判断に効く差分を分けることで、似た候補を重複と誤判定するのを防ぐ。
未確認の挙動は未確認として残し、現行に機能がないと断定する前に関連実装全体を検索する。
追加差分のない既存機能は対応表に示し、追加機能の採否を問う設問にはしない。
既存機能を新しい候補として選ばせると、取り込み済みの体験を再実装する作業が生まれる。

## 大まかな採否を選ぶフォームを作る

候補ごとに、使う場面と操作後の体験が伝わる画像・GIF・操作例・説明を付ける。
静止画だけで伝わらない開閉や連動は、連続した画像や操作できる例で補う。
動画の操作条件が不明なら、その不明点を説明と分けて示す。

採用、保留、今回は取り込まないを選べるようにする。
利用者が最初から欲しいと挙げた機能も候補に含め、既知の意向を説明に反映する。
この段階では、基盤変更・データ形式・ライブラリ選定を設問へ混ぜない。
機能の必要性と実現方式を分けることで、利用者が欲しい体験を先に選べる。

説明が分からない、別候補との違いが分からないという回答は、採否が決まったものと扱わない。
一般的な用語で説明し直し、差が分かる例を提示してから採否を確認する。

## 保留を再開できる形で保存する

保留には、参考元、現行との差分、利用場面、保留理由、関連する回答、再開時の未決事項を残す。
利用者が別 Epic への保存や候補の集約を指定した場合は、その単位に合わせる。
同じ理由・用途でまとめても、候補ごとの根拠と差分を失わないようにする。
今回は取り込まない候補を、保留として起票しない。
保留と除外を区別することで、後続の作業が利用者の優先順位を変えてしまうのを防ぐ。
