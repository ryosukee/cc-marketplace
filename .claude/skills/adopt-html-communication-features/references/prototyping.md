# 試作と UX の確認

採用する機能が決まったら、利用者の用途に合う実現方式と操作を試作で選ぶ。
操作の意味・図や文章の内容・実際の見やすさを一緒に確かめる。

## 方式を選ぶ材料を揃える

既存の共通機能で表せる範囲と、追加が必要な範囲を調べる。
ライブラリや依存の比較が必要なら、公開一次情報と動く例で表現力・制約を確かめる。
利用者が追加調査を求めた対象は、その機能を扱う時点で調べる。
欲しい体験を選んだ後に方式を比べることで、参考元の技術選定を無条件に持ち込むのを防ぐ。

## 比べられる試作を作る

利用者が判断する違いに応じて、複数案を同じ内容・同じ状態で比べられる形にする。
見た目の差なら、毎回小さな修正を 1 案ずつ見せるのではなく、差の分かる案を同時に示す。
違いが定まっていないときは、適切なデザインパターンを調べてから案を作る。
案の数を固定せず、異なる選択肢を比べられるだけの案を用意する。

製品へ入れる操作と、案を切り替えるためだけの比較用操作を、配置と説明で明確に分ける。
どこまでが製品へ入るか分からない試作では、利用者が操作や情報量を評価できない。
試作しただけで共通テンプレートを変更しない。

架空例でも、対象分野の状態・イベント・結果・処理の関係を確認する。
誤ったモデルを図の見た目で補わない。必要なら例の仕様を直してから比較する。
内容の誤りと UI の分かりにくさを分けることで、正しい操作を選べる。

## 操作の意味と見やすさを確かめる

各操作について、変更する値と維持する値を定義し、試作の表示と動作に反映する。
作成時の初期値、利用者が選んだ試行開始値、現在値を扱う場合は、その意味とリセット先を分ける。
試行履歴とフォーム回答を混ぜるかどうかも、用途に合わせて決める。
異なる意味の値を同じ呼び名で扱うと、表示だけ整えても操作後に矛盾が残る。

ブラウザで、操作できる場所の見分けやすさ、情報を読む順序、表示面積、文字の大きさ、スクロール量を確認する。
実際に使う幅と狭い幅、明暗、キーボードやタッチで成立するかを対象に応じて試す。
動作テストだけで見やすさを確認済みにしない。

図は、表す関係に合う図法と配置を選ぶ。
フロー、状態遷移、循環、階層、並行、時系列などを一つの配置へ押し込まない。
意味を保ったまま読める図法を選ぶことで、横幅が変わっても関係を追いやすくする。

## 合意した挙動を確定する

回答の選択値と補足を一緒に読み、採用した案・変える箇所・未決事項を記録する。
「作り直して」「改善が必要」という回答は、修正した試作を再提示する要求として扱う。
試作を作り直す指示を、その案の採用承認に読み替えない。
どの版の何を選んだかを残すことで、後の統合が未承認の案へ戻るのを防ぐ。
