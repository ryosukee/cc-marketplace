# 類似資料から html-communication へ機能を取り込む

参考資料から利用者ができることと操作の違いを調べ、採否を選んでから方式を検討する。
参考元の見た目をそのまま移すのではなく、利用者の用途に合わせて試作し、合意した挙動を共通機能へ取り込む。

## 入力を確認する

参考資料の URL・skill・コード・画像・動画と、利用者が挙げた関心や用途を確認する。
未提示の任意情報をまとめて要求せず、比較や判断に必要になった情報だけ尋ねる。

## いま行う工程の参照を読む

- 初回調査と採否選択には、[比較と選定](./references/comparison.md)を読む。
- 採用候補の方式・見た目・操作を決めるときは、[試作と UX の確認](./references/prototyping.md)を読む。
- 合意済みの挙動を実装するときは、[統合と完了確認](./references/integration.md)を読む。

複数工程を一度に依頼されても、採否を選ぶ前に実装方式や基盤変更を決めない。
何を欲しいかという判断に、実装コストや参考元の構成への追従を混ぜないためである。
利用者がすでに機能と方式を指定した場合は、その合意を使って必要な工程だけ進める。

## 工程ごとの成果を残す

1. 比較では、確認できた資料と未取得範囲、現行との差分を根拠付きで残す。
2. 選定では、採用・保留・今回は取り込まない・説明待ちを区別し、回答と理由を残す。
3. 試作では、比較できる操作例と、採用した挙動・対象外の範囲を残す。
4. 統合では、実装・検証・説明・画像の対応を残す。
5. 完了確認では、当初の候補に対する到達点と、公開・手元反映の証拠を残す。

作業と決定は agent-kanban に記録する。調査結果や確認フォームは html-communication で提示し、
その skill の生成・回答受領・レビュー手順を使う。各ツールのコマンドや書式をこの skill へ複製しない。
記録と操作の正しい所在を分けることで、ツールの更新に伴う手順の食い違いを防ぐ。
