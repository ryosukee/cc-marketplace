# 入り組んだ説明・報告・確認は HTML で行う

調査報告・設計判断の比較・設問の多い確認など、前提や構造が入り組んだ内容は、
ターミナルへのテキスト出力ではなく self-contained な HTML ページを生成して見せる。
構造化して順序立てて読める形に作り込むこと自体が目的なので、体裁は手を抜かない。

## 適用基準

- HTML にする: 前提説明が長い調査報告、複数の表・比較を含む設計判断、設問が概ね 4 問を超える確認、順序立てた説明が必要なもの
- テキストのまま: 短い報告、単発〜少数の質問（チャットのフリーテキストで質問する）

HTML にすると決めたら、ターミナル向けに書いた（書きかけた）長文をそのまま HTML へ移し替えない。
まとめから詳細へ辿れる構造（セクション分け、比較表、出典の分離）に組み直す。

## 配置先と URL の解決

配置先ディレクトリと配信 URL は環境変数から解決する（値のセットアップは環境側の文書の管轄）。

- `CLAUDE_HTML_COMMUNICATION_DIR`: 共通ページディレクトリ。未設定なら既定値 `~/.local/share/claude-html-communication` を使う
- `CLAUDE_HTML_COMMUNICATION_BASE_URL`: 配信のベース URL（例: `https://<ホスト名>.<tailnet 名>.ts.net`）。
  ページの serve URL は `{CLAUDE_HTML_COMMUNICATION_BASE_URL}/{ファイル名}`、一覧のルート URL は `{CLAUDE_HTML_COMMUNICATION_BASE_URL}/`
- `CLAUDE_HTML_COMMUNICATION_BASE_URL` が未設定・空の場合は、ページ提示の前にユーザーに URL を確認し、
  そのセッションではその値を使う。あわせて環境変数としての恒久設定を提案する

## 生成・表示方法

- 共通ページディレクトリ（`CLAUDE_HTML_COMMUNICATION_DIR`。無ければ `mkdir -p` で作る）に
  `{略号}-f{NNN}.html`（form）/ `{略号}-r{NNN}.html`（report）の名前で書く。
  番号空間をプロジェクトごとに閉じることで、並行セッションが同じ番号を取り合わなくなり、
  他プロジェクトのページを上書きすることが命名上ありえなくなる
    - 略号はプロジェクトごとの短い識別子で、index 内の `projects` 台帳が正典。
      台帳に無いプロジェクトなら、そのプロジェクトの最初のページを作るときに決めて登録する
      （3〜5 文字。既存の値と衝突しないことを台帳で確認する）
    - **発番はファイルシステムを見る**: `ls {略号}-f*.html` の最大連番 + 1
      （3 桁ゼロ埋め、該当が無ければ 001。欠番は再利用しない）。
      index のエントリから求めない。一覧の読み落としで既存ページを上書きする事故が起きている
    - 日付・内容はファイル名に持たせず、index のエントリ（`project` / `created` / `title`）と
      ページの `<title>` で管理する。短い名前にするのは serve URL をタスクや通知の 1 行に
      省略なしで収めるため（一覧 UI は末尾から省略され、途切れた URL はリンクとして機能しない）
    - 既存ページの移行: 完了（`answered` / `confirmed`）のページは改名しない。
      未完了のページは、そのプロジェクトを作業対象にしているセッションが新名へ改名し、
      旧名を転送スタブにする。旧命名（`YYYY-MM-DD-<プロジェクト>-<内容>-<種別>.html`）と
      接頭辞なしの旧短名（`f008.html` 等）は、完了分をそのまま据え置く。
      3 世代が同居するが、index は `file` の値をそのまま使うので表示は壊れない
    - ブラウザで自動で開かない（`open` コマンドを実行しない）。`file://` 直開きは
      「一覧に戻る」等の相対リンクが serve 側の一覧と繋がらず不便なため。
      閲覧はユーザーが提示された serve URL（またはファイルパス）から自分で行う
    - ユーザーに見せる閲覧用 HTML（確認フォーム・調査レポートを含む全部）はここに置く。
      scratchpad は単一セッション内で使い切る中間物専用で、閲覧用 HTML は置かない
    - 種別は連番の直前の f = form（要回答）/ r = report（読むだけ）で表す。
      連番シリーズ（第 N 回フォーム等）はファイル名ではなく title で表す
    - サブディレクトリは作らない。プロジェクトの分離は略号の接頭辞で、
      グルーピングは index.html 側で表現する
    - 改稿は同名上書きにする（URL は初版のまま維持）。別議題は新しい連番で作る。
      ファイル名を変える必要が生じたら、旧名を新名への転送スタブ
      （0 秒 meta refresh + 通常リンク）にして配布済み URL を生かす
    - 各ページの左下に「一覧に戻る」ボタン（`./` = index へのリンク）を常時固定のオーバーレイで置く。
      固定位置はビューポート左端ではなく本文カラムの左端に揃える
      （例: `left: max(12px, calc((100vw - <カラム幅>px) / 2 + <カラム padding>px))`）。
      下部固定フッターがあるページではフッター左端に置いてよい
    - **生成に使った skill の版をページと index の両方に記録する。**
      ページ側は `<meta name="generator" content="claude-html-communication X.Y.Z">` と、
      下部バー（report は `#footer-nav`）の `#ver`。index 側はエントリの `skillVersion`。
      版は `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` の `version` を読んで入れる。
      古い雛形で作られたページを参考にしないための目印で、下の「既存のページを読んで
      参考にしない」を版で裏づける
    - **ページを作り直したら、ページ側と index 側を同じターンで揃える。**
      ページだけ直して index を置き去りにすると、一覧の版が古いまま残り、
      次に参考可否を判断するときに誤った版を見る。
      更新するのは次の全部で、変わっていない項目だけを据え置く

        | 場所 | 項目 | いつ更新するか |
        | --- | --- | --- |
        | ページ | `<meta name="generator">` | 作り直したとき必ず |
        | ページ | 下部バー（report は `#footer-nav`）の `#ver` | 作り直したとき必ず |
        | ページ | `<title>` | 議題・設問数の表現が変わったとき |
        | index | `skillVersion` | 作り直したとき必ず |
        | index | `title` | ページの `<title>` と一字一致させる |
        | index | `questions` | 設問の総数が変わったとき（form のみ） |
        | index | `type` | form と report を入れ替えたとき |
        | index | `status` / `statusChanged` | 状態が変わったとき |
        | index | `updated` | 内容を書き直したとき必ず（初回は付けない） |

        `file` と `created` は改稿で変えない（URL と初出日は初版のまま維持する）。
        代わりに `updated` へ改稿日を入れる。一覧は `created → updated` の形で両方を出し、
        並び順も `updated` を優先する。これが無いと、全面的に書き直したページが
        一覧では手つかずのページと区別できない
    - ページは必ず `templates/page.html` を起点に作る。既存のページをコピーして作らない。
      一度コピーで分岐すると、そのページ系統は以後の雛形更新を受け取らなくなる。
      改稿・続編も同じで、雛形の最新版から作り直す
    - 組み立ては `scripts/assemble-page.mjs` で行う。本文（`<main>` から下部バーまで）だけを
      本文ファイルに書き、`node scripts/assemble-page.mjs <本文> <出力> --title <title> --file <名前>`
      で雛形の head と script を付ける。form は `--qs "q1=ラベル|…"`（省略時は設問カードから拾う）、
      report は `--report`、パターン集の CSS は `--css <style.css>`。版は plugin.json から入る
    - 既存のページを参照してよい範囲は、何を取るかで分かれる
        - **この skill と雛形が定めている事柄は、既存ページを見ずに決める。**
          何が定めに当たるかは版ごとに変わるので、ここでは列挙しない。
          いま skill と雛形に書いてあることが、そのまま対象になる。
          既存ページから取ると、そのページが作られた当時の定めを持ち込むことになる
        - 規定されていない、その議題に固有の見せ方の工夫は参照してよい。
          雛形が持てない一点物なので、過去の工夫から学ぶ価値がある。
          取るのは考え方だけで、実装は写さず雛形の上で作り直す
        - 先に [見せ方のパターン集](./references/patterns/README.md) を見る。
          使ってよい条件と使ってはいけない条件が揃っているので、
          過去のページを読むより早く採否を決められる。
          パターン集に無ければ、これまでどおり過去のページを参照してよい
        - パターン集に無い形をその場で作ったら、次に使えるものだけパターン集へ足す。
          追加の手順はパターン集の README にある
        - 参照する前に必ずそのページの版を確認する。ページ下部と
          `<meta name="generator">`、index の一覧に出る。
          版が古いほど現行の規定との食い違いが多く、見せ方の工夫だけを取るつもりでも
          古い規定が混入しやすい。版の記録が無いページは、記録を入れる前のもので最も古い
        - 改稿対象そのものと、リンク先として内容を確認する場合は、この制限の対象外
    - 雛形が持つもの: ライト/ダーク・印刷スタイル・セーフエリア・下書き自動保存（端末ローカル）・
      一覧に戻る・回答コピー・form / report 両方の追従領域・3 pane・本文の範囲と現在地の追従・
      脚注と補足の双方向リンク・設問のグループ容器（`.qgrp`）
    - 構造は 3 pane。左に設問 `#q-pane`、中央に本文 `#bd`、右に脚注と補足 `#fn-pane`。
      1340px 以上で 3 列になり、それ未満は DOM 順のまま 本文 → 設問 → 脚注 の 1 列で流れる。
      DOM 順をこの並びにするのは、狭幅で読み終えた直後に答えられるようにするため
    - 幅の段は 5 つ。ページ側でブレークポイントを足さない

        | 発火する幅 | 構成 | 設問 / 本文 / 脚注の列幅 |
        | --- | --- | --- |
        | 〜1023px | 1 列 | 本文 640px |
        | 1024px〜 | 2 pane | — / 640 / 300 |
        | 1340px〜 | 3 pane | 300 / 640 / 300 |
        | 1700px〜 | 3 pane | 320 / 960 / 320 |
        | 2100px〜 | 3 pane | 360 / 1240 / 360 |

    - **広い段で伸ばすのは表・図・コードだけで、地の文は伸ばさない。**
      本文の列が広がっても、段落・箇条書き・見出し・引用には上限を掛ける
      （1700px 段で 720px = 全角 45 字、2100px 段で 800px = 全角 50 字）。
      列と一緒に地の文を伸ばすと 1 行が長くなりすぎ、行の頭へ視線を戻せなくなる。
      雛形がこの上限を持っているので、ページ側で外さない
    - 本文には `section.rng[data-q]` で設問ごとの範囲を作る。
      範囲のラベル（`.rlabel`）は「設問 2 / 5」とだけ書き、「設問 2 の判断材料」のように
      役割を説明しない。読み手が知りたいのはいまどの設問を読んでいるかで、
      その範囲が判断材料であることは 3 pane の並びと設問カードの追従が示している。
      前提部分は範囲を持たせない（その位置では設問をどれも開かない）。
      追従は各範囲と表示領域の重なりの高さで決める。節の先頭が閾値を超えたかという点の判定はしない。
      読んでいる範囲の設問カードが開き、手で開閉したものは自動追従から外れる
    - 地の文と UI の色の役割は既定の 3 つを全ページで通す。ページごとに割り当てを変えない
        - 青 `--link` = 操作できるもの + 現在地
        - 地の濃淡 = 構造（見出しの罫・表の罫・区切り）
        - 琥珀 `--mark` = 本文中の要点
    - **図の中は色を自由に使ってよい。** 条件は 3 つ
        - 何の色かを凡例で示す
        - 色だけに意味を載せず、字面か形を併記する（WCAG 1.4.1）
        - その色を図の外（地の文・表・設問・UI）へ持ち出さない
    - 図の外でパターンが固有の色を持ってよいのは、**その色に定着した意味がある場合に限る**。
      差分の赤と緑、判定の可否のように、読み手が別の意味に取りようがないもの。
      足すときは色だけに意味を載せず、字面か形を併記する。
      色はそのパターンの中で閉じ、本文の地の文へ持ち出さない
    - 本文テキスト `--fg` と構造の線 `--rule-strong` は必ず別トークンにする。
      兼用すると両者のコントラストが 1.00 になり、ダークで区別が消える（実測で確認済み）
    - 現在地は範囲の左の縦罫を 2px の `--link` に変える。面は敷かず、専用の色相も作らない。
      文書 UI の先例 8 件のうち新色相を立てたものは 0 件で、5 件が主アクセントの流用だった
    - 見出しの標識は左の縦罫 4px、色は無彩の `--rule-strong`。
      青にすると現在地の青い縦罫と 2 本並んで役割が読めなくなる
    - 脚注と補足は番号の系列を分ける。脚注は数字 (1, 2)、補足は英字 (a, b)
    - フォントサイズは雛形の 4 段階（`1.4em` / `1.15em` / `1em` / `0.875em`）だけを使い、新しい段を足さない。
      図の CSS（下記の `data-scope="figures"`）だけはこの制限の対象外
    - 下部固定バー（追従エリア）は要素の種類で 3 ゾーンに分ける。詰め込まず、種類ごとに置き場を決める
        - 情報ゾーン（`.bar-info`、最上段の細い帯）: 操作しない読むだけのラベルだけを置く。
          プロジェクト名バッジ `#proj`・進捗 `#cnt` を左、状態メッセージ `#res` と版 `#ver` を右。
          ボタンを混ぜない
        - 入力ゾーン（`#free` 単独）: 自由記入欄を全幅で最大化する（`width: 100%`、高さも確保）
        - 操作ゾーン（`.bar-actions`、最下段）: ナビ（`#back` 一覧に戻る）を左に隔離し、
          操作ボタン群（`.action-cluster`）を右へ寄せる。主操作（回答をコピー）は右端でアクセント塗り、
          副操作（リセット）はゴースト（`.subbtn`）にして主副を見た目で分ける。
          3 つのボタンは常に 1 行に収める。副操作のラベルを「入力をリセット」まで伸ばすと
          3 pane の狭い bar で折り返す（1340px で内幅 306px に対し合計 339px。実測）
    - 3 pane のときバーは脚注 pane の真下へ寄せ、そこから画面右端まで伸ばす
      （1340px 段で `left: calc(50% + 344px); right: 0`。1700px 段は `+ 504px`、
      2100px 段は `+ 644px`）。設問 pane の下ではなく脚注 pane の下に置くのは、
      設問カードが使える縦幅を最大に取るため。丈を削るのは `#fn-pane` だけにする。
      列幅 300px 丁度で止めるとボタン 3 つが 1 行に収まらないので、右端は画面端まで伸ばす
    - プロジェクト名バッジ（`#proj`）で、どのプロジェクトの確認・報告かをスクロール位置に関わらず常に示す。
      プロジェクト名は index のエントリの `project` と同じ値にする
    - report 形式（設問なしの読む専用ページ）は操作ボタンが無いので、追従する固定領域（`#footer-nav`）に
      「一覧に戻る」とプロジェクトバッジを横並びで置くだけにする。スクロールしても消えないようにする。
      雛形にコメントアウトで入れてあるので、`#bar` と入れ替えて使う
    - 表は雛形の形をそのまま使う。`min-width` で狭幅時の潰れを防ぎ、
      横スクロール領域は `role="region"` と `tabindex="0"` でキーボードから操作できるようにし、
      `caption`（`aria-labelledby` の参照先）と `scope="col"` を必ず書く
    - 図も表と同じ作法でキャプションを付ける。雛形の `.fig` で包み、`.cap` を図の下に置く。
      字の大きさと色は表の `caption` と揃える。番号を振り、何の図かを書く
    - **図の CSS は本文の CSS と分ける。** 雛形の `<style>` の後ろに
      `<style data-scope="figures">` をもう 1 つ置き、図のための CSS だけをそこへ入れる。
      色役割とフォント段の制限は、この `style` の中には適用しない。
      機械検査もこの `style` を対象から外す
    - 図を Tailwind で組んでよい。外部 CDN は使えないので、生成時に CLI を回して
      使ったクラスだけの CSS を出し、`data-scope="figures"` の `style` へ貼り込む。
      手順は [見せ方のパターン集](./references/patterns/README.md) にある。
      リセット（preflight）は読み込まない。読み込むと雛形の表・見出し・段落の作りが消える
- 同ディレクトリの `index.html` で一覧と状態を管理する（Claude が生成・更新。
  エントリは index 内のインライン JS 配列 `entries`）
    - 1 つの議題に複数ページを作るときは、代表ページ 1 件だけを index に登録する。
      代表は回答・確認を受けるページ（設問があれば form、無ければ主レポート）。
      判断材料の明細などサブページは index に登録せず、代表ページの本文からリンクし、
      サブページ側にも代表ページへのリンクを本文冒頭に置く。
      index に同レイヤーで並べると、読む側には無関係な複数件に見えて読む順が決まらない
    - サブページは index にエントリを持たないため状態管理をしない
    - form 型のエントリには設問総数 `questions`（数値）を持たせ、一覧に「設問 N 問」を表示する。
      これは設問セクション数ではなく答える設問の総数（1 セクションに複数設問がありうるため）。report 型には持たせない
    - エントリの `title` はページの `<title>` と一字一致させる。改稿でページ側の title を
      変えたら index も同時に更新する（一覧の表示名と遷移先の名前がずれると探せない）
    - form を `awaiting` で登録したら、TaskCreate で回答待ちタスクを作る。subject は
      「{serve URL} ← {ページ title}に回答」の形で URL を先頭に置く（一覧 UI は末尾から
      省略されるため。短名ファイルの URL なら省略なしで収まる）。report の `unconfirmed` も
      同様に確認待ちタスクを作る。回答・確認を受領したターンで completed にする。
      task ツールが提供されない環境（subagent 等）では作らない
    - ページ作成時のエントリは必ず未完了で登録する。状態は form → `awaiting`（回答待ち）、
      report → `unconfirmed`（確認待ち）。提示しただけのページを完了扱いにしない
    - 進捗レポートのように節目ごとに改稿し続ける report は `living`（更新中）で登録する。
      確認を求めず、確認待ちタスクも作らない。改稿のたびに `updated` を進める。
      完了状態を持たない。役目を終えたら `confirmed` にする
    - 状態遷移は必ず「未完了 → 完了」を踏む: form は「## HTML フォーム回答」を受領したターンで
      `answered`（回答済み）へ、report はユーザーから内容への確認応答（会話での言及・了解）を受けたターンで
      `confirmed`（確認済み）へ更新する
    - 「## HTML フォーム回答」を受け取ったら、そのターンの最初の操作として index.html の当該エントリを
      `answered` に更新する。回答内容の反映作業より前に status を先に落とす
    - **完了したページを削除しない。** ファイルも index のエントリも残す。
      台帳・設計ドキュメント・引き継ぎ資料が出典に引いたページを消すと、その確定の根拠へ到達できなくなる。
      実際に 3 ページが失われている（efso-idp の eidp-f003 / eidp-f004、cc-marketplace の ccm-f045）
    - 一覧が長くなる問題は表示側で解く。index は完了分をプロジェクトごとに直近 10 件まで出し、
      溢れた分は `archive.html` へ辿らせる。件数の上限は `templates/index.html` の `RECENT_DONE`
    - **index を書き換えたら `scripts/build-archive.mjs` を回す。**
      archive.html は index.html から生成するので、エントリの追加・状態の更新のたびに作り直さないと
      古い一覧が残る。生成先は共通ページディレクトリ
    - ユーザーが明示的に削除を指示したときだけ削除する。そのページを出典に引いている記録が無いことを
      先に確かめ、引いているものがあれば実文を写してから消す
    - セッションが操作してよいのは、自分のプロジェクトのページと index.html（+ PWA 固定アセット）だけ。
      他プロジェクトのページの改稿・削除はしない
    - index の最下部に運用元を明記する: この skill（cc-marketplace の claude-user-communication plugin、
      `plugins/claude-user-communication/skills/html-communication/`）に基づく Claude Code の
      HTML コミュニケーション用ディレクトリである旨と、skill の GitHub URL を footer に書く。
      index を再生成するときも維持する
    - PWA 固定アセットを配置する: `manifest.json`（name = claude-html-communication、start_url = index.html、
      display = standalone）と `icon-192.png` / `icon-512.png`。index の `<head>` に
      `<link rel="manifest">` と theme-color を入れる。「閲覧用 HTML のみ」の例外はこれらと index.html だけ
    - **版を上げたら index の見出しも書き換える。** `<title>` と `<h1>` の `.ver` に
      `v{バージョン}` を出し、一覧を開いた人がいまどの版で生成されているかを見られるようにする。
      値は plugin.json の `version`。エントリの `skillVersion` の最大値ではなく、plugin の版そのものを出す
    - index・PWA アセットが消えていたら、この skill の `templates/`
      （index.html 雛形・manifest.json・icon-192.png・icon-512.png）から再生成する
    - `gallery.html` は [見せ方のパターン集](./references/patterns/README.md) を実物で並べたページ。
      `scripts/build-gallery.mjs` が生成する。パターンを追加・削除・修正したら作り直し、
      共通ページディレクトリへ置く。index からはリンクで辿らせ、一覧のエントリは持たせない
      （回答・確認の対象ではないため、状態遷移を持たない）
    - 雛形 `templates/index.html` の表示仕様（レンダリング JS・CSS）を変えたら、
      配信中の index.html にも同じ変更を適用する。配信中の index は以後エントリだけを
      更新し続けるため、雛形の更新は自動では届かない
- モバイル閲覧: claude-html-communication は tailnet 内限定の HTTPS 配信にしてある。
  提示時のターミナル出力には、ファイルパス / ページの serve URL / 一覧のルート URL の 3 つを必ず併記する
  （出力の全体像は下記「提示時のターミナル出力」）
- CSS/JS はすべてインラインで self-contained にする。外部 CDN・フォント・画像に依存しない
- `prefers-color-scheme` でライト/ダーク両対応にする
- 構成は「前提（この文書は何の話か）→ まとめ（フォームでは推奨案のまとめ、報告では報告のまとめ）→ 詳細 →（あれば）設問」の順。
  セクション番号か目次を付ける
- まとめの前に 2〜3 文の前提を置く。何のトピックか、どういう経緯でこの文書が要るのかを、
  他の作業から戻った読者がコンテキストを復帰できる粒度で書く。いきなりまとめから始めない
- **セクション番号を `h2` の中に書かない。** 見出しはタイトルだけにし、番号は見出しの前の行に置く。
  番号と見出しを同じ行に続けると、どこまでが番号でどこからがタイトルかが読み手に分からない
    - 系統は設問の有無で 2 つに分け、両者を混ぜて通し番号にしない。
      どちらになるかは、その `h2` の中に設問ブロックがあるかだけで決まる。
      判断材料の説明が同じ節にあっても変わらない
    - 説明の節に出してよいのは、複数の設問に共通する前提だけ。1 つの設問にしか効かない
      判断材料は、長くてもその設問の節に置く。読み手は設問の節だけを読んで答えられる
      状態を求めており、前の説明へ戻らないと分からない設問は差し戻される
    - 設問を含むセクション: 範囲のラベル（`.rlabel`）に「設問 2 / 5」を出す。
      分母は設問セクション数。見出しは別に番号を持たない
    - **設問を含むセクションの見出しは問いにする。** 「〜をどこに書くか」「〜を採用するか」の
      疑問形で、何を決めるかを書く。推奨する答えを見出しに載せない。読み手が見出しで知りたいのは
      何を問われているかで、推奨は選択肢のバッジと冒頭のまとめブロックが持つ。
      説明の節の見出しは従来どおり主張型（結論を見出しに載せる）
    - 設問が無い読む専用のセクション（前提・報告・比較・分析）: 見出しの前に `.secnum` の行を置き、
      「説明 2 / 4」を出す。分母は説明セクション数
    - ラベルは `設問` と `説明` に固定する。末尾の「参考資料（判断には不要）」
      「生成に関する補足（判断には不要）」「付録 回答の preview」は読み飛ばし可の別枠で、
      この 2 系統に含めず番号も付けない

## 情報設計（構成・テーブル・羅列）

情報デザイン norm ライブラリ（product-boilerplate repo の `docs/norms/`、出典付き）に従う。

### 本文を書く前に 2 つ整理する（必須・最初にやる）

構成と出力に入る前に、次の 2 つを先に決める。

1. 何を本文に書き、何を補足に回すか。読者がこの判断・理解に要る情報だけを本文に残し、
   細部は末尾の「参考資料（判断には不要）」へ回す。情報過多は避ける
2. どの順で説明するか。読者が「何の話だっけ」とならない並びにする。
   前提は簡潔に、詳細は補足へ

提示前に確認: 本文の各セクションが読者の判断・理解に要るか。前提や細部が膨らんでいたら補足へ移し、
説明順が追えるかを確かめる。

### 作成時に特に効く要点（詳細・出典はライブラリ側）

- 冒頭に地図を置く: 前提（何の話か・経緯）→ この文書の目的。
  前提の後にまとめを出す（前提はまとめの手前に置く 2〜3 文、背景の長い経緯とは別物）
- 「読み方」の節を書かない。どこから読むか・どこを飛ばしてよいかの案内は置かない。
  構成と見出しで分かるようにするのが先で、案内文が要る時点で構成が悪い
- **冒頭に設問の件数・所在・設問どうしの関係を書かない。** 「決めることは 6 件で、各設問は
  判断材料の直後にあります」「設問 2〜4 は設問 1 で案 1 系を選んだ場合の設計判断です」の類は、
  読み方の案内そのもの。上から順に読めば分かる並びにするのが先で、予告が要るなら並びが悪い。
  設問へのリンクの目次も置かない。件数は設問 pane の見出しと下部バーの進捗が示す
- **ラベル + コロンで段落を作らない。** `この文書: …` `読み方: …` `結論: …` のような、
  太字ラベルにコロンを付けて説明を続ける形は使わない
  （user global rule「日本語テキストの執筆要点」が AI 口調の定型として禁じており、
  適用範囲に HTML 報告が含まれる）。HTML では構造で表す
    - ラベルが要るなら、ラベルを独立した行にして小さく弱い色で置く（雛形の `.eyebrow`）。
      コロンは付けない
    - 節として立つ内容なら見出し（`h2` / `h3`）にする
    - ラベルが無くても分かる内容なら、ラベルごと消して地の文にする
- 冗長にしない。不要な細部・重複・言い換えを削る。読者が判断に使わない情報は参考資料へ逃すか落とす。
  各セクションは判断に効く分だけにし、網羅のための説明を足さない
- 1 議題 1 セクション。判断セクションは「決めること → 背景 → 判断材料 → 設問」の同型に揃える。
  設問の節は自己完結させる。対象が何か（どのファイル・どの条項・どの提案か）と、
  選択肢に出る語の実体を、その節の中に書く。前の節で説明したからと省かない
- **並列列挙を表にしない。** 表にしてよいのは 2 つだけ。列が選択肢で行が観点の比較表と、
  キーから別の値を引く対応表。行が独立した項目で、列がその項目を説明する記述でしかないなら
  ネストした箇条書きにする。項目を第 1 階層、根拠や出典を第 2 階層へ置く
    - 上の 2 形に当てはまるかを先に見る。決まらなければ列を縦に読んで判定する。
      同じ列に同じ種類の値が並び、列どうしを見比べられるなら 2 つ目の軸が実在する。
      列見出しが項目のフィールド名でしかなく、縦に読むと値の種類がばらばらなら、軸は行しか無い
    - 表にすると、セルに収まらない内容が押し込まれて短い判定値の規定に反する。
      実測（2026-08-22、205 表）では、並列列挙の 65% がセルに文を含み、比較表は 12% だった
- 表の前提・条件・読みどころは補足（`.su`）へ出し、表のセルから参照マーカーで飛ばす
- **`caption` は表の下に置く**（`caption-side: bottom`）。表の本体を先に見せる
- **「決め手」という語を使わない。** 表のどの行が効くかはハイライトが示す。
  「決め手は◯◯の行」「どこが決め手か」の類の文を書かない
- テーブルのセルは流し読みできる短い判定値（体言止め・記号・数値）にし、文を書かない。
  根拠・詳細は脚注か補足へ出す。1 セル 1 情報。
  **表の直下に補足リストを置かない。** 脚注と補足は pane に出るので、
  本文を汚さずに表と同時に読める
- 比較表は「列 = 選択肢、行 = 観点」で列は 5 以下。判断を分ける行はハイライトする
- 出典・長い補足を本文の括弧書きで埋め込まない。出典はチップ等に分離する
- 用語は初出の位置で説明する。冒頭に用語集を置かない（下記）
- 脚注は本文と双方向のページ内リンクにする（下記）
- 回答・判断に不要な資料は末尾の「参考資料（判断には不要）」へ隔離し、「読み飛ばしてよい」と明記する。
  入れるのは明細・出典の一覧・生データ・再現手順。ページの作られ方はここに入れない
- **ページの作られ方は「生成に関する補足」へ分ける。** 入れてよいのは 5 つだけ。
  推定と実測の区別 / 確認できなかった箇所 / 調査の範囲と除外条件 / 数値の基準時点 / 改稿である事実。
  判定は「読み手がこのページの内容の確からしさを判定するのに要るか」
    - 入れない: 改稿を何回したか、subagent を何本使ったか、どの指摘を受けて何を直したか、
      レビューを何ラウンド回したか。いずれも読み手が中身を判定するのに使わない
    - 1 項目 1〜2 文に収める
    - 書くことが無ければ節ごと置かない。空の節を作ってから埋める内容を探さない
- フォームには入力の下書き自動保存を実装する（localStorage、入力の都度保存・再訪時に復元。端末ローカル）
    - 「リセット」ボタンを併設する（localStorage の下書きを消して空に戻す）
    - 端末をまたいだ下書きの持ち運びは行わない。下書きは書いた端末の中だけで復元する
- 推奨バッジには根拠の併記と覆し可能性（非推奨側も選べることの明示）を必須にする
    - 選択肢の説明を長所と短所に分ける形（雛形の `.proscons`）を使うときは 3 つを守る。
      推奨案の短所に「他案が勝つ条件」を書く（これが覆し可能性の明示を兼ねる）、
      1 行 1 文 60 字以内にする（`label` はクリック対象で読み込む場所ではない）、
      選択肢の説明（`.d` = 案の中身）と積層して使う（長所短所 = 案の帰結）。
      選択肢が 2 つで片方が明確に優位なときは使わない。短所が空振りする
- **推奨が依存する前提には、実測か一次情報の出典を必ず付ける。**
  出典は実装・公式ドキュメント・変更履歴・過去の回答フォームのいずれか。
  **自分が同じセッションで書いた文書を出典にしない。** 要約は限定・条件・例外を落とすので、
  それを根拠にすると落ちたことが分からないまま前提になる。
  実測値と推定値は区別して書く
- **Claude に読ませる文書・仕組みの置き場を問う設問では、種別を全件並べてから落とす。**
  rule（user global とプロジェクト固有）/ 参照知識 skill / hook / agent / 作業手順 skill /
  CLAUDE.md の 6 種を当て、採らない種別には落とした理由を 1 文で書く。
  並べずに 2〜3 案だけ出すと、読者は「他に手が無い」と受け取る。
  置き場を問う設問でないなら、この項目は当たらない
- **推奨の説明には「他案を排除する理由」を書く。** 推奨案の利点だけを書かない。
  「A は速い」は根拠ではなく、「B は速いが復旧手段が無い」が根拠。
  覆せる条件も、読者がその場で真偽を判定できる形にする
  （「今後 〜 しか出ないなら」のような全称命題は判定できない）
- **複数の判断を 1 つの設問で一括承認させない。** 「この N 件でよいですか」の形は禁止。
  判断 1 件につき設問を 1 つ置き、それぞれに選択肢を付ける。設問が増えること自体は
  まとめる理由にならない
    - 対象は、判定・置き場・処置のような個別に覆せる判断の集合。
      集合全体への処理方針（順序・時期・まとめて処理するか）を問う設問は 1 件の判断なので対象外
    - why: 一括承認は、個別に覆したい読み手に「どれをどう直すか」を自由記述で書かせる形になり、
      選択肢形式の利点が消える
- **確認も選択肢を持つ設問にする。** チェックリストは使わない。
  「承認するだけ」に見える項目も、覆す余地があるなら選択肢が要る。
  覆す余地が無いなら、それは設問ではないので設問にしない
    - why: チェックリストは 1 項目あたりの情報量が選択肢より落ちる形をしていて、
      「本文で説明済みだから参照だけでよい」と書く経路ができる。
      「判断が要るものは混ぜない」という条項だけでは、判断の要る項目が混ざるのを防げない
- **まだ読んでいない後続の設問を前提にした条件を、判断材料に書かない（非推奨）。**
  読者はその設問の選択肢も用語もまだ知らないので、条件が判定できない。
  前提が要るならその設問より前に置くか、条件ごと 1 つの設問へ統合するのが先
    - それでも書くときは「設問 N で推奨案を選んだ場合」までにとどめる。
      個別の選択肢の名前や、その説明を読まないと分からない用語を出さない
    - 1 文に条件を 2 つ以上詰めない。条件が 2 つあるなら文を分ける
- **設問カードには回答済みかどうかのマーカーを付ける**（雛形の `.qstat`）。
  折り畳んだ状態でも、どこまで答えたかが一覧で分かるようにする。
  色は使わず、形（輪郭の丸 / 塗りの丸）と語（未回答 / 回答済み）の両方で区別する。
  雛形の色役割は 3 つに固定してあり、状態を表す枠が無い。
  判定は下部バーの進捗と揃えて、選択肢を選んだら回答済みとする（補足欄だけの記入は未回答）

### 用語の説明は補足 pane へ出す

用語の説明は本文に置かず、補足（`.su`）へ出して本文から参照マーカーで飛ばす。
定義を要るのは知らない読者だけで、知っている読者には本文を分断する障害物になる。
3 pane では補足 pane が本文と同時に見えるので、飛ばずに読める。

- 冒頭に用語集の節を作らない。語が初めて判断に関わる位置で参照マーカーを置く
- 1 語 1 補足。1 補足に複数の語を詰めない
- 説明は 1〜3 文。何であるかと、その判断にどう効くかまでを書く
- 短い定義を並べるときは `※ 語 = 定義` の形を 1 行ずつ使い、語だけを太字にする。
  補足 pane の中で使う書き方で、本文には置かない
- 1 つの節で 3 語を超えるなら、説明の順序か構成が間違っている。語を減らすか節を分ける

**識別子・番号つきの語は、必ず補足に実体を書く。**
規範 ID（`DG14`）、フェーズ番号（`T4`）、フォーム番号（`f017`）、PR 番号、
独自の分類コードが対象。番号だけでは何を指すか分からず、
読者は台帳を開かないと判定できない。ページ内で完結させる。

**自分で作った語を使わない。**
既存の一般語・公式名を先に探し、それを使う。

**汎用語を特定の物の名前として使わない。**
「台帳」「一覧」「設定」「エントリ」のような汎用語は、文脈を共有していない読み手には
一意に定まらない。特定のファイル・エントリを指すときは固有名（plugin 名・ファイル名・
エントリの id）で呼ぶ。補足で定義しても足りない。同じ語がページ内で別の物も指しうるため。

```html
<p>現行の <span class="suref" id="suref-a"><a href="#su-a">a</a></span>DG14 は…</p>

<p class="su" id="su-a"><a class="sunum" href="#suref-a">a.</a> DG14 = 執筆規範の条項番号。
現行の実文は「修飾語は係り先の直前に置き、スコープが曖昧なら鉤括弧で括る」。
鉤括弧の部分は 2026-08-15 に廃止が決まっている。
  <a class="suback" href="#suref-a" aria-label="本文へ戻る">&#8617;</a></p>
```

判定基準: その説明を消したとき、直後の表や設問が読めなくなるか。
なるなら補足に置く。ならないならその語は本文に要らない。

### 脚注は双方向のページ内リンクにする

出典・実測値・根拠を脚注へ逃がしたら、本文の参照記号と脚注を相互にリンクする。
番号だけを振って飛べない状態にしない。

- 本文側: `<sup>` の中にリンクを置き、脚注へ飛ばす。id は `fnref-{番号}-{同一脚注内の連番}`
- 脚注側: id は `fn-{番号}`。先頭の番号を参照元へのリンクにし、末尾に戻りリンク（`↩`）を置く
- 同じ脚注を複数箇所から参照するときは、参照ごとに別の id を振り、
  戻りリンクを参照の数だけ並べる（`↩1` `↩2`）。戻り先が 1 つに潰れると往復できない
- `scroll-margin-top` を入れ、飛んだ先がビューポート端に貼りつかないようにする
- `:target` で飛んだ先を一時的に強調する。番号だけでは着地点が分からない

```html
<td>載る<sup class="fnref" id="fnref-2-1"><a href="#fn-2">2</a></sup></td>

<p class="fn" id="fn-2"><a class="fnnum" href="#fnref-2-1">2.</a> 実測（2026-07-27）: …
  <a class="fnback" href="#fnref-2-1" aria-label="本文へ戻る">&#8617;</a></p>
```

参照記号と脚注の対応（リンク切れ・id の重複・脚注の定義漏れ / 参照漏れ）は、
下記「提示前の機械検査」のスクリプトが検査する。

## 確認（設問）を含めるときの作り

- **設問が多いページは設問をグループ化できる（任意）。** カードに `data-grp` を付け、
  設問 pane に雛形のグループ容器（`.qgrp`）を置く
    - グループ名は内容の名詞句だけ。件数・接頭語・動詞句を付けない。
      名前はそのページの実際の内容から付ける
    - グループ見出しには回答進捗（n/N）が JS で付く
    - カードの summary はグループ内番号「{グループ名の先頭語} n / N {設問ラベル}」にする
    - 本文の範囲ラベルは「{グループ名} n / N（設問 通し / 総数）」。
      通し番号の分母は総設問数のまま変えない
    - グループ外の設問は従来の「設問 N / M」のまま混在できる
- 設問は関連するセクションの直下に置く。ページ末尾にまとめて並べない
    - 設問が多いとき、末尾集約は判断材料と設問の往復スクロールが発生して回答しづらい
    - 回答コピー機能は全セクションの設問を集約して 1 テキストにする（配置と集約は別）
- 最終確認などの自由記入欄は、ページ末尾ではなくスクロール追従の下部固定領域に置く（コピー用フッター内など）。
  上から順に読みながら、気づいた点を都度記入できるようにする
- 各設問に選択肢 (radio / checkbox) を用意し、推奨案には推奨バッジを付ける
- 技術選定などの比較設問には、選択肢の説明文だけで判断させない。設問の直前に多観点の比較表
  (機能・性能・実績・エコシステム・リスク・移行性・保守状況など、その選定で効く観点) を置き、
  各観点は調査の裏取り付きで書く。選択肢の description は比較表の結論の要約に徹する
- 選択肢に収まらない回答用に、設問ごとに「その他」の自由記述欄を付ける
- 設問ごとに補足記入欄（任意）を付ける
- ページ末尾に回答の live preview と「回答をコピー」ボタンを置く。
  ボタンはそれまでの選択・自由記述を 1 つのテキストに整形してクリップボードへコピーする
- 整形フォーマットは Claude Code にそのまま貼れる形にする:

  ```text
  ## HTML フォーム回答（{テーマ}）
  - Q1（{設問}）: {回答}
  - Q2（{設問}）: {回答}
  - 補足: {自由記述}
  ```

- クリップボード API が使えない環境向けに、preview の textarea を全選択コピーできるフォールバックを付ける
- 未回答の設問がある状態でもコピーは許可し、未回答は `未回答` と明記する

## 提示前の機械検査

ページを生成・改稿したら、op-review より前に検査スクリプトを実行する。

```sh
"${CLAUDE_PLUGIN_ROOT}/skills/html-communication/scripts/validate-page.sh" <ページのパス>
```

- 3 層（html-validate / linkinator --check-fragments / 雛形固有の自作検査 + onclick grep）を
  一括実行し、指摘を JSON で stdout に集約する。`total` が 0 になるまで直して再実行する
- 検査対象はそのセッションで生成・改稿したページだけ。過去ページには旧雛形由来の指摘が
  残っているため、一括適用しない
- `ref-order`（脚注番号・補足英字が初出順でない）で落ちたら、`node scripts/renumber-refs.mjs <ページ>`
  で振り直してから再検査する。pane 内の並びも揃える。冒頭のまとめブロックは初出順の対象外
- 「一覧に戻る」リンク（`./`）の解決に同ディレクトリの index.html が要る。
  共通ページディレクトリ内のファイルパスで実行する
- npx のキャッシュがあればオフラインで動く。1 ページ約 7 秒（初回のみダウンロードで + 数秒）
- Exit: 0 = 指摘なし、1 = 指摘あり、2 = 前提条件エラー（node / npx が無い等）
- 検査を通したら、ターミナルに書く内容を URL と問いだけに絞る。
  申し送りを書きたくなったらページへ足して、検査からやり直す

## 提示前のレビュー

設問を含むフォームは、提示前に `page-reviewer` agent を **1 本だけ** 起動する。
設問の無い報告は起動しない。

呼び出すときに渡すもの。

- 対象ページの絶対パス
- 一次情報の所在（台帳・設計ドキュメント・実装・過去の回答フォーム）
- そのページが何を決めるためのものか

agent が見るのは、一次情報との突合（捏造と誤引用）と、推奨・選択肢集合の妥当性だけ。
文言・マークアップ・可読性は見ない。それらは上の機械検査と、下の作成規範が持つ。
手順と観点は [page-reviewer](../../agents/page-reviewer.md) にある。

### 反復の終了条件

**指摘 0 件まで繰り返さない。**

- 推奨または選択肢集合を変える指摘が出たら、直して **もう 1 度だけ** 回す
- 文言・マークアップの指摘は、そのラウンドで直して終わる。再ラウンドしない
- レビュー実行中は対象ファイルを編集しない。agent は起動時点の版を読む

### この形にした理由

実測（2026-08-18、idea-hub の ih-f007）で、4 facet 2 ラウンド 8 本が指摘 133 件・
subagent トークン 828k・1 ラウンド約 14 分を使った。内訳は設計妥当性 25 件 / 165k、
内容整合 23 件 / 264k、情報デザイン 27 件 / 280k、clarity 58 件 / 118k。

- 推奨や選択肢集合を変えた指摘は、設計妥当性と内容整合からしか出ていない
- 情報デザインと clarity は全体の 48% のトークンを使い、判断を変えた指摘が 0 件
- 情報デザインの指摘の多くは雛形自身の欠陥で、ページごとに再発見されていた（雛形を直した）
- clarity の指摘の大半は機械判定できる形をしていた（機械検査へ移した）

統合後を同じ規模のページ（ccm-f026、設問 2 件・図 2 点）で 1 本回して **84.8k トークン**。
統合前の 2 facet 合計 429k に対して約 80% 減で、一次情報の重複読みが消えた分が出ている。
指摘の質は落ちていない。この 1 本が、旧 4 facet の 2 ラウンドが見逃していた
「推奨の根拠にした前例が当時の実文に存在しない」を `git show` で確かめて出した。

clarity を外したことで残る穴は、未定義の造語のように文脈を知らない読者にしか
気づけないもの。機械検査が拾えるのは識別子・文長・参照マーカーまでで、造語は判定できない。
取りこぼしが実際に判断を歪めたら、
[提示前レビューの norm](./references/review-norms.md) の表を見直す。

## 提示時のターミナル出力

ターミナルに書いてよいのは次の 2 つだけ。

- ページの serve URL / 一覧のルート URL / ファイルパス。
  複数ページを作った議題では代表ページの分だけを出す（サブページは代表からリンクで辿る）
- ユーザーへの問い（op-review を回すか、次にどちらへ進むか等）

**ターミナルに申し送りの枠を作らない。** ページの作られ方（改稿である事実、index の状態を変えた理由、
op-review が未実施である事実、確度の低い箇所）は「生成に関する補足」へ置く。
判断が要るもの（op-review を回すか、index の変更が妥当か等）は補足へ流さず、設問にする。

判定基準: いま書こうとしている文は URL か問いか。どちらでもないならページへ移す。
結論・要約・セクション構成の説明・表の再現・推奨の根拠は、すべてページの中にある。
ユーザーの直接の質問への回答も、ページに書いたなら書かない。

なぜ枠を作らないか: 「ページに書いていない申し送り」を例外として認めると、
提示のたびにその枠を埋める内容を探すようになる。ページに書けたはずの内容が
ターミナルへ逃げ、読まなくても分かる要約が再生産される。

## 回答の受け取り

ユーザーから「## HTML フォーム回答」で始まるテキストが貼られたら HTML フォームの回答として扱う。
