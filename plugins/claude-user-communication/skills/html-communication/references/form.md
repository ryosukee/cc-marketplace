# 確認フォームの構成と回答操作

`{SKILL_DIR}` は `SKILL.md` がある skill ディレクトリの絶対パスを表す。
この参照ファイルがある `references/` ではない。コマンド内では実際のパスに置き換える。

- 設問の節は組み立て時に `section.rng[data-q]` の範囲になる。
  範囲のラベル（`.rlabel`）は組み立てが「設問 2 / 5」だけを出し、「設問 2 の判断材料」のように
  役割を説明しない。読み手が知りたいのはいまどの設問を読んでいるかで、
  その範囲が判断材料であることは 3 pane の並びと設問カードの追従が示している。
  前提部分は範囲を持たせない（その位置では設問をどれも開かない）。
  追従は各範囲と表示領域の重なりの高さで決める。節の先頭が閾値を超えたかという点の判定はしない。
  読んでいる範囲の設問カードが開き、手で開閉したものは自動追従から外れる

- form の残回答量は画面上部のバーと「残り N / M 問」で示す。
  選択・下書き復元・リセットのたびに設問カードと同じ完了判定で更新し、回答するとバーが減る。
  項目別選択は全項目を選んだときに1問完了とする。補足入力だけでは回答済みにしない。
  右下に回答数を重ねて表示しない。進捗の置き場を一つにして本文と操作欄の高さを保つ
- form の下部固定バーは、一覧復帰・回答コピー・「その他」の3操作を1行に置く。
  コピーを主操作として広く取り、全体補足とリセットは「その他」から開くメニューに入れる。
  補足欄はメニュー内の全幅を使う複数行入力にし、閉じても入力と自動保存を保つ。
  メニューは閉じるボタン・Escape・外側クリックで閉じ、キーボードで開閉と入力ができるようにする。
  補助操作を使わない間は本文を読む高さを保ち、使うときには入力の面積を確保する
- 3 pane のときバーは脚注 pane の真下へ寄せ、そこから画面右端まで伸ばす
  （1340px 段で `left: calc(50% + 344px); right: 0`。1700px 段は `+ 504px`、
  2100px 段は `+ 644px`）。設問 pane の下ではなく脚注 pane の下に置くのは、
  設問カードが使える縦幅を最大に取るため。form で丈を削るのは `#fn-pane` だけにする
  （report は `#footer-nav` が全幅に敷かれるので、[報告の構成](./report.md) のとおり両方の pane を削る）。
  メニューの補足欄はバーより広くできるが、画面端を越えない幅に収める

- form は、議題の広い前提の後に「このフォームについて」のブロックを置き、その後に設問ごとの節を置く。
  「このフォームについて」には、今回のフォームで何を提示し、何を確認するかを書く。
  推奨案、選択肢、判断結果のまとめは書かない。各設問の節では判断材料から設問へ進む

- 説明の節に出してよいのは、複数の設問に共通する前提だけ。1 つの設問にしか効かない
  判断材料は、長くてもその設問の節に置く。読み手は設問の節だけを読んで答えられる
  状態を求めており、前の説明へ戻らないと分からない設問は差し戻される
- 設問を含むセクション: 範囲のラベル（`.rlabel`）に「設問 2 / 5」を出す。
  分母は設問セクション数。見出しは別に番号を持たない
- **設問を含むセクションの見出しは問いにする。** 「〜をどこに書くか」「〜を採用するか」の
  疑問形で、何を決めるかを書く。推奨する答えを見出しに載せない。読み手が見出しで知りたいのは
  何を問われているかで、推奨は選択肢のバッジと説明が示す。
  説明の節の見出しは従来どおり主張型（結論を見出しに載せる）

- **冒頭に設問の件数・所在・設問どうしの関係を書かない。** 「決めることは 6 件で、各設問は
  判断材料の直後にあります」「設問 2〜4 は設問 1 で案 1 系を選んだ場合の設計判断です」の類は、
  読み方の案内そのもの。上から順に読めば分かる並びにするのが先で、予告が要るなら並びが悪い。
  設問へのリンクの目次も置かない。件数は設問 pane の見出しと上部の残回答バーが示す

- 1 議題 1 セクション。判断セクションは「決めること → 背景 → 判断材料 → 設問」の同型に揃える。
  設問の節は自己完結させる。対象が何か（どのファイル・どの条項・どの提案か）と、
  選択肢に出る語の実体を、その節の中に書く。前の節で説明したからと省かない

- 推奨バッジには根拠の併記と覆し可能性（非推奨側も選べることの明示）を必須にする
    - 選択肢の説明を長所と短所に分ける形（JSON の `pros` / `cons`。雛形の `.proscons`）を使うときは 3 つを守る。
      推奨案の短所に「他案を採る条件」を書く（これが覆し可能性の明示を兼ねる）、
      1 行 1 文 60 字以内にする（`label` はクリック対象で読み込む場所ではない）、
      選択肢の説明（`.d` = 案の中身）と積層して使う（長所短所 = 案の帰結）。
      選択肢が 2 つで片方が明確に優位なときは使わない。短所が空振りする

- **Claude に読ませる文書・仕組みの置き場を問う設問では、種別を全件並べてから落とす。**
  rule（user global とプロジェクト固有）/ 参照知識 skill / hook / agent / 作業手順 skill /
  CLAUDE.md の 6 種を当て、採らない種別には落とした理由を 1 文で書く。
  並べずに 2〜3 案だけ出すと、読者は「他に手が無い」と受け取る。
  置き場を問う設問でないなら、この項目は当たらない
- **推奨の説明には「他案を排除する理由」を書く。** 推奨案の利点だけを書かない。
  「A は速い」は根拠ではなく、「B は速いが復旧手段が無い」が根拠。
  覆せる条件も、読者がその場で真偽を判定できる形にする
  （「今後 〜 しか出ないなら」のような全称命題は判定できない）
- **複数の判断を 1 つの回答で一括承認させない。** 「この N 件でよいですか」の形は禁止。
  判断 1 件につき設問を 1 つ置き、それぞれに選択肢を付ける。設問が増えること自体は
  まとめる理由にならない
    - 同じ二択を各項目へ繰り返す `question.items` は、項目ごとに独立した radio を持つため使ってよい。
      設問カードと回答行は一つでも、判断は項目ごとに別々に覆せる
    - 対象は、判定・置き場・処置のような個別に覆せる判断の集合。
      集合全体への処理方針（順序・時期・まとめて処理するか）を問う設問は 1 件の判断なので対象外
    - why: 一括承認は、個別に覆したい読み手に「どれをどう直すか」を自由記述で書かせる形になり、
      選択肢形式の利点が消える
- **確認も選択肢を持つ設問にする。** チェックリストは使わない。
  「承認するだけ」に見える項目も、覆す余地があるなら選択肢が要る。
  覆す余地が無いなら、それは設問ではないので設問にしない
    - why: チェックリストは 1 項目あたりの情報量が選択肢より落ちる形をしていて、
      「本文で説明済みだから参照だけでよい」と書く経路ができる。
      「判断が要るものは混ぜない」という条項だけでは、判断の要る項目が混ざるのを防げない
- **まだ読んでいない後続の設問を前提にした条件を、判断材料に書かない（非推奨）。**
  読者はその設問の選択肢も用語もまだ知らないので、条件が判定できない。
  前提が要るならその設問より前に置くか、条件ごと 1 つの設問へ統合するのが先
    - それでも書くときは「設問 N で推奨案を選んだ場合」までにとどめる。
      個別の選択肢の名前や、その説明を読まないと分からない用語を出さない
    - 1 文に条件を 2 つ以上詰めない。条件が 2 つあるなら文を分ける
- **設問カードの回答済みマーカー（`.qstat`）は雛形が付ける。**
  折り畳んだ状態でも、どこまで答えたかが一覧で分かる。
  色は使わず、形（輪郭の丸 / 塗りの丸）と語（未回答 / 回答済み）の両方で区別する。
  雛形の色役割は 3 つに固定してあり、状態を表す枠が無い。
  判定は上部の残回答バーと揃い、選択肢を選ぶと回答済みになる（補足欄だけの記入は未回答）

## 確認（設問）を含めるときの作り

- **設問が多いページは設問をグループ化できる（任意）。** JSON の `groups` に `{ id, name }` を書き、
  設問の節に `group` を付ける。設問 pane のグループ容器（`.qgrp`）・カードの summary・範囲のラベルは組み立てが出す
    - グループ名は内容の名詞句だけ。件数・接頭語・動詞句を付けない。
      名前はそのページの実際の内容から付ける
    - グループ見出しには回答進捗（n/N）が JS で付く
    - カードの summary はグループ内番号「{グループ名} n / N {設問ラベル}」になる
    - 本文の範囲ラベルは「{グループ名} n / N（設問 通し / 総数）」になる。
      通し番号の分母は総設問数のまま変わらない
    - グループ外の設問は従来の「設問 N / M」のまま混在できる
    - 3 pane の設問 pane では、雛形の JS が設問カードを本文に出てくる順に並べる。
      グループに入れた設問とグループ外の設問が混ざっていても、本文の順のまま並ぶ。
      グループ容器を pane に書く順は、表示の並びに影響しない
- 設問は関連するセクションの直下に置く。ページ末尾にまとめて並べない
    - 設問が多いとき、末尾集約は判断材料と設問の往復スクロールが発生して回答しづらい
    - 回答コピー機能は全セクションの設問を集約して 1 テキストにする（配置と集約は別）
- 最終確認などの自由記入欄（`#free`）は、下部固定領域の「その他」から開くメニューに置く。
  ページ末尾には出ない。回答を受領したページでも補足を開いて読めるようにする。
  上から順に読みながら、気づいた点を都度記入できる
- 相互排他的な案を選ぶ設問は従来の radio にする。複数の独立した項目を採るかどうか選ぶ設問は
  `question.multiple: true` を書いて checkbox にする。省略時は radio。推奨案には `recommended` のバッジを付ける。
  radio の推奨は 1 件まで、checkbox は複数付けられる。書式は [設問の JSON](./form-format.md)
- 同じ二択を複数の項目へ繰り返すときは `question.items` を使う。設問カードは一つのまま、各項目に独立した
  radio を置く。全項目を選ぶまで回答済みには数えない。選択肢の文言が短く、項目数も少ない場合は、
  文言を各項目に表示する。文言が長い場合、または項目数が多く反復が読みづらい場合だけ記号を使い、
  記号と文言の対応を設問カードの冒頭で定義する。完成例と採用条件は
  [item radio](./patterns/item-radio/README.md) に置く
- 技術選定などの比較設問には、選択肢の説明文だけで判断させない。設問の直前に多観点の比較表
  (機能・性能・実績・エコシステム・リスク・移行性・保守状況など、その選定で効く観点) を置き、
  各観点は調査の裏取り付きで書く。選択肢の description は比較表の結論の要約に徹する
- 選択肢に収まらない回答用に、設問ごとに「その他」の自由記述欄と補足記入欄（任意）が付く。
  `question.items` では二択を崩さず、「その他」は付けない。設問全体の補足記入欄だけを付ける
- ページ末尾の回答の live preview と「回答をコピー」ボタンは組み立てが置く。
  ボタンはそれまでの選択・自由記述を 1 つのテキストに整形してクリップボードへコピーする
- 整形フォーマットは作業中の CodingAgent にそのまま貼れる形（雛形の script が固定している）:

  ```text
  ## HTML フォーム回答（{テーマ}）
  - Q1（{設問}）: {回答}
  - Q2（{設問}）: {回答}
  - 補足: {自由記述}
  ```

  checkbox の回答は同じ Q 行に `複数選択: {"values":["項目A","項目B"],"other":"自由記述"}` と出る。
  `other` は「その他」を選んだ場合だけ入り、通常の選択肢と同時に選べる。
  `record-answer.mjs` は `answers.items` の既存 `value` を `null` とし、選択した通常の値を `multiple` 配列に記録する。
  radio の回答行と `value` は従来どおり

  項目別 radio の回答は同じ Q 行に `項目別選択: {"項目ID":"選択肢","未回答の項目ID":null}` と出る。
  `record-answer.mjs` は `answers.items` の `value` を `null` とし、項目 ID ごとの値を `selections` に記録する

- クリップボード API が使えない環境向けの、preview の textarea を全選択コピーするフォールバックは雛形が持つ
- 未回答の設問がある状態でもコピーは許可し、未回答は `未回答` と明記する（雛形の script）
