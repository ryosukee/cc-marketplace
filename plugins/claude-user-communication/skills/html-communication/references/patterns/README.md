# 見せ方のパターン集

資料の内容に応じて任意に選べる、代表的な表現の見本を集める。
議題ごとに作った表現のうち、採用条件を示して次に使えるものだけを残す。

このファイルはカタログ自体の規約だけを持つ。個々のパターンは同階層のディレクトリにある。

## 置き場の役割

| 置き場 | 役割 |
| --- | --- |
| [共通の生成と一覧の運用](../common-workflow.md) | 色の役割、フォントの段、ページの構成 |
| [本文の規範](../writing.md)と[フォームの規範](../form.md) | 表の作りと設問の置き方 |
| [生成元 JSON の書式](../page-format.md) | 本文を書く JSON のキーとブロックの形 |
| `templates/page.html` | 基盤の実装。head と script だけを持ち、本文の markup は組み立てが出す |
| このディレクトリ | 個別のパターン。使うページだけが取り込む |

任意に選ぶ表現の CSS はパターンのディレクトリに置き、使うページだけが取り込む。
使わないページへも CSS を運ぶと、共通テンプレートが表現の種類に応じて伸び続ける。

採用済みの固定操作は、生成元 JSON・生成器・共通テンプレートが持つ。
詳細パネル、階層の展開、図のそばの補足、脚注全文の表示は
[共通操作](../detail-operations.md) の書式で指定し、ギャラリーへ操作例を追加しない。
行番号付きコード、差分、呼び出しツリーと対象別の回答は、
[コード・差分・呼び出しツリー](../rich-code.md) の書式で指定する。
見本の件数ではなく、作成側が選ぶ表現か、ページで揃える操作かで置き場を決める。
共通化が難しいときは、対象範囲・理由・追加で必要なデータや生成側の対応を示し、方式を利用者と決める。
共通化できないという理由だけでギャラリーへ移さない。

## ディレクトリの構成

パターン 1 つにつきディレクトリ 1 つ。中身は 3 ファイルに固定する。

```text
patterns/
├── README.md                       # このファイル
└── {pattern-name}/
    ├── README.md                   # front matter の group + 名前・条件・出典
    ├── style.css                   # CSS。雛形の CSS トークンを参照してよい
    └── example.html                # 使用例の HTML 断片
```

`{pattern-name}` は英小文字とハイフンにする。公式のデザインシステムに同じ形があれば
その呼称に揃え、無ければ説明的な名前を付ける。

## グループ

パターンの README の先頭に front matter を置き、`group` を書く。gallery の左のリンク集が
これで束ねる。書かなければ「その他」に入る。

```yaml
---
group: 進行と状態
---
```

グループは**用途で切る**。コンポーネントの種類（navigation / data display のような
デザインシステムの分類）で切らない。この集まりを引くのは「こういうことを伝えたい」と
思ったときで、部品の種類を知りたいときではない。

現在あるグループ:

| グループ | 何を伝えるためのものか |
| --- | --- |
| 進行と状態 | 工程がどこまで進んだか、いま何がどの状態か |
| 比較と選択 | 複数の案が何によって違うか |
| 変更と差分 | 現行から何が変わるか |
| 構成と境界 | 何がどの範囲に属し、範囲の間で何が渡るか |

新しいグループは、そこに入るパターンが実際に出てきたときに作る。
空のグループを先に用意しない。1 グループに 1 件しか入らない状態が続くなら、
グループの切り方が細かすぎる。

## パターンの README に書くこと

6 つだけ。増やさない。

- front matter の `group`。用途で切る
- 名前。公式の呼称に揃えたか、自分で付けたかを書く。自分で付けたなら公式に無い旨も書く
- 何を表すか。1 文
- 使ってよい条件
- 使ってはいけない条件
- 近縁パターンとの区別。似ているが別物のものがあれば、使い分けの基準

出典があれば情報源ブロックで最後に置く。

判定基準: 次にこの形を使いたくなったとき、条件だけ読んで採否を決められるか。
決められないなら条件の書き方が悪い。

## 使い方

1. このディレクトリを見て、使えるパターンがあるかを確かめる
2. あれば生成元 JSON の `css` にパターン名を書く（組み立てが `style.css` を雛形の CSS の末尾に足す）。
   `example.html` を参考にした markup は `src/{語幹}.figures.html` の `<template data-fig="…">` に置き、
   JSON からは `custom`（キャプション無し）か `fig`（図として番号とキャプションを付ける）で参照する
   - 設問の生成方法を示す item radio は例外で、`question.items` を使う。`example.html` は、組み立て後の表示を示す
3. 無ければその場で作る。任意に選ぶ代表的な表現として次に使えるものだけ、作った後にここへ足す

生成ページは self-contained が必須なので、CSS は組み立てが必ずページの中へ貼り込む。
外部ファイルとして参照しない。

## 図の生成手段を選ぶ

図を本文へ埋め込むか、独立した Viewer で見せるかによって生成手段を選ぶ。

| 要件 | 生成手段 |
| --- | --- |
| 既存のカード、比較、進行、差分、境界の表現で足りる | このパターン集を使い、本文へ埋め込む |
| パターン集に無い独自の図を本文へ埋め込む | Tailwind CLI で markup と CSS を生成する |
| 読み手が線をたどって読む図を本文へ埋め込み、下記「図を D2 で組む」の条件を満たす | D2 で SVG を描画し、img として埋め込む |
| architecture、workflow、sequence、data flow、lifecycle / state diagram を探索・trace・export できる形で見せる | 利用可能なら Archify で独立 HTML Viewer を生成する |
| HTML レポートの要点と、操作可能な詳細図の両方が要る | 本文にはパターン集か Tailwind で要点を置き、Archify の独立 Viewer へリンクする |

Archify は独立した HTML Viewer を作る skill であり、ページへ取り込む CSS と markup のパターンではない。
このディレクトリや gallery には追加しない。現在の skill 一覧で Archify が利用できなければ、
既存パターンまたは Tailwind のインライン図を使う。html-communication から Archify を自動で導入しない。

## 処理順と状態の図を選ぶ

処理順を示すのか、保持する状態とイベントによる変化を示すのかを先に決める。
状態図は関係の意味に合わせて選び、すべてを一律の上下の進行順にはしない。

| 伝える関係 | パターン | 配置で示すこと |
| --- | --- | --- |
| 処理順と条件判断 | [flowchart-decision](./flowchart-decision/README.md) | 処理の矩形と判断の菱形を分け、結果を枝へ置く |
| 同じ操作の結果による状態の分岐 | [state-result-branch](./state-result-branch/README.md) | 開始状態から択一の結果へ枝分かれする |
| 同じ状態へ戻る遷移 | [state-self-transition](./state-self-transition/README.md) | 自己ループを外側へ出す |
| 異なる状態間の往復 | [state-cycle](./state-cycle/README.md) | 状態を並べ、往路と復路を別の線にする |
| 親状態と子状態 | [state-hierarchy](./state-hierarchy/README.md) | 子状態を親状態の枠内へ置く |
| 同時に有効な複数の状態軸 | [state-parallel](./state-parallel/README.md) | 親の中を領域に分け、状態軸の名前を付ける |

処理順は [flowchart-decision](./flowchart-decision/README.md) を使う。
状態の分岐は [state-result-branch](./state-result-branch/README.md)、同じ状態へ戻る経路は [state-self-transition](./state-self-transition/README.md)、往復は [state-cycle](./state-cycle/README.md) を使う。
親子関係は [state-hierarchy](./state-hierarchy/README.md)、同時に有効な状態軸は [state-parallel](./state-parallel/README.md) を使う。

これらは操作スクリプトを持たない静止見本である。
状態ノードの選択・イベント実行・履歴表示は共通実装へ指定し、パターンごとに同じ操作を複製しない。
採用条件と近縁表現との違い、図法の一次資料は各パターンの README にある。

## 図を Tailwind で組む

独自のインライン図は Tailwind CLI で作る。外部 CDN は読み込めないので、生成のたびに CLI を回して
使ったクラスだけの CSS を出し、ページの `<style data-scope="figures">` へ貼り込む。

作業ディレクトリを 1 つ作り、次の 3 ファイルを置く。

```text
work/
├── in.css        # 下記の 3 行 + 段落余白の打ち消し
├── figure.html   # 図のマークアップ
└── package.json  # npm install tailwindcss で作られる
```

`in.css` の中身。

```css
@import "tailwindcss/theme.css";
@import "tailwindcss/utilities.css";
@source "./figure.html";
/* preflight を読み込まないので、雛形が段落に載せている下余白だけを図の中で打ち消す */
.fig p { margin: 0; }
```

**リセット（preflight）を読み込まない。** `@import "tailwindcss"` と書くと入ってしまう。
入れると雛形の表・見出し・段落・ボタンの作りが全部消える。

```sh
npm install tailwindcss@4.3.3
npx @tailwindcss/cli@4.3.3 -i in.css -o out.css --minify
```

**版を固定する。** `@latest` にすると、次に回したときに版が変わって図の見た目が動いても
検知できない。上げるときは図を作り直して差分を見る。

出た `out.css` を `src/{語幹}.figures.html` の `<style data-scope="figures">` へそのまま入れる。
組み立てがページの雛形の `<style>` の後ろに置く。
図 3 つ程度で 9 KB 前後。ダークは Tailwind の `dark:` が `prefers-color-scheme` を見るので、
雛形と同じ切り替わり方になる。

アイコンはインライン SVG の `symbol` を figures ファイルの `template` と `style` の外に置き、`<use href="#id">` で呼ぶ
（組み立てが `<body>` の先頭に置く）。アイコンフォントもアイコンセットも読み込まない。

色とフォントの段は、この `style` の中では雛形の規定の対象外
（[共通の生成規定](../common-workflow.md) と [図の手順](../figures.md)）。機械検査もこの `style` を飛ばす。

### 守ること

1. **Tailwind は図の中だけで使う。** 判定はその要素が `.fig` の中にあるかどうか。
   本文・表・設問カード・下部バーに使わない。外に出た時点で雛形の CSS と二重管理になる
2. **preflight を読み込まない。** `@import "tailwindcss"` と書くと入る。
   `theme.css` と `utilities.css` を個別に読む
3. **生成した CSS は `<style data-scope="figures">` にだけ入れる。**
   雛形の `<style>` に混ぜない。この属性が、規定を適用しない範囲と機械検査が飛ばす範囲の
   両方を決めている
4. **色に意味を持たせたら凡例を出す。** 図の中は色が自由になるぶん、これが唯一の縛りになる。
   色だけで区別させず、名前か形を併記する
5. **アイコンはインライン SVG の `symbol` で持つ。** アイコンフォントもアイコンセットも
   読み込まない。figures ファイルの `template` の外に `symbol` を置いて `<use>` で呼び、色は `currentColor` にして
   図の色に追従させる
6. **生成物を手で編集しない。** `style.css` は CLI の出力。直すときは `example.html` の
   クラスを変えて生成し直す

## 図を D2 で組む

D2 は、要素と要素を結ぶ線で意味を伝える図を、配置と線の引き回しまで計算して描く。
ラベルは折り返さず、図は画像として縮む。Tailwind は HTML の要素で組むので表せる形が広く、
文字は折り返し、ページのフォントとページ内検索に揃う。線を引くのは苦手。
このため Tailwind を既定にし、D2 は次の判定で当てはまる図にだけ使う。

### D2 を使う図の判定

上から順に当て、最初に当たったもので決める。

1. シーケンス図・ER 図・クラス図は D2 で描く。D2 に専用の形（`sequence_diagram`・`sql_table`・`class`）がある
2. 読み手が線をたどって読む図は D2 の候補にする
    - 当たるのは、隣り合わない要素を線で結ぶ図、線が合流・交差する図、自分自身へ戻る線がある図
    - 線が無い図と、1 列に並んだ隣どうしを直線で結ぶだけの図は Tailwind で描く。
      層、範囲の帯、マトリクス、比較、比率、時系列のように、位置・囲い・大きさで意味を伝える図はここで Tailwind に決まる
3. D2 の候補は、次の 2 つを両方満たすときだけ D2 で描く。満たせないなら図を分けるか、
   線を減らして Tailwind で文字を主にした図にする
    - ラベルが 1 行に収まる。目安は全角 10 字。長い説明は本文か凡例として図の外に置く
    - 描いた図の幅が 560px 以下。縦向き（`direction: down`）に描き、横に並ぶノードを 2〜3 個に抑える

why: D2 はラベルを折り返さないので、長いラベルはノードを横に広げる。
図は本文の列と画面の幅に合わせて縮むので、幅 560px を超えると横幅 390px の画面で文字が 10px を下回る
（350 ÷ 560 × 16 = 10）。D2 は全角 1 文字を約 19px と見積もるので、全角 10 字のノードは幅約 235px で、2 つ並べて約 530px に収まる。

### 手順

1. 生成元 JSON に `{ "fig": { "id": "…", "caption": "…", "d2": true, "alt": "…" } }` を書く。
   書式は [D2 の図](../figure-format.md#d2-の図) にある
2. 原文を `src/{語幹}.{図の id}.d2` に書く
3. `node "{SKILL_DIR}/scripts/render-d2.mjs" <src/{語幹}.json>` で SVG を描画する
    - D2 は npm の WASM 版 `@terrastruct/d2@0.1.33` を実行のたびに一時ディレクトリへ入れて使う。
      npm registry に届かないと描画が止まる
    - Codex の sandbox はネットワークに出られないので、sandbox の外で実行する承認を求めて回す。
      承認を得られなければ、D2 の図をやめて Tailwind で描く
    - テーマはライト 0（Neutral Default）、ダーク 200（Dark Mauve）で、ページと同じく OS の設定で切り替わる
    - レイアウトは D2 の既定の dagre になる。線を直角に引き回したい図は、原文に
      `vars: { d2-config: { layout-engine: elk } }` を書いて elk にする。
      elk は自分へ戻る線を図の外へはみ出して描くので、自分へ戻る線がある図は dagre のままにする
4. 組み立てる。原文を直したら 3 からやり直す

### 守ること

1. **図の要点を本文に文字で書く。** img の中の文字はページ内検索にかからず、支援技術にも読まれない。
   図を見なくても本文だけで要点が分かるようにする
2. **幅 560px を超えたら描き直す。** `render-d2.mjs` と `check-source.mjs` が指摘する
3. **色に意味を持たせたら凡例を出す。** 図の色は `vars.d2-config` の `theme-overrides` と
   `dark-theme-overrides` で図ごとに変えられる。条件は Tailwind の図と同じ
4. **SVG を手で編集しない。** 直すときは `.d2` を直して描画し直す。SVG の先頭の注釈にある原文のハッシュが合わなくなる

## 実物を並べて見る

全パターンを 1 枚に並べた HTML を作れる。

**このディレクトリと gallery は確定した完成品だけを置く場所。**
検討中の候補・採否の判定・暫定の注記を混ぜない。
新しい形を試すときは、このディレクトリの外に比較用のページを別に作って判断し、
残すと決まったものだけをここへ入れる。

```sh
node "{SKILL_DIR}/scripts/build-gallery.mjs" <出力先パス>
```

出力は 1 枚。2 pane で、左にグループ別のリンク集、本文に全パターンを並べる。
リンクは同一ページ内のアンカーで、ページを移動しない。
スクロールに合わせて現在地が追従する。狭幅では 1 列になり、リンク集が本文の先頭へ来る。

リンク集を独立した pane に置くのは、パターンが増えたときに本文へ埋もれないようにするため。
本文と同じ流れに置くと、一覧としての役目を果たさなくなる。

パターンごとの個別ページは作らない。配信するファイルがパターンの数だけ増えるため。
全パターンの CSS を 1 枚に連結するので、増えるとセレクタが衝突しうる。
衝突が起きたら、そのときに個別へ切り出す形を再検討する。

配信ディレクトリへ `gallery.html` として出すと、
index の「見せ方のパターン集」からリンクで辿れる。
一覧のエントリは持たせない（回答・確認の対象ではないため）。

**このディレクトリを更新したら gallery を作り直す。** パターンの追加・削除・修正の
どれでも作り直す。生成物は手で編集しない。

### gallery が雛形のページレイアウトを引き継がない理由

生成物の本文は `main` ではなく `.gallery` で包む。雛形の CSS は `main` を
ページ用のグリッドにするメディアクエリを持っており、連結すると gallery にも
ページの列配置が適用される。器を `.gallery` にすれば、雛形のページレイアウト用セレクタ
（`main` / `#bar` / `#q-pane` / `#toc-pane` / `#fn-pane`）がどれも一致しない。
持ち込みたいのは色トークンと文字組だけで、ページの骨格ではない。
