# 読む専用の報告と確認

`{SKILL_DIR}` は `SKILL.md` がある skill ディレクトリの絶対パスを表す。
この参照ファイルがある `references/` ではない。コマンド内では実際のパスに置き換える。

- report 形式（設問なしの読む専用ページ）は操作ボタンが無いので、追従する固定領域（`#footer-nav`）に
  「一覧に戻る」・プロジェクトバッジ・生成した版を横並びで置くだけにする（確認を受けた後はその表示も入る）。
  スクロールしても消えないようにする。JSON の `type` を `report` にすると組み立てがこの形にする
- **report の左の列には本文の見出しツリー（`#toc-pane`）を置く。** 設問が無いぶん空く列で、
  1024px 以上の 2 pane で出す。狭幅では見出しツリーを隠し、本文を 1 列で読む。
  本文へ案内文を置かない規定は地の文に当たるもので、本文の外の領域に置く一覧はこれに当たらない
  （form では `#q-pane` が同じ位置で同じ役目を担っている）
    - 載せるのは節の見出し（`h2`）だけ。参考資料と生成に関する補足は読み飛ばしてよい節なので載せない。
      `h3` も載せない。節の件数で出し分けもしない
    - いま読んでいる節は `h2` の画面上の位置で決める。report の節は範囲の要素で包まれていないので、
      form の `.rng` を単位にする追従とは判定が別になる。読み位置の線は form と同じ画面の上から 35%。
      現在地がツリーの表示領域から出たら、雛形の script が pane の中だけをスクロールして戻す
    - 現在地の表し方は本文の範囲と揃える。左の縦罫を 2px の `--link` にし、面は敷かない。
      項目そのものは操作できるものなので `--link` で出す
    - 見出しツリーは上部バーと下部ナビの間に収め、長い一覧は pane 内でスクロールする。
      脚注と補足は本文に重なる独立したパネルへ出す。
    - 雛形は form 用と report 用の `<script>` を `data-scope` で分けて持ち、組み立てが使わないほうを落とす
- **`#footer-nav` の中身は本文の列に合わせる。** 帯は全幅に敷いたまま、
  1024px 以上では本文列の左端へ合わせる。狭幅では本文と同じ中央の幅に収める。

- report の構成は「前提（この文書は何の話か）→ 報告のまとめ → 詳細」の順にする

## report の確認

report には回答フォームが無く、ユーザーは「確認しました」と明示せずに次の話へ進むことが多い。
そのため、確認済みにするかを Claude の側から問う。

- ユーザーの返答が `unconfirmed` の report を読んだうえで次へ進んでいると取れたら、そのターンの返答で、
  その report を確認済みにしてよいかを問う。取れる返答は、report の結論を前提にした指示、
  report の内容への言及や質問、report が示した次の作業への着手の指示
- 対象は、このセッションで提示して `unconfirmed` のままの report。`living` の report は問わない
- 承認を受けたターンで
  `node "{SKILL_DIR}/scripts/record-answer.mjs" <src/{語幹}.json> --confirm "<発言の逐語>"` を回す。
  発言には、report を読んだと取れた返答と、承認の返答の両方を逐語で入れる。status は `confirmed` になる
- 断られたら `unconfirmed` のまま据え置く。同じ report について再び問うのは、
  ユーザーが新たにその report の内容に触れたときだけにする
- 推測で確認済みにしない。返答が読んだうえかどうかは Claude の推測でしかない

why: form の回答は決まった形のテキストで届き、受け取ったことが受領の操作のきっかけになる。
report の確認は決まった形で届かないので、問わないと状態の更新のきっかけが生まれず、
読み終えた report が確認待ちのまま一覧に残る。確認待ちが読み終えたものと未読のものの混在になると、
一覧から未読の report を見つけられない。
