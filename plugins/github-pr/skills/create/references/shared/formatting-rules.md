# PR 本文の共通フォーマットルール

テンプレート（ロング版・ショート版）共通で適用するルール。

## 大前提

このタスクや変更について何も知らない初見の人に伝えるつもりで書く。
専門用語やプロジェクト固有の概念は本文中で必ず説明する。「知っているだろう」は前提にしない。

## 対比の主語を明示する

現状と理想の対比を書くとき、「何がそう言っているのか」を必ず明示する。
主語がないと、このリポジトリの話なのか外部仕様の話なのかが読み取れない。

```markdown
<!-- NG: 主語がなく曖昧 -->
- `description`/`globs`/`alwaysApply` の3フィールドを必須と記載していた
    - 公式は `paths` のみ

<!-- OK: 主語を明示 -->
- このリポジトリの rule-authoring.md では `description`/`globs`/`alwaysApply` の3フィールドを必須と記載していた
    - 公式は `paths` のみ
```

## Claude が投稿するコメントの署名行

Claude が投稿する PR コメント（行指定・ファイル・conversation comment・スレッド返信）は、
本文の末尾に空行を挟んで次の 1 行を付ける。PR 本文ではなくコメントが対象（PR 本文の footer は別にある）。

```text
🤖 posted by Claude Code
```

`gh` CLI はユーザーのトークンで投稿するので、投稿者ではユーザー自身のコメントと見分けられない。
この行だけが Claude の投稿を見分ける手がかりになる。更新フローで見直す・編集する・resolve する対象は、
この行を持つコメントに限る。この行が無いコメントはユーザーか他の人の投稿として扱い、編集も resolve もしない。

## テーブルの使用

まず箇条書きで書くことを考える。情報の構造として比較・対応関係が明確でテーブルが適していると判断した場合のみテーブルにする。

## PR 参照 (`#XX`) の書き方

他の PR を `#37` 等で参照する場合、GitHub UI 上で PR タイトルに展開されて長くなる。
`#XX` リンクは必ず箇条書きの独立した項目にし、後ろに文を続けない。

- `#XX` を主項目にし、補足情報（マージ済み、状態等）はネストする
- 文脈の説明が先にある場合は、説明を主項目にして `#XX` をネストする

```markdown
<!-- #XX を主項目にするパターン -->
- #37
    - マージ済み

<!-- 文脈が先にあるパターン -->
- 以前の変更に対応漏れがあったので修正
    - #XX
        - ver x.x.x にマージ済み、prd 未リリース

<!-- NG: リンクが補足と同じ行に混在 -->
- マージ済み, #37
- Phase1 (#37) はフロントマターの...
```
