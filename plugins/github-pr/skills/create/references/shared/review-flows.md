# PR のレビューの 2 系統

PR を draft で作った後の流れは、誰がレビューするかで 2 つに分かれる。
open（ready for review）を誰が行うか、本人の了承が PR のどこに残るか、誰がマージするかが違う。

## 系統 A: セルフレビュー・セルフマージ

レビュアーが作者本人だけの repo。

GitHub は PR の作者が自分の PR に approve を付けることを許さない。
Claude Code はローカルで本人の `gh` 認証を使うので、Claude が出した PR も作者は本人になり、
この系統では approve が付けられない。代わりに `approve` ラベルを本人の了承の合図として使う。

1. draft で作る
2. 作成直後に open する（`gh pr ready {number}`）。open は形式的な操作なので指示を待たない
3. 本人がレビューし、マージしてよければ PR に `approve` ラベルを付ける
4. ラベルが付いていることを確かめてマージする

ラベルの確認は次のコマンドで行う。

```bash
gh pr view {number} --json labels --jq '[.labels[].name] | index("approve") != null'
```

`true` ならマージしてよい。`false` ならマージせず、本人のレビューを待つ。
判定はラベルの有無だけで行い、コメントの本文やチャットの了承を根拠にしない。

repo に `approve` ラベルが無いときは、本人に作成を依頼する。Claude は作らない。

## 系統 B: 他人にレビューしてもらう repo

作者本人のほかにレビュアーがいる repo（組織の repo など）。

1. draft で作る
2. 本人が draft のままレビューし、その指摘に対応する
3. open は本人の確認が済んだ合図として本人が行う。open は他人にレビューを依頼する公開の操作なので、指示なしに行わない（本人の指示があれば代わりに行う）
4. 他人がレビューし、approve を付ける
5. マージは人間が行う。Claude はマージしない

## 系統の判定

repo の所有者が本人のアカウント（組織ではない）で、他のレビュアーがいなければ A。組織の repo か、他のレビュアーがいれば B。迷ったら B。
