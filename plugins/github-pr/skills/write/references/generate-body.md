# PR 本文の生成

## 規模の判定とテンプレート選択

事前に取得した差分情報から PR のテンプレートを選択する。判断軸はファイル数や行数ではなく **差分を見れば変更内容が自明に理解できるか** にある。多ファイルでも内容が自明ならショート版でよい。

| テンプレート | 基準 |
|---|---|
| ショート版 ([template.md](short/template.md) + [rules.md](short/rules.md)) | 差分を見れば変更内容が自明に理解できる。レビュアーが本文の補助なしで判断できる |
| ロング版 ([template.md](long/template.md) + [rules.md](long/rules.md)) | 設計判断・非自明な理由・複数箇所の連携があり、レビュアーが全体像を把握するのに本文の補助が必要 |

典型例:

- ショート版: 単一箇所のバグ修正、ドキュメント更新、config bump、コメント/文言修正、リネーム、依存バージョン更新、ルール/スキル/プロンプトの調整
- ロング版: 新機能追加、アーキテクチャ変更、複数箇所をまたぐリファクタ、バグの根本原因が非自明、複数の独立した変更を含む

判断が難しい場合はユーザーに確認する。

リポジトリに `.github/PULL_REQUEST_TEMPLATE.md` が存在する場合はそのテンプレートを優先する。

## タイトル

- ユーザー指定のタイトルを使用、またはコミットから自動生成（日本語）

## Pre-open チェックリスト

PR は draft で作成される。本文の**最下部 (How to check の後)** に以下の折りたたみを挿入する。PR author が draft → open にする前に確認すべき最低限のタスク。

```markdown
<details open><summary>Pre-open checklist</summary>

- [ ] PR body の内容を確認した（必要に応じて手動で書き換えてよい）
- [ ] セルフレビューをし、行指定コメントの内容を確認した
- [ ] How to check のリスト内容が妥当であることを確認した
- [ ] How to check の各項目を確認しチェックをつけた

</details>
```

配置ルール:

- レビュアー視点で本文の先頭にあるとノイズになるため、最下部に置く
- デフォルトは `open` 属性を付けて開いたままにする。チェックボックスをクリックするたびに閉じるのを避けるため

## WARNING（ベースが main 以外の場合）

ベースブランチが `main` 以外の場合（= 他の PR のブランチから派生している場合）、本文の最先頭に以下を記載する:

```markdown
> [!WARNING]
> #XX から先にマージします
```

`#XX` はベースブランチに対応する PR 番号。この WARNING はテンプレートの構成よりも前（本文の1行目）に置く。
`#XX` の書き方は [formatting-rules.md の「PR 参照 (`#XX`) の書き方」](shared/formatting-rules.md) に従う。

## 本文

選択したテンプレートとルールを Read し、その構成に従って本文を生成する。

## トンマナ

PR 本文は `.md` ファイルではないため、Markdown 向けの整形ルールが自動適用されない。次を意識する:

- 一文は短く。接続が多い長文より、短文 + 箇条書き
- 複数の文が改行なく続く長い段落は避ける。話題や論点の区切りで改行・空行を入れる
- 3〜4 文を超えるなら段落を分けるか箇条書きに切り替える

## 冒頭で端的に要点を示す

PR 本文の冒頭 (概要セクション) は、レビュアーが背景知識なしで、ぱっと見で主題を把握できるように書く。PR 本文は内部調査の過程や発見順から書いてしまいがちなので、明示的に意識する。

原則:

- **「何の PR か」を 1 フレーズで言い切る → 詳細はネストで**
    - 概要の最初の行は「◯◯ の改善です」「◯◯ のバグ修正です」のような 1 フレーズ宣言にする
    - 複数の情報 (何を・なぜ・どう) を 1 行に詰め込まない。詳細は下のネスト箇条書きに分ける
- 結論から書く。調査の過程や発見順から始めない
- 短文 + 箇条書きで、1 ブロックの分量を軽く保つ。ぱっと見で重い段落を作らない
- 読者が知りたい順に並べる。順番の例はいくつかあり、PR の性質で変わる
    - バグ修正: 症状 → 原因 → 対応
    - 機能追加: 何を作ったか → なぜ必要か → 変更の要点
    - リファクタ: 何を整理したか → 動機 → 影響範囲
    - 順番は一例。PR ごとに読者が一番知りたい順を考える
- 概要と変更の詳細で抽象レベルを分ける
    - 概要: 方針レベル (「◯◯ の方針を追加」「◯◯ の挙動を変更」)
    - 変更の詳細: 実装レベル (セクション名、関数名、コード変更)
    - 概要でセクション名や関数名を繰り返さない。重複になる

PR 番号 (`#XX`) の書き方は [shared/formatting-rules.md](shared/formatting-rules.md) の「PR 参照 (`#XX`) の書き方」に従う。1 行に詰めず、独立した箇条書き項目にする。

### 端的に示すための手段

冒頭で要点を伝える目的のために、以下を使える場面があれば使う。該当しない PR では不要:

- 症状の Before/After 対比 (「本来 X / 実際 Y」のような短い対比)
- 症状を示す外部リンク (Slack 通知、Actions run、Issue、Sentry 等)
- スクリーンショット埋め込み (URL だけでなく `<img>` タグで本文中に直接埋める)
- 定常フロー外のきっかけの明示 (Slack 議論、会議の話題、思いつき、障害通知 等)
    - project によっては「定常フロー」自体がないこともある。その場合は「何がきっかけで思い立ったか」を素直に書く
- 主目的以外の「おまけ変更」の予告 (本来は別 PR 推奨だが、まとめる場合は冒頭で開示)
- 「原因ではない可能性」の先回り排除 (レビュアーが自然に疑いそうな別原因を「〜は正しかった」と明示)

## 参照ドキュメントの permalink

背景知識としてリポジトリ内の既存ドキュメントを参照する場合、main の最新ではなく commit ハッシュ付き permalink を使う。将来ドキュメントが更新されてもレビュアーが PR 作成時点の内容を参照できる。

```
https://github.com/{owner}/{repo}/blob/{commit_sha}/path/to/doc.md
```

`{commit_sha}` は PR の HEAD コミット (`git rev-parse HEAD`) を使うのが分かりやすい。

## How to check

PR authorがレビュー前にチェックを入れ、検証済みの状態でレビューに出すためのセクション。レビュアーも自身の環境で同じ手順を再現できる。

### 省略可能なケース

**レビュー以外に確認手段がない PR では How to check セクション自体を省略してよい**。無理に埋めるとノイズになる。

- 省略可: ドキュメント/コメント/文言の修正、スキル/ルール/プロンプトの調整、意味的変更のない fmt、typo 修正
- 必須: コード変更、挙動変更、バグ修正、新機能、設定の意味的変更

境界ケース (ドキュメントだが CI で lint される、スキルだが自動検証がある等) は省略せず 1〜2 項目だけ入れる。

レビューでしか判断できないこと（記述の内容面での正確性、設計の妥当性等）は含めない。逆に、レビュアーが手動でやると面倒だがコマンドで代替できること（網羅性の grep 確認等）は積極的に入れる。実行可能なものはできるだけエビデンスを残す。コマンドなら実行結果のログ、動作確認ならキャプチャなど。

以下の観点をタグとして使う。該当する項目がない観点は省略する。無理に全観点を埋めない。

- `[正確性]` — 今回の変更自体が意図通りに実現できている
    - テストがカバーしている、grep で変更の反映を確認できる等
- `[前提]` — 変更方針の根拠（参照した情報源、前提とした事実）が正しい
    - 参照した公式ドキュメントへのリンク、既存実装でバグが再現し修正後に消えることの確認等
- `[デグレ]` — 変更していない周辺箇所で壊れていない
    - 既存テストが通る、旧い参照が残っていない等

書き方のルール

- 主項目（チェックボックス行）は「何を確認するか」を断定形で書く。疑問形（「〜か」）にしない
    - チェックを入れる = この状態であることを確認した、という意味になる
- 確認手順はネストに書く。長ければ `<details>` で折りたたむ
- 確認手段は確実で再現可能な方法を選ぶ。結果が毎回同じになる方法を優先する
    - CI / ユニットテストがあればそれで十分。CI が自動実行される場合でも「このテストが通る」程度の言及はしてよい
    - grep、diff、ファイル内容の直接確認など、決定的に検証できる手段を使う
    - 「Claude に質問して回答を確認」のような非決定的な方法は避ける
- コマンド結果をエビデンスとして載せる場合は Bash tool で実行し、出力をそのまま転記する。テキストとして生成しない
    - 複数コマンドがある場合はスクリプトにまとめて一括実行し、stdout を貼る
    - Claude 等で実行した結果には実行者がわかるラベルを付ける（例: `(Claude 実行)`）
    - Claude が実行した結果であってもチェックボックスは `[ ]` のままにする。PR authorが結果を確認してチェックを入れる
