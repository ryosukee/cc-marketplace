# セッション振り返りの手順

セッションで得た学びの明文化だけを扱う。作業状態の棚卸しと次セッションへの
引き継ぎは debrief と handover が担当する。

## 1. 候補を洗い出す

会話を時系列ではなくテーマで見直し、繰り返しうる失敗、実害、判断基準、
機能した／しなかった手順を抽出する。今回使った rule・skill・agent の指示が
実際の挙動と合っていたか、既存文書の陳腐化や変更の反映漏れも確認する。
記憶に蓄積した知見のうち、恒常的な指示に昇格すべきものも調べる。

## 2. 優先度と反映先を決める

| 優先度 | 基準 | 対応 |
| --- | --- | --- |
| A | 実害があり、将来再現しうる | 強く推奨 |
| B | 再利用価値が高い | 推奨 |
| C | あると便利だが、実害は小さい | 任意 |
| D | 一度きり・無関係・自明 | 不要 |

発生回数ではなく、判断を再利用できるかで決める。一回でも実害があり
パターン化できるものは候補にする。偶然性が高いものは明文化しない。

適用対象に応じて、対象パスを限定できる制約は project rule、特定タスクの
知識や手順は skill、agent の振る舞いは agent 定義、プロジェクト全体の前提は
project instructions に置く。既存ファイルで足りるなら新規ファイルを増やさない。
Claude Code 専用か Codex 専用かも判断し、一方にしか通用しない指示を
共通の文書に混ぜない。

## 3. ユーザーが扱う項目を選ぶ

候補の**項目名と優先度だけ**を一覧で示す。原因分析や文案をこの一覧に
詰め込まない。`draft-tasks.md` を読み、今回対話すると決めた項目を
現在の draft の「セッション内タスク」に記録する。

## 4. 各項目を自己検証し、対話する

項目ごとに、文案を提示する前に次を確認する。

- 行動だけでなく、その判断と前提まで原因を掘り下げたか。
  「X をしたから X するな」だけの規範にしていないか。
- 元の失敗場面でその指示を読めば、実際に誤った判断を止められるか。
- その事例だけに狭まりすぎず、何にでも当てはまるほど広すぎないか。
- このセッションを知らない人にも、何をすればよいか分かるか。

検証に通らなければ文案を直す。二回直しても通らなければ、その旨を伝えて
対話する。提示するときは、実際に起きたこと、本来の判断、失敗の原因、
反映先と文案を示す。前三者は判断材料であり、規範本文へ混ぜない。

一度に複数の判断を長文で並べず、一項目ずつ判断できる形で提示する。
各項目の対話開始時に `[x/n] {項目名}` で進捗を示す。
CodingAgent 別の入口に複数項目の提示方法があればそれに従う。
ユーザーの承認を得た項目だけ、その場で反映する。結果が決まるたびに
draft の状態を更新する。

「やらない」は却下であり、未完了として次セッションに戻さない。
「今回はやらない」だけを先送りにする。却下した候補を再提案しそうなら、
handover の「却下と決めたこと」に決定を残す。

## 5. 変更の確定方法を確認する

全項目の対話と反映が終わったら、コミット、PR、保留などの確定方法を
ユーザーに確認する。承認された範囲を超えて変更しない。
