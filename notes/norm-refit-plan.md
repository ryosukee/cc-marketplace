# norm-refit: 実装計画

norm-refit をどの順で進めるかの正典。何をどこまでやるか、依存が何か、次に何をするかは
この文書だけを見れば分かる。

役割の分担は次のとおり。この文書に決定の経緯や決め手を書かない。進行状態も書かない。

| 置き場 | 持つもの |
| --- | --- |
| この文書 | 段階の定義、作業の一覧と順序、依存、待ち条件 |
| [norm-refit: 確定事項メモ](./norm-refit.md) | 何をどう決めたか、決め手、出典 |
| task list | いま何に取りかかっているか（常に 1 件だけ） |

task list には、この文書の見出しを指す task を 1 件だけ置く。作業が進んだら
その 1 件の参照先を次の見出しへ差し替える。作業の中身を task に書き写さない。

## 全体像

| 段階 | 中身 | 到達点 |
| --- | --- | --- |
| 0 | 着手前の整理 | 記録の食い違いが無くなり、対応表が揃う |
| 1 | コア実装（PR 4 本） | norm-refit の実装が終わる |
| 2 | T4 のコア | 凍結を解く判断材料が揃う |
| 3 | T4 の後始末 | norm-refit が完了し、編集凍結が解ける |
| 4 | 実装後に続く 10 件 | 終了条件の外。順に片付ける |

段階 1 と段階 2 は時間軸で重ねる。T4 の設計と決定は実装の成果物に依存しないので、
最初から並走できる。実装の完成を待つのは段階 3 の facet 参照の切り替えだけ。

段階の所要は書かない。台帳にも棚卸しにも見積もりが無く、推定を置くと根拠のない数字が
独り歩きする。並行の切り替えを所要の比較で決められないのも同じ理由。

## 編集凍結

対象は boilerplate 側の norms 全体（100 本）と、実装が統合する汎用執筆分 52 本。
重複が生じるのは 52 本の側で、同じ内容が 2 箇所に存在するあいだ、facet レビューが
読み込む正は boilerplate 側のまま。両方を編集できると、どちらが最新かを判定できなくなる。

- 開始は PR 1 の実文に着手した時点。書き写している最中に元が編集されると、
  差分が不可視のまま PR に載る
- 解除は段階 3 の facet 参照の切り替え時点
- 実効の担保は写し元 commit の記録による。基準点は product-boilerplate の
  `6dfddfc31b326d86c47d496646321551f07e5206`（2026-08-19 記録。`docs/norms/` は
  README を含めて 6 ファイル 915 行、作業ツリーはクリーン）。
  段階 3 の切り替え直前に同じ範囲の差分を取る。差分が出たら凍結が破れているので、
  写しへ反映してから切り替える

台帳は中間期を「一括実装後から T4 完了まで」と定めている。これは 1 PR 前提で書かれた定義で、
分割 PR に合わせて書き直す（段階 0 の対象）。
