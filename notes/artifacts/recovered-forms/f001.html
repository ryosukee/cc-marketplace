設問 2/11 汎用規範の重複の解消方式（Q2）

決めること: 重複 47 グループのうち L1（汎用規範）に関わる分の解消方式。 github-pr / impl-spec / session が関与する重複・矛盾は 47 中 27 グループ （インベントリ台帳で実測。関与数であり、27 の全部が汎用規範ではない）。 残り 20 グループには、rule の要点と正典 skill の間の重複（これも本設問の解消対象）、 媒体固有どうしの重複、外部正典との重なり（Q6 が扱う）が混在する。論点は plugin 設計原則 「plugin は skills / hooks / agents で自己完結する。rule の存在を暗黙前提にしない」 （.claude/rules/plugin-design.md）との折り合い。 確定済みの「別 plugin なら互いを知るべきでない」が禁じるのは、plugin 間の明示参照 （別 plugin のファイルや skill を名指しで読ませる指示）。重複を消すとは、正典 + 常時層（正典の実体と参照機構は Q3 で決める）に寄せて、 各 plugin 内の再実装を削ることを指す。正典が skill の場合（Q3 = A）でも自己完結原則と 両立する理由は、他 plugin が正典を名指し参照せず、読むトリガを plugin の外の常時 rule が持つから。 Q3 = B なら正典は plugin の外に出るため、この論点自体が生じない。

検討して採らない案が 2 つある。(1) marketplace 内 symlink での実体共有 （plugin 間共有の唯一の公式手段）: install 時に cache へ複製展開されるため正典改定に追従せず、 --plugin-dir の開発時には壊れる。(2) 部分統合（重複密度の高い組だけ、 例: japanese-text-writing + claude-user-communication）: 両者の重複は入口判定と要点の再掲で、 一元化（Q2 推奨案）がそのまま解消し、統合しても github-pr 等との重複は残るため解消手段として不十分。

設問 5/11 常時層に置く最小規範（Q5）

決めること: 常時層に規範の実文をどこまで置くか。

背景: 毎ターン起きる場面なのにどの層にも規範が無い欠落が 2 つ特定されている。 「フリーテキストを選んだ後の書き方」と「進捗報告（tool call 間の 1 行）」で、 どちらも数行の返答なので skill の発動（まとまった文章が対象）は期待できない。 一方、既定の system prompt が結論先行・取捨選択・共有文脈なしの読者を前提にした書き方を 毎ターン指示済みであり、規範を 1 つ足すと既存規範の遵守率が下がる方向に働く5。 足すなら system prompt との差分だけを数行に限る。置く場合の実文のたたき台:

進捗報告（tool call 間の 1 行）: 作業の実況ではなく、分かったこと・方針が変わったことだけを書く。
数行返答: 最重要の一文を先頭に置き、次のアクションがあれば明示して終える。

実装条件: たたき台は既定 system prompt の該当節の実文と突合し、 重複する項目（結論先行など）を落として真の差分だけを残す。
