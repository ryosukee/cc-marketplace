norm-refit: 正典の器とタイプ分類の再設計（5 問）

規範改修プロジェクト norm-refit のテーマ T2（執筆規範の正典と入口の設計）の再設計フォーム。 前版 f005 への回答で、正典を skill に置くこと自体の再検討（第 1 回フォーム f001 の Q3 確定の 見直し）と、形式判定より先に生成物のタイプ分類を構造として整理することが指示された。 その方向はターミナルで骨格合意済みで、このフォームは具体案の確定を行う。 確定済み事項の照合先は台帳 notes/norm-refit.md。

結論: 推奨案は、(1) 正典を rules 層（正典 reference 群 + 入口 rule）へ移す （f001 Q3 = skill 案の覆し。配布協調の問題が構造ごと消える）、(2) それに伴い japanese-text-writing plugin は解体、(3) タイプ分類は「種別」と「媒体」の 2 軸に分け、 入口の一次分岐は 3 つだけ、(4) 入口 rule は共通原則を再掲しない 6 項構成で text-output.md、(5) 正典 reference は rules/references/writing/ 配下の 6 ファイル、(6) 外部正典への言及は plugin 内蔵で解消、の 6 点。

決めること: 5 件。

  • 設問 1 正典の器（rules 層への移行と plugin 解体）
  • 設問 2 タイプ分類の構造（2 軸・一次分岐 3）
  • 設問 3 入口 rule の中身と名前
  • 設問 4 正典 reference のファイル構成
  • 設問 5 外部正典への言及の解消方式（T5）

読み方: 設問 1・2 が構造の決定で、設問 3〜5 はその具体化。 各設問セクションは判断材料 → 設問の順で自己完結する。

設問 1/5 正典の器: rules 層へ移す（f001 Q3 の覆し）

f001 Q3 では「skill 正典 + 入口 rule」（A 案）が「rule 二層」（B 案）に勝って 確定した。当時の決め手は 2 つ: B 案は claudeMdExcludes というマシンごとの設定を 要すること、symlink 越えの動作が未実測なこと。この 2 つはテーマ T6（一時メモ運用）の実装で 両方消えた。paths 除外方式（実在しないパターンを frontmatter に書き、reference を 常時ロード対象から外す方式）は設定不要でファイルに閉じ、 symlink 越え・サブディレクトリ・rule からの相対リンク解決まで実測済み。 比較をやり直した結果が表 1。決め手は「配布協調」の行で、rules 層案では rule と正典が同一経路（symlink + git pull）で原子的に更新されるため、問題が構造ごと消える。 表の記号は、優位 = ◎、劣位 = △、同等 = 無印。

※ L1 / L2 = f001 Q1 で確定した規範の層分け。L1 = 媒体を問わず全生成物に共通の 横断規範（今回の正典の中身）、L2 = 媒体固有の規範（各 plugin が持つ）。

skill 側に残る固有の利点は description による自律発動だけだが、実測では description は 常時の指示として効かず（発動時のみ有効）、主経路はどのみち入口 rule のトリガ文になる。 残るリスクは paths 除外がハーネスの挙動に依存する点（将来壊れると reference が 常時ロードに戻り、エラーなしで context が太る）。採用時は claude-known-issues 台帳 （既知バグ・制約の台帳。Claude Code 更新のたびに突合 agent がチェックする）にエントリを立て、 この無症状故障の検知経路を確保する。

採用した場合の含意: japanese-text-writing plugin は解体する。分類別 references 5 本は 種別規範（正典の一部）として rules 層へ移設し、plugin・marketplace エントリ・ 関連参照（README / CLAUDE.md / textlint-plan 等）を整理する。

skill 維持を選んだ場合に引き受けるもの（f005 設問 3 で提案し、未回答のまま保留中の 運用規約 3 点）: (1) skill 名の恒久固定（改名時は旧名を誘導だけの中身で 1 版残す）、 (2) rule と plugin の対になる変更は同一 PR + release 手順まで一連で実行、 (3) rule に依存先 plugin 名を明記し、skill 不在に気づいたらユーザーへ指摘。 対応する不整合は、skill 名変更での空振り / 対変更の版ずれ / 未インストール環境での空トリガ、 の 3 種。維持を選んだ場合はこの規約案を別フォームで再提示して確定させる。

設問 1/5（正典の器）

設問 2/5 タイプ分類は 2 軸に分け、入口の一次分岐は 3 つ

f005 補足の指示（形式判定の前にタイプの特定と構造整理）への設計。 生成物の分類を「何を生成するか（種別）」と「どこへ出すか（媒体）」の 2 軸に分ける。 決め手は、媒体側にはそれぞれ発動主体が既にあり（md = markdown-formatting rule の paths、 PR = github-pr、spec = impl-spec、handover = session、HTML = html-communication）、 入口に媒体を列挙すると削ろうとしている重複が入口で再発すること。

種別軸の一次分岐は 3 つに固定する。

  1. 数行の応答・進捗報告 → 何も読まない。常時 rule の最小規範だけで完結
  2. まとまった文章（複数段落の文書・調査まとめ・長い返答）→ 正典を読む。 種別の細分（参照 / 判断 / 論文 / 解説 / 読み物の現行 5 分類）は正典内の判定表が担う
  3. 確認・質問 → 少数ならフリーテキスト（常時 rule の範囲）、 多数・入り組む場合は HTML フォーム（html-communication）へ

入口が持つ媒体分岐は HTML 提示の 1 つだけ（ファイルパスを持たない出力で唯一、 他に発動主体が無いため）。共通 rule は L1 共通原則（取捨・構成・文レベル・用語）で、 「まとまった文章」の全種別に共通に掛かり、種別規範はその上の差分だけを持つ。

粒度の方針: 一次分岐 3 は固定し、種別の細分は正典内判定表に置いて正典改定だけで 増減できるようにする。判定表には「迷ったら判断文書の規範」のフォールバックを持たせて 分類不能を作らない。深い分岐を常時 rule に書かないのは、常時層の総量制約と、 「規範を 1 つ足すと、既存規範の遵守率が下がる方向に働く」という調査結論 （notes/research-ledger.md の 1 節）が根拠。

設問 2/5（タイプ分類の構造）

設問 3/5 入口 rule は共通原則を再掲しない 6 項構成

f005 設問 2 の再設問。器が rules 層になっても中身の骨格は変わらないが、 1 項目めが「形式判定」から「タイプ判定（設問 2 の一次分岐 3）」に置き換わり、 6 項目めの参照先が skill から正典 reference への相対リンクになる （設問 1 で skill 維持を選んだ場合は 6 項目めが skill 発動のトリガに戻るだけで、 他 5 項は器に依存しない）。統合対象は常時 rule 2 本 （japanese-text-writing.md と user-communication-format.md）。 f001 Q4 の確定は「中身 4 項目案（形式判定 / 数行返答の最小規範 / 正典を読むトリガ / 共通原則の要点）を採用」（台帳の記録）。このうち「共通原則の要点」は 現行 rule の二重管理を再生産するため、フォーム f004（取捨選択規範の再設計）で確定した 実文群に置き換えることを提案する。構成案:

  1. タイプ判定（一次分岐 3。まとまった文章 → 正典へ、確認多数 → HTML フォームへ）
  2. 取捨の判定基準 B（B は f004 の選択肢ラベル。確定した改稿版で、骨子 = 情報の取捨は読者の判断か確信度を変えるかで決め、表現と配置は処理労力で決める。 理由なく残した情報は誤読を生む）
  3. 生成前手続き 2 点（目的の 1 文 = 読者は何を判断・実行するか + 読者の既知・未知の書き出し）
  4. 保持規則 L1 の 4 項（前提・条件・例外・数値 / 範囲・前提知識の宣言 / 確信度のヘッジ（1 主張 1 つ）/ 読者誘導の道標）
  5. 数行返答・進捗報告の最小規範（f001 Q5 確定。たたき台 2 行程度、自立実文として書き直し）
  6. 正典 reference への参照（相対リンク。通常の ./references/... 形式）

rule のファイル名は、中身をどの案にしても旧 2 名を引き継がず text-output.md を 既定とする（別名の希望は補足欄へ）。

設問 3/5（入口 rule の中身）

設問 4/5 正典 reference は core + 種別 5 ファイル

正典の実体を置く rules 層のファイル構成案。設問 1 で skill 維持を選んだ場合、 この設問は無効（現行 plugin 内の references を維持する）。方針は、共通層 1 ファイル + 種別 5 ファイル（現行 japanese-text-writing の references を移設）で、 notes-format と同じ paths 除外を各ファイルに付ける。

rules/
├── text-output.md          # 入口（常時ロード）。設問 3 の 6 項
└── references/
    ├── notes-format.md     # 既存（T6）
    └── writing/
        ├── core.md         # 共通原則 + 種別判定表 + f004 の効果 4 分類 +
        │                   # 保持規則の詳細 + 文レベル編集規則 + 再掲の条件
        ├── reference-docs.md    # 種別: 参照（移設）
        ├── decision-docs.md     # 種別: 判断（移設 + 検証報告の保持規範を追記）
        ├── academic-writing.md  # 種別: 論文（移設）
        ├── explanatory-writing.md  # 種別: 解説（移設）
        └── narrative-writing.md    # 種別: 読み物（移設）

読む量の設計: 入口 → core.md（共通 + 判定表）→ 該当種別 1 ファイル、の最大 3 段で、 skill 案の「SKILL.md → 分類 reference」と同じ深さ。効果 4 分類 = 読者の頭で何が変わるか （判断・行動 / 疑問の解消 / 誤解の訂正 / 確信度）の分類で、f004 で正典詳細への配置が確定済み。 現行 skill の出典 6 件（frontmatter の sources）は core.md へ移す。

設問 5/5 外部言及は plugin 内蔵で解消する（T5）

f005 設問 4 の再設問（未回答だった。器の変更の影響は受けない）。 外部正典 = product-boilerplate repo の情報デザイン norm ライブラリ（docs/norms/。 S/T/F/V/C は norm の ID 系列）。 f001 Q6 の回答は「そもそも外部 skill への言及がダメなのでは」で、参照しないで済む構成か、 関連 plugin としての組み込みかの再設計が指示された。言及の実測は、html-communication skill （HTML ページ提示 skill）の SKILL.md 1 箇所 + 同 skill の references/facet-review-norms.md （フォームレビューの norm 定義）3 箇所（repo 名指し 1 + norm ID 経由の参照 2）。 決め手は、T4（レビュー機構の再設計）が「生成側 skill が facet / norm を定義」する方向で 進んでおり、norm を plugin 自身に持たせる案がそのまま T4 の前提になること。
