T1（Q8）: なぜ AI 生成文書は冗長で要領を得ないのか

Q8 は成果物の取捨選択を指示する文面（長さ指示の置き換え）を問う設問で、 回答はその手前の根因調査からやり直す指示だった。 フォームのたたき台（書く前の 1 文確定 + 削る基準）は「概ね良いがまだ足りない」。 読者が何も知らない前提での必要十分性や、人間の書き手が無意識・意識的に行っている判断を 真正面から調査し、根因の説明と改善案を出し直す。既存の調査台帳 5 節（writer-based prose 論、 読者知識が執筆に反映されない実験）を起点に、そこで扱っていない領域へ広げる。 Q8 補足の「haiku など低性能モデルに解釈させて理解可能性を検証する」レビュー手段は、 コストが掛かるため成果物の種類ごとの適用として T1 の改善案に含めて評価する。

T2（Q3 補足）: 正典 skill + 入口 rule のゼロベース設計

参照機構は A 案で確定。ただし命名・配置は現行（japanese-text-writing の skill / rule 名）に とらわれず設計し直す。加えてplugin と rule の配布協調を議題化する: 正典 skill は marketplace 経由、入口 rule は repo の rules/ から symlink 配布と、経路が別なので、 入口 rule が指す skill 名の安定性、両者の版ずれ、plugin 未インストール環境で 入口 rule だけが残る状態、の扱いを決める必要がある。

T3（Q2 補足）: 重複の個別判断材料を作る

基本線は plugin 独立性を重視した現状維持で確定。そのうえで、重複 47 グループのうち plugin が関与する 27 グループの明細（どの指示が、どこで、どう重複しているか）を再抽出し、 1 グループずつ「独立性のため残す / 基底 rule の管轄として plugin 側から削る」の判断材料を提示する。 「rule があるから skill には書かない」という個別判断はありうる、が回答の指示。

T4（Q7）: レビューを facet / norm 定義 + op-review に一本化する

検知マトリックスの承認ではなく、ゼロベースの再設計を指示された。方向性は 「生成側の skill が facet / norm を定義していれば、レビューは op-review （成果物を norm と照合して approve / request changes を判定する汎用レビュー skill。 現在は kanban-agent-orchestrator のプロジェクトローカルにある）で統一でき、 文書種別ごとの専用 reviewer（spec-reviewer / handover-reviewer）は不要になるのでは」。 op-review の plugin 化は既存タスク「op-pr-review-assist 設計」の論点に含まれており、 T4 はそのタスクと合流させる。マトリックス自体は分かりやすいと評価されたので、 再設計後の最終形のマトリックスだけをどこかの README に恒久記録する（置き場は T4 で決める）。

T5（Q6）: 外部正典への言及そのものを無くす

フォームの選択肢（転記を削って参照を残す）の前提を覆し、「そもそも外部 skill への言及がダメなのでは」 が指示。html-communication が product-boilerplate の norm ライブラリを名指しする構造をやめ、 参照せずに成立する構成にするか、関連 plugin として取り込むかを設計する。 正典の参照構造の話なので T2 と論点が重なり、T2 の設計フォームに相乗りさせる。

T6（Q11）: 一時メモは 2 層構造で設計し直す

repo 内ファイルの方向は承認。ただし単一の decisions ファイルではなく、 「どのタスクのメモがあるかの一覧」+「タスク・プロジェクトごとのメモ本体」の 2 層にする。 decisions という名前は仰々しいので、一時メモ置き場として名前・場所を設計する。 何も決めないと handover に書いてしまう傾向があるため、この運用を rule / CLAUDE.md / global rule のどれに書くかの判断も含める。

説明 4: スコープは 5 plugin の規範改稿までで、L3 正典の中身は変えない

含む: rules/ の常時層の統合・圧縮（Q4・Q5）、正典 skill の新設（T2 の設計に従う）、 規範を持つ 5 plugin（claude-user-communication / impl-spec / session / github-pr / japanese-text-writing）の規範部分の改稿（T3 の個別判断に従う）、レビュー機構の再設計（T4）、 一時メモ運用の新設（T6）、散文向けの長さ指示の全廃と置き換え（T1 の成果に従う）。

含まない: L3 外部正典（product-boilerplate の norm ライブラリ）の中身の変更、 発動検証ハーネス（導入済み・PR #2 で別トラック）、PR レビュー支援 skill 本体の設計 （既存タスク。T4 と接続はする）、Claude Code 本体・system prompt への働きかけ。

説明 5: プロジェクト名は norm-refit を推奨

今後の html-communication ページの title 先頭に「norm-refit: 」を付け、 一覧でこの改修の文書だと分かるようにする。候補 3 案の比較。決め手は「短さ」と「範囲の合致」 （3 案とも repo の kebab 慣例には合う）。
