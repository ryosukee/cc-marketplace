設問 1/9 処遇表の一括承認

r012 の表 3（重複グループ 47 件の処遇）と 説明 4〜5（重複グループ外の拾い上げ・実装チェックリスト追加分）の 一括承認。設問 2〜9 で個別に確定する論点は含まない。 この承認に新しい方針の決定は入っていない。振り分けに使った判断基準はすべて確定済みの事項で、 今回新しく決めたのは、規範 1 件ずつをどのファイルに置くかという割り当てだけ。

※ 一括承認の範囲 = 確定済みの原則（詳細規範への集約 / plugin 自己完結による残置 / AskUserQuestion 系の削除 / T4 送り）を 47 グループへ適用した割り当て。 確定を覆す判断はこの設問に含めず、すべて設問 2〜9 に切り出してある。

設問 2/9 core に無い汎用規範が 5 件、分散したまま残っている

処遇の過程で「現行の共通原則に無いが、core に 1 回書きすれば重複や欠落が 解消する」規範が 5 件出た。いずれも承認済みの core 構成（現行共通原則 + f004 確定分（取捨の判定基準・生成前手続き・保持規則の実文群）+ 種別判定表）への追加になるため、 まとめて確認する。推奨はまとめて採用。

  • 見出しは内容を特定できる具体的な句にする（DG21）: 現在は参照と解説の 2 ファイルに同趣旨が分散。共通句を core へ移し、種別固有分 （参照 = 見出しだけで目的の節へ到達できる構成、解説・読み物 = 手順だけの見出しと、 結論を言い切って山場を消す見出しの禁止）だけを各所に残す
  • 読者を「あなた」と呼ばない（役割名で書く）（DG30）: AI 口調の禁止の チャット残留群へ追加。読み物の例外（境界に限り可）は種別側に残る
  • 引用は原文から verbatim にコピーし、中略を明示する（DG29）: 現在は論文 reference に しかない。facet レビューで非 verbatim 引用が 6 件検出された実績があり、台帳の作業メモでも 組み込み候補として確定待ちだった
  • 出典リンクは貼る前に参照先を確認する（DG28）: 事前検証の規範としては 現在 github-pr にしかない（markdown-formatting rule にあるのは出典の記法のみ）。 数行の追加で、github-pr 側は再掲として残す
  • 固有名の原則に例外根拠を併記する（DG13）: 「参照不要な固有名は出さない」の原則に 「再開・再現目的の文書では識別子が情報そのもの」という例外判定を 1 文添える （session plugin の引き継ぎ資料規範「具体識別子は省略しない」との方向差の整理）
設問 2/9（core への新規追加）

設問 3/9 skill 廃止で、手段変更時の再確認規範が受け皿を失う

ask-with-choices skill の廃止（確定済み）で、skill 内の汎用行動規範 「実行中に手段が変わったら確認に戻る」が受け皿なく消えることが網羅性レビューで判明した。 実文の骨子: 承認は目的でなく具体的な手段・構成に対して与えられる。実行中にブロッカーへ当たって 手段を変えるなら、その時点で承認は失効しており、実装・状態変更の前に確認へ戻る。 実例（2026-07）: 合意済みの構成が環境制約で不可能と判明した際、代替構成を無断で構築し 永続設定まで書き込んで指摘を受けた。

受け皿の候補は 2 つ。user global rule の propose-before-implement （提案と実装の分離。趣旨が最も近く、常時ロードで全プロジェクトに効く）へ 1 節追記するか、 html-communication skill（確認フォームの運用の一部として）へ移すか。 執筆規範ではないため詳細規範 core は候補にしない。 rule への追記は常時層（全セッションに常時ロードされる rule 群）が 5 行前後増える トレードオフを持つ（常時層の最小化は f007 Q1 の決め手）。 それでも rule を推すのは、この規範は確認フォームを開かない場面（実装作業中の手段変更）でこそ 効く必要があり、skill 配置では届かないため。

設問 3/9（手段変更時の再確認規範の受け皿）

設問 4/9 AskUserQuestion の使用指示が 3 plugin に 35 箇所残っている

AskUserQuestion（Claude Code 組み込みの選択肢提示ツール。レンダリングバグにより 時限禁止中）の使用指示について、確定済みの除去対象は impl-spec（16 箇所、実測）だけだが、 レビューの grep で dotclaude（13 箇所）と mkdocs-setup（6 箇所）にも実在すると判明した。 恒久的に使わないというゴール（フォーム外確定）に対し、ask-with-choices 廃止後は 時限禁止を宣言している同 skill 冒頭の WARNING が消えるため、 残すと禁止の根拠が無いまま使用指示だけが残る。

作業量の実態: impl-spec は文言の削除・書き換えで済むが、残り 2 plugin は それを超える。mkdocs-setup は frontmatter の allowed-tools 変更と、複数選択 （multiSelect）前提の 2 段階選択フローの代替設計が要る。dotclaude は 「4 問ずつに分ける」などツールの仕様に由来する進行規則を含み、確認フローの書き直しになる。 そこで「除去の確定」と「実装の同梱」を分けた 3 案で確認する。

設問 4/9（AskUserQuestion 除去のスコープ）

設問 5/9 一括実装 PR のスコープは台帳内で矛盾している

整合性レビューが台帳内の矛盾を検出した。「norm-refit 全体は最終的に 1 つの PR + 提出前メタレビュー」（2026-08-14 確定。メタレビュー = 提出前に複数観点の 独立レビューを回す規定）と、f007 Q4 の中間期定義 （一括実装 PR の後、T4 完了までは boilerplate 版が facet 注入の正）は両立しない。 中間期が存在する以上、一括実装 PR は T4 完了前に出るからだ。両確定は同日のため 台帳から前後は断定できないが、f007 Q4 は補足質問への回答（詳細は T4 で詰める）まで 確認済みで、粒度も細かい。どちらを選んでも一方の確定を覆すため、対称に確認する。

設問 5/9（一括実装 PR のスコープ）

設問 6/9 表規範の「最小限」の解釈が 2 通りある

f001 Q1 の確定（md 文書の表の書き方の最小限を markdown-formatting rule （以下 MF）へ移設する）の「最小限」の解釈が 2 通りある。参照 reference には表の規範が 2 つあり、 セルの書き方（セルは短い判定値にする = DG23）は文句なく移設対象だが、 使い分け（比較・対応は表、並列は箇条書き = DG22 の参照側）まで含むかが読み切れない。 MF は常時ロードの rule なので、広く解釈すると常時層が増える。

設問 6/9（表規範の移設範囲）

設問 7/9 問いの回収の規範は、論文と読み物で逆向きの例外を持つ

「立てた問い・送った論点は回収する」という同趣旨の規範が、論文 （全回収・回収しない伏線の禁止）と読み物（明示回収しつつ、最後に一つだけ開いたまま 残してよい）で逆向きの例外を持つ。共通化すると読み物の例外（緊張の設計の中核）が消えるか、 論文側に不要な緩和が混入する。T3 は「同趣旨の別規範」として両ファイルに並立残置し、 「規範の実体は 1 箇所」の例外として台帳に理由を記録する案を推す。

設問 7/9（問いの回収の扱い）

設問 8/9 太字上限の正を 1 箇所にすると、HTML 媒体に届かなくなる

太字は論理の要所に限り一節に一、二箇所まで、という上限規範が markdown-formatting rule（MF）と読み物 reference の両方にある。MF は md ファイル限定を自称する rule のため、 MF だけを正にすると、HTML 本文で書く読み物には上限規範が届かなくなる （f006 Q2 の 2 軸設計（種別 × 媒体）の媒体軸に穴が開く）。妥当性レビューは、 読み物側にも数値を残す意図的二重化（その旨を明記）を推した。

設問 8/9（太字上限の扱い）

設問 9/9 idea-hub 側の Q81 条項更新が、どのスコープにも未割当

f007 Q4 で、情報デザイン norms の複数用途条項の「正の向き」を変更する （汎用分の正は執筆詳細規範側にする）と確定した。この条項の記録元は idea-hub リポジトリの 決定台帳（Q81）で、そちらへの反映作業がまだどのスコープ（一括実装 / T4 / 単発作業）にも 割り当てられていない。他リポジトリの文書の更新は norm-refit の範囲外のため、 実施はいずれにせよ idea-hub 側のセッションかユーザー経由になる。
