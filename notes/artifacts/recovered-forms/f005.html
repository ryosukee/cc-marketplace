規範改修プロジェクト norm-refit の設計フォーム第 1 回（f001）の Q3 で、 「正典 skill + 入口 rule」の参照機構が確定した。正典 skill = 執筆規範の全文を持つ唯一の置き場、 入口 rule = 常時ロードされて正典 skill へ誘導する薄い rule、という 2 層構成。 あわせて、命名・配置はゼロベースで設計し直すことと、plugin と rule の配布協調の議題化が 指示された（テーマ T2。T 番号は確定事項台帳 notes/norm-refit.md のテーマ番号）。 外部正典への言及を無くす再設計（T5）もこのフォームに相乗りさせる。 現状の実測を踏まえた設計案を 4 問で確認する。確定済み事項の照合先は同台帳。

結論: 推奨案は、(1) plugin / skill 名はゼロベース比較の結果として現名 japanese-text-writing を維持し中身を正典に全面改稿、(2) 入口 rule は共通原則を再掲しない 6 項構成の 1 本に統合、(3) 配布協調は機構を作らず運用規約 3 点で担保、 (4) 外部正典の言及は使用分を plugin 内へ自立内蔵して解消、の 4 点。

設問 2/4 入口 rule の中身

統合対象は常時 rule 2 本（japanese-text-writing.md と user-communication-format.md）。第 1 回フォーム（f001）の Q4 で 「1 本に統合し、中身 4 項目案 = 形式判定 / 数行返答の最小規範 / 正典を読むトリガ / 共通原則の要点、を採用」と確定済み。このうち「共通原則の要点」は、 現行 rule の二重管理（表 1 の ★ 行）を再生産するため、 フォーム f004（取捨選択規範の再設計）で確定した実文群に置き換えることを提案する。統合 rule の構成案:

  1. 形式判定（フリーテキストか HTML ページか。ask-with-choices = 選択肢形式の確認 skill への分岐は廃止で消える）
  2. 取捨の判定基準 B（f004 確定の改稿版。骨子 = 情報の取捨は読者の判断か確信度を変えるかで 決め、表現と配置は処理労力で決める。理由なく残した情報は誤読を生む）
  3. 生成前手続き 2 点（目的の 1 文 = 読者は何を判断・実行するか + 読者の既知・未知の書き出し）
  4. 保持規則 L1 の 4 項（前提・条件・例外・数値 / 範囲・前提知識の宣言 / 確信度のヘッジ / 読者誘導の道標）
  5. 数行返答・進捗報告の最小規範（f001 Q5 確定。たたき台 2 行程度、自立実文として書き直し）
  6. まとまった文章は正典 skill を読むトリガ

共通原則の実文は正典 skill だけが持ち、rule 側には再掲しない。 rule のファイル名は、中身をどの案にしても旧 2 名を引き継がず text-output.md を 既定とする（対象が「ユーザー向けテキスト出力全般の入口」のため。別名の希望は補足欄へ）。

設問 3/4 plugin と rule の配布協調

入口 rule（repo の rules/ から symlink 配布、git pull で更新、次セッションから有効）と 正典 skill（marketplace 経由、update 手順の実行後に有効）は配布経路と反映タイミングが別で、 次の 3 つの不整合が起こりうる。

  1. 指す skill 名の変更で rule が空振りする
  2. 対で変えた rule と skill の内容の版ずれ
  3. plugin 未インストール環境で rule のトリガだけ残る

機構（hook 等）は作らず、不整合 1〜3 に 1:1 で対応する運用規約で担保する案を推奨する。

  • 規約 1（不整合 1 に対応）: 正典 skill の名前は恒久固定。やむを得ず改名する場合は、 旧名 skill を新名へ誘導するだけの中身にして 1 版残してから消す
  • 規約 2（不整合 2 に対応）: rule と plugin の対になる変更は同一 PR で行い、release 手順 （bump → push → marketplace update → plugin update）まで一連で実行する
  • 規約 3（不整合 3 に対応）: rule 本文に依存先 plugin 名を明記する。 skill が見つからない状態に気づいたら、作業を止めずにユーザーへ 1 行で指摘する
