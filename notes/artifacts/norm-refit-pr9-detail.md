### A-1. 分類の定義と数え合わせ

条項の単位は「節」または「独立して効く箇条書き 1 項目」。節が複数の分類にまたがるときは分けて数える。
節の冒頭にある適用範囲の宣言文（`authoring.md:10`、`skill-authoring.md:10`、`agent-authoring.md:10`、
`claude-component-authoring.md:10-11`）は条項ではないので数に入れない。

| 分類 | 意味 |
| --- | --- |
| 採用 | 新設・改訂する 5 ファイルのどれかに置く |
| 重複 | cc-marketplace の既存規範が同じことを持っている。置かない |
| 不採用 | boilerplate の構成に依存するか、前例（ccm-f041）で採らないと決着している |
| 実装時の判断 | 採否が未確定。H の未特定に既定案付きで送る |

````markdown
# Claude 向け文書の書き方

Claude が指示として読む文書の、種別の選び方と、種別を問わず共通する命名・条項・参照・why・改訂を定める。
新規作成と改訂の両方でこの規範に従う。

## 種別を選ぶ

上から順に判定し、最初に当たった種別で作る。

1. 特定のファイルパターンに対する宣言的な制約・判断基準か → rule。
   どのプロジェクトでも効かせるなら user global rule、そのプロジェクトだけなら project rule
2. ファイルパターンに絞れない知識・規約か → 参照知識 skill
3. モデルの判断を挟まず必ず実行される必要があるか → hook。
   rule と skill はモデルへの指示なので従われない可能性が残り、強制は hook だけができる
4. 独立したコンテキスト・tool 制限・model 指定で実行させたい specialist か → agent
5. 手順と参照資材を伴う作業か → 作業手順 skill
6. どれにも当たらないプロジェクト全体への指示 → CLAUDE.md

知識・規約は、paths で絞れるなら rule に置く。rule は paths の一致で確実に載るのに対し、
参照知識 skill は description のセマンティックマッチに依存するので発動が不確実で、適用範囲も曖昧になりやすい。

## 種別の付け替え

種別のあいだに上下関係はない。内容がどの発動条件に合うかが変わったら付け替える。

- 参照知識 skill → rule: 内容が特定の paths パターンに対応づけられると判明したとき
- rule → 参照知識 skill: paths パターンでは広すぎるか狭すぎるとき、
  またはファイルを触らない作業（調査など）でも必要なとき
- 付け替えたら元の種別から該当部分を削除する。両方に残すと片方だけが更新される

## 命名

- ファイル名は内容を表す kebab-case の名詞句にする (例: `markdown-formatting.md`)。
  分類コード・略号を新設しない

## 条項の書き方

- 条項にするのは表面の行動ではなく、その行動を生んだ判断の構造にする。
  「X をした → X するな」の形は、場面の形が変わると適用できない
- 適用範囲を「本当にそれを必要とする対象」に絞る。広い対象へひとまとめに適用しない
- 何にでも当てはまって判断基準にならない条項になっていないか確かめる。
  誰でも同意するが行動を変える基準にならないなら広すぎる
- 補足説明を消しても適用範囲と判断が変わらないなら、元になった場面の再説明なので消す
- 判定基準は、読み手がその場で真偽を判定できる形で書けるときだけ置く。作れないなら無理に置かない
- 具体事例を書いてよいのは、抽象的な条項の例として列挙する場合と、
  致命的で具体的な禁止指示が必要な場合の 2 つだけ。
  why: 具体事例をそのまま書くと、その事例にしか効かない。
  同じ根本原因の別パターンが来たときに条項が機能しない

## what と why を pair で書く

条項には「何をする / しない」と「なぜそうするか」を pair で書く。
what だけでは、条項が想定していない場面で判断材料が足りなくなる。
why があれば条項の本質を理解した上で、未知のケースにも適用できる。

why の書き方:

- その条項が無いと何が壊れるかという本質的な理由を書く
- 現在形で書く。いま何が成り立つかだけを述べ、何があったかは書かない
- 主語を条項の対象に取る。書き手や過去のセッションを主語にしない
- 日付付きの具体事例を書かない。事例は書いた時点の場面に縛られ、場面の形が変わると
  条項を支えなくなる。事例から抽出した構造だけを理由として残す

判定基準: 書いた why を過去形にできるか。できるなら経緯が混ざっている。
「〜が起きた」「〜していた」「〜に変えた」と書ける文は why ではなく履歴で、
git 履歴と commit message の担当になる。

## 書かないもの

指示でない文は、読み込まれた分だけコンテキストを消費し、条項の密度を下げる。次のものを書かない。

- 実際のコードやディレクトリを見れば分かる情報。ディレクトリ構成の転写、
  関数のシグネチャ一覧、ファイル数、コード行数、実コードのコピーが対象。
  二重管理はメンテ負荷と乖離リスクを生む
- 特定インシデントの調査状況や修正進捗（「root cause 未特定」「次回検証予定」「暫定 workaround」等）。
  状態の追跡は、進捗の記録を目的とする文書で行う

コードサンプルは、原則だけでは正しいコードを書けない場合のみ、原則を示す最小限の擬似コードとして載せる。
載せた時点で実コードとの同期を維持する義務が生じる。この義務を負いたくないなら載せない。

workaround を手順に組み込む場合は、一時的であることを示す注記ではなく手順として完結させ、
状態が変わったら手順ごと削除する。

## 諦めルールの前に root cause を調べる

「失敗したらリトライせず停止」「タイムアウトしたらスキップ」等の諦めルールを書く前に、root cause を調査する。

- 失敗の具体的な log・error を読み、再現条件を特定する
- 原因が分かってから、修正するか明確な workaround として文書化する
- 調査しても原因不明の場合のみ、「原因不明。調査ログ・再現手順付きで停止」と書く

why: workaround をそのまま条項にすると、解決可能な問題が隠蔽される。

## 文体

定義形で書く。「〜する」「〜を読む」「〜しない」の形にし、依頼形（「〜してください」）を使わない。
依頼形は丁寧さの分だけ語が増え、守るべき内容と依頼の言い回しが混ざる。
どこまでが定義でどこからが言い方かの境目も曖昧になる。

## アンチパターン節の書式

アンチパターンを列挙するときは 2 カラム表で書き、両カラムとも肯定文（例: 「〜する」）で統一する。
否定文と肯定文が混在すると、どちらが推奨か解釈が曖昧になる。
カラム名が役割を分けているので、中身は肯定文だけで伝わる。

```markdown
| アンチパターン | 代わりにどうするか |
| --- | --- |
| 太字見出しで段落を区切る | サブセクションか箇条書きのネストにする |
```

## 参照

- 自動ロードで既に載る文書に言及しない。paths が一致する rule と常時ロードの rule は、
  対象ファイルの編集時点で読み込まれているので、言及は重複になる
- 外側の構造に言及しない。「この文書は X から参照される」「Y から起動される」のような呼ばれ方も、
  「共通原則の上にこれを重ねる」のような層の関係も書かない。
  どの文書を読ませるかの誘導は、入口・呼び出す側が持つ
- 読み手を辿らせる責任がその文書にあるとき（入口 rule、呼び出す側の skill）は、
  自動ロードされない参照先への参照を書く

## 改訂

- 文書自身を書き直すとき、その文書の既存記述を書き直しの根拠に使わない。
  判断根拠は実態（コード・実測・一般原則）から取る。
  既存記述に誤りがあるとき、それを根拠にすると誤りが「そう書いてある」という権威で固定化する。
  why: 書き直しの対象になっている時点で、その文書には実態に合わない記述が
  含まれている疑いがある。直すモードでは、まず文書の側を疑う
````

```markdown
## 種別を判定してから書く

skill には 2 種別ある。書き始める前にどちらかを決める。
判定基準: 読み手にさせたいことが作業の実行なら作業手順 skill、知識の参照なら参照知識 skill。
公式のドキュメントでは、参照知識 skill が Reference content、作業手順 skill が Task content にあたる。

参照知識 skill の名前には `ref-` prefix を付け、参照資材は skill ディレクトリの `references/` 配下に置く。
どちらも公式の仕様ではなく、この規範が定める慣習。

## frontmatter

- 書けるフィールドは公式の一覧を引いてから決める。手元で動いているという理由だけで書かない
- 既定のままでよいフィールドは書かない。既定値を明示しても挙動は変わらず、
  既定が変わったときに追従が要る
- 参照知識 skill は `user-invocable: false` にする。ユーザーが直接呼ぶ入口ではなく、
  description による自動発動だけで使われるため、ユーザー向けのコマンド一覧から外す
- 作業手順 skill は `user-invocable` を指定しない。既定のままユーザーが呼べる

description は skill が発動するかを決める。次の 4 つを守る。

- 「〜に関する skill」のような受け身の要約ではなく、発動条件を能動的に書く
- 対象 skill の機能だけを書く。他 skill との関係や補完関係を含めない
- 自動で発動させたい skill は、発動点（どの作業のどの時点で読むか）と、
  発動させたい場面の言い回しを書く。読み飛ばされない強さで書く
- 用途を特定の操作（レビュー・実装等）に限定しない。同じ知識はどの操作でも参照される

## 決定論的な手続きはスクリプトに出す

作業手順 skill の中で、入力から出力が一意に決まる手続きは、本文に手順として書かずにスクリプトへ出し、
SKILL.md からはその実行を指示する。

判定基準: その手順を 2 回実行したとき、判断で結果が変わりうるか。変わらないならスクリプトにできる。

- 対象になるもの: ファイルの収集・整形・集計、決まった順序でのコマンド実行、形式が決まった出力の生成
- 対象にならないもの: 読んで判断する、案を出す、優先順位を決める

why: 決定論的な手続きを自然言語で書くと、実行のたびに解釈の揺れが入り、結果が再現しない。
トークンも毎回消費する。

## 呼び出し元を問わず動かす

作業手順 skill は、ユーザーが直接呼ぶ場面と、別の skill やセッションが呼ぶ場面のどちらからも起動する。
どちらでも動く形にする。

- 呼び出し側に固有の概念（工程名・直前の工程の成果物等）を前提にしない。
  「前工程の成果物」のような呼び出し元前提の語を避け、呼び出し元を問わない表現にする
- 入力は最小限の必須項目と、任意のコンテキスト情報で構成する
- 任意項目が無くても基本機能は動くようにする。精度は下がってよい

## 文体

作業手順 skill は、H1 直後の導入文も各ステップも定義形で書く。
導入文は skill 全体が何をするものかを述べ、ステップはその中の 1 手順を述べる。役割は違うが文体は同じ。

- OK: 「与えられた調査対象を調査し、構造化されたレポートを生成する」（導入文）
- OK: 「Read で調査対象を読む」（ステップ）
- NG: 「この skill は調査作業を支援します」（skill 自身を語っていて、何をするかの定義になっていない）

参照知識 skill の本文は宣言的に知識を書く。指示形や手順のステップを持たない。
```

### C-5. `rules/agent-authoring.md`（新設）

6 義務は `notes/norm-refit.md:2131-2134` の確定。節名を固定しないので、
「次の 6 つを書く」の形で列挙し、書き方の細目は各項目の下位階層に置く。

```markdown
---
paths:
  - "**/agents/*.md"
---

# agent の書き方

agent（独立したコンテキストで動く subagent）の定義ファイルの、ファイル形式・frontmatter・
冒頭に書く責務・入出力の書き方を定める。新規作成と改訂の両方でこの規範に従う。

## ファイル形式

1 agent 1 ファイル。ファイル名は agent 名と一致させる（agent `code-review` なら `code-review.md`）。

## frontmatter

- 書けるフィールドは公式の一覧を引いてから決める。手元で動いているという理由だけで書かない
- `tools` は責務の遂行に必要なものから逆算して選ぶ。
  必要な tool が無いと、agent は下位の手段へ黙ってフォールバックし、指示した調べ方が効かない

## 冒頭に責務を書く

agent 定義の冒頭に、次の 6 つを書く。節に分けても地の文でもよく、節名は固定しない。
6 つのどれかが書かれていない定義を作らない。

- ゴール: この agent が達成すべきこと。達成できたかを読み手が判定できる形にする。
  description は発動条件を書く場所なので、ゴールの代わりにはならない
- やること: 具体的な作業内容
- やらないこと: 責務外の作業を why 付きで列挙する。
  「やりたくなるが踏み込むべきでない」操作を明示する
- 詰まった場合: 問題に当たったときの行動（差し戻す / 報告する）。
  判定を偽らない。沈黙して成功と紛れる報告をしない
- 完了報告: 「プロセスが完了した」と「成果物が期待を満たしている」は別の判断で、両方を分けて書く
    - プロセス結果: 検査が通った、対象を全件読んだ、といった事実
    - 品質判断: 成果物が期待する基準を満たしているかの評価
    - NG: 「検査が全件通ったので完了」（プロセス結果を品質判断にすり替えている）
    - OK: 「検査は全件 PASS。ただし 2 件は基準が対象を捉えておらず、品質は確認できていない」
- 確かめた範囲: 報告のうち、実際に確かめたことと確かめていないことを分けて書く。
  判定基準: 報告の各文について、何をどう確かめたかを 1 文で書き出せるか。書き出せないものは確かめていない

why: 冒頭に責務の全体像が無いと、手順の途中で責務を拡大解釈する。
「やらないこと」が無いと、関連する作業に踏み込んでコンテキストとターンを浪費し、本来の責務がおろそかになる。
プロセスの完了を成果の品質と混同すると、壊れた成果物が「完了」として報告される。

## 入力と出力を明示する

- どんな情報を受け取り、何を返すかを書く
- 手順は具体的に書く。実行するコマンド、読むファイル、判断基準を書く
```

### C-6. `rules/claude-md-authoring.md`（新設）

```markdown

  - "CLAUDE.md"
---

# CLAUDE.md の書き方

CLAUDE.md に何を書き、何を書かないかと、更新の時期を定める。

## 役割とサイズ

CLAUDE.md はセッション開始時にコンテキストへ読み込まれるプロジェクトガイド。
コードの書き方ではなく、プロジェクトの構造・ビルド方法・ドメイン知識を伝える。

200 行以下に収める。超える場合は rule に分離するか、`@path` import で本文を外に出す。

why: 常時コンテキストに読み込まれるため、長いほどコンテキストを消費し、指示の遵守率が下がる。

## 書くもの・書かないものの判定

判定基準: プロジェクトの事実を伝える記述は CLAUDE.md、作業の仕方を課す規範は rule、
機能の仕様は設計ドキュメントに置く。

書くもの:

- プロジェクト概要（1〜2 行）と技術スタック
- ビルド・起動コマンドと検証コマンド (lint / test)
- ディレクトリ構成の概要
- ドメインモデル・ドメイン用語の概要
- 環境構成（開発 / 本番 / CI の違い）
- 既知の制約・注意事項
- 開発フローの概要

書かないもの:

- 言語・フレームワーク固有のコーディング規約
- テスト規約の詳細
- コンポーネント・モジュール設計の詳細
- 機能仕様・画面フロー・UI 挙動

## rule との重複を作らない

rule に詳細がある内容は、CLAUDE.md には概要 1〜2 行だけを書く。
設計ドキュメントに詳細がある内容は、概要 1〜2 行とリンクを書く。同じ内容を両方に書かない。

why: 重複すると片方だけ更新されて陳腐化し、矛盾した指示になる。

## 更新の時期

次の変更をしたら、同じコミットで CLAUDE.md も更新する。

- ドメインモデル・スキーマ・ドメイン用語が変わったとき
- ビルド・検証コマンドが変わったとき
- rule・skill・agent の構成が変わったとき

why: 記述とコードが乖離すると、コードベースを誤解した実装につながる。
```
