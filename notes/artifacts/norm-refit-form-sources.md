repo 内のファイルなら git が持つので消えない。台帳の出典はこの文書の見出しを指す。

## 回答が含まれない理由

生成ページは回答を保存しない。入力は端末の localStorage にだけ残り、HTML には入らない。
したがってここに写せるのは設問と判断材料までで、どれが選ばれたかは台帳の結論行が持つ。
両方を合わせて 1 件の記録になる。

### 説明 3 分割を縛る制約は 3 つ

入口 rule の圧縮と詳細規範の新設は同一 PR。`rules/` は symlink で即時反映されるため、入口 rule から共通原則を削った時点で詳細規範が入っていないと、全プロジェクトで規範が消えます。分割の最大の禁じ手です。

rules 層の PR を plugin 側より先に出す。rules は即時、plugin は version bump と update を経て反映されます。逆順にすると参照切れが 2 種類生じます。

UC の削除が先、ask-with-choices の削除が後。`rules/user-communication-format.md` が skill を名指しで参照しているので、逆順だと存在しない skill を指す区間ができます。

逆に、rules 層の PR を先に閉じておけば、plugin 側が update されるまでの区間は「古い plugin が旧規範を持つ」だけで参照切れになりません。時間差そのものは害になりません。

## ccm-f018 実装: 除外トークン・一次情報 rule・破損検知

タイトルは「norm-refit 実装: 除外トークン・一次情報 rule・破損検知」。設問 3 件。

### 冒頭

前のページ（f017）の 7 問のうち 5 問は確定した。残る 2 問（除外トークンの値、primary-sources-first の処遇）と、補足で出た検知の仕組みを扱う。

### 説明 1 除外トークンにランダムが入っている

現在の値。この 1 箇所だけで使われています。

引用（`rules/references/notes-format.md` 冒頭）:

```
---
paths:
  - "zzz-never-match-k4q7x"
---
```

末尾の `k4q7x` はランダムです。「絶対にマッチしない」ことを担保する意図で付けたものですが、実在しないファイル名であれば何でもマッチしないので、ランダムである必要はありません。

同じ値を 5 ファイルにコピーする運用にすると、ランダム部分が「この値には意味がある」「ファイルごとに変えるべき」という誤読を生みます。読んだ人が由来を探しても何も出てきません。

置き換え案は `never-match-reference-only` です。マッチしないことと、このファイルが reference 専用であることの両方が値から読めます。

この rule 自身も移設対象（`rules/decision-record/references/` へ）なので、値を変えるとしてもファイルには他の理由で触ります。追加のコストはありません。

### 説明 2 一次情報 rule と core は正面から衝突していない

引用（`rules/primary-sources-first.md`「適用場面」節の末尾）:

> 判定基準: その記述を「たぶんこうだ」と思って書いたなら、まだ裏を取っていない。既存実装・公式ドキュメント・変更履歴のどれかで確認してから書く。確認できないものは「未確認」と明示する。

引用（同「探索順序」節）:

> 1. 手元の repo (ghq_root 配下): 対象そのものの実装・docs・git 履歴
> 2. registry・台帳類: dotclaude registry 等の参照 repo リスト
> 3. 過去セッションの成果物: handover、設計ドキュメント、transcript
> 4. ここまでで足りないものだけ Web 検索・公式ドキュメントで調べる
>
> git 履歴も一次情報に含める。過去にどう判断してなぜ変えたかの記録は、現 HEAD に無いドキュメントでも `git show <rev>:<path>` で読める。

引用（japanese-text-writing skill「事実・意見・不確実性」節）:

> 事実と意見（解釈・評価）を文単位で区別する。意見は意見と分かる形で書く
> 数値・性能・実績には「実測」か「推定（未実測）」かを付ける

引用（引用マージ案 core.md ドラフト「実測と推定」節）:

> 直接観測した結果（実測）と、状況証拠からの推論（間接観察）を同格に扱わない。「確定」「確認済み」と書けるのは実測だけ。間接観察は推定と明示し、実測の確認先を残す

引用（同「エビデンスの適格性」節）:

> 外部の仕様・制約・挙動を述べる根拠は、提供元の公式ドキュメント（公式サイト、RFC 等）を使う。自分たちの調査ドキュメント・設計ドキュメントは、その主張の裏付けにはならない。それらへの参照は関連文書への参照として別に示す

### 説明 3 突き合わせた結果

表 1 条項の関係

| primary-sources-first 側 | core 側 | 関係 |
| --- | --- | --- |
| 確認できないものは「未確認」と明示する | 実測か推定かを付ける / 間接観察は推定と明示 | 3 重複 |
| 「たぶんこうだ」と思って書いたなら裏を取っていない | 判断と数値には出典を付ける | 部分重複 |
| 探索順序 1: 手元の repo を当たる | 自社ドキュメントは裏付けにならない | 誤読を招く並置 |
| 探索順序 2-3、git 履歴 | （対応なし） | rule 固有 |
| （対応なし） | スニペットから推測しない / 要約ツールの回答は本文ではない | core 固有 |

3 重複の中身: 「未確認と明示する」に相当する要求が 3 か所にあります。primary-sources-first の判定基準、core の「実測か推定かを付ける」、core の「間接観察は推定と明示」。同じ行為を求めています。

部分重複の中身: 粒度が違います。primary-sources-first は書き手の内省による判定（そう思ったなら確認しろ）で、core は成果物の要件（出典が付いているか）です。どちらか一方では拾えないものが残ります。

誤読を招く並置の中身: 文言はぶつかって見えますが対象が違います。前者は調べ始める場所、後者は主張の根拠に使えるもの。ただし並べて読むと「手元の docs を読んだから裏付け済み」と誤読できます。core 側にその旨の 1 文を入れる案は既にドラフトに入っています。

この突き合わせで、当初の設問（rule を core へ移すか残すか）が成り立たなくなりました。移す理由だった「重複がある」は 1 件だけで、しかも rule 側の 1 文を消せば解消します。

### 説明 4 破損の検知は実現できる

paths 除外が壊れたことを機械的に検知できるかを実測しました。`claude -p` に「system prompt に含まれる user global rules の見出しを列挙して」と問うと、常時ロードされている rule のファイル名一覧が返ります。

実行したところ 9 件ちょうどが返り、除外している `notes-format.md` も条件ロードの `markdown-formatting.md` も現れませんでした。除外は現時点で正しく効いています。期待リストとの差分を取れば破損を検知できます。sentinel を仕込む必要すらありません。

走らせるタイミングは Claude Code の更新を検知したときが適切です。破損は harness の変更で起きるので、それ以外のタイミングで走らせても無駄になります。known-issues plugin が既に更新検知の SessionStart hook を持ち、`rule-paths-exclusion-undocumented` の監視エントリも所有しているので、そこに検査スクリプトを足すのが自然です。コストは更新ごとに headless 1 回です。

却下した案: statusline の JSON による受動検知。キーが `contextWindowPercent` しかなく内訳を持たないため（実測）、会話量と混ざって判別できません。

これは norm-refit とは別の plugin 変更になります。実装の PR には含まれません。

## ccm-f020 一次情報 rule の移管先

タイトルは「一次情報 rule の移管先: idea-hub への全面移植を検証した」。設問 1 件。

### 冒頭

f019 の補足で出た「primary-sources-first は開発の文脈に限っているので idea-hub へ全面移植でいいのでは」という提案を、idea-hub の設計台帳を読んで検証した。

結論: 提案は筋が通ります。この rule は開発ワークフローの行動規範で、汎用執筆規範ではありません。ただし idea-hub は設計フェーズ完了・実装前で受け皿がまだ存在しません。同じ状況に対する先例が idea-hub 側に既にあるので、それに揃えるのを勧めます。

### 説明 1 idea-hub は rule 配置の設計を持っている

引用（idea-hub `docs/design/decisions.md`「Q36 rule 配置設計」）:

> 結論: 部分確定。5 段階スペクトル、「配置は paths に従う」、boilerplate は汎用性軸 / repo はレイヤー軸。あわせて boilerplate 側の分類軸が 4 軸（claude / process / code / stack）に docs を加えた 5 軸に変更された

この 5 軸のうち `process` が開発の進め方の規範を受け持ちます。一次情報から調べるという行動規範はここに該当します。

引用（同「Q39 最小ロード原則」）:

> rule の paths は「その rule が編集判断を実際に変えるファイル集合」と一致させる。分割判定は「この rule の内容の一部しか関係しない編集が日常的に起きるか」で、Yes なら分割して段階を下げる。広い paths が許されるのは architecture / style / process のようにその範囲の全編集で判断を変える場合のみ

`process` は広い paths が許される例として名指しされています。一次情報 rule を idea-hub 側の process に置いても、常時に近い形で効かせられます。

cc-marketplace の rules 層は全プロジェクトに symlink で配られます。idea-hub 側の boilerplate rules は repo 生成時に配られる想定で、配布の経路が違います。

### 説明 2 分解すると行き先が 3 つに分かれる

表 1 内容ごとの行き先

| 内容 | 性質 | 行き先 |
| --- | --- | --- |
| 「たぶんこうだ」と思って書いたなら裏を取っていない | 執筆一般に通じる | core へ取り込む |
| 確認できないものは「未確認」と明示する | core と 3 重複 | 削る |
| 探索順序 4 段 | この環境と開発に固有 | idea-hub |
| git 履歴も一次情報に含める | 開発に固有 | idea-hub |

取り込む 1 文は、仕様に限定した書き方をやめて執筆一般の形にします。差分は次のとおり（取り消し線が削除、太字が追加）。

> その記述を「たぶんこうだ」と思って書いたなら、まだ裏を取っていない。~~既存実装・公式ドキュメント・変更履歴のどれかで~~**出典に当たって**確認してから書く。

元の文が挙げていた確認先（既存実装・公式ドキュメント・変更履歴）は開発の文脈なので落とし、確認先の具体は core の「エビデンスの適格性」節が既に持っています。

この 1 文は core の出典節「判断と数値には出典を付ける」と角度が違います。あちらは成果物の要件、こちらは書き手の内省による判定です。片方だけでは拾えないものが残ります。

### 説明 3 受け皿がまだない

idea-hub は設計フェーズ完了・実装前です。boilerplate repo も rule の配布機構もまだ存在しません。

引用（idea-hub `docs/design/decisions.md`「Q81 norm ライブラリの置き場」）:

> 結論: 用途 3 分割の方針を確定（レビュー注入用 → op-review plugin のリソース / 作成時指針用 → 参照知識として該当軸へ / 汎用執筆規範 → cc-marketplace）。移管は受け皿ができた時点で実施し、それまで bp repo の docs/norms/ が暫定の単一正。

移管先を決めておいて、受け皿ができるまでは現在地を暫定の単一正とするという形です。一次情報 rule も同じ扱いにできます。
