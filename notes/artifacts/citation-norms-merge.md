作成 2026-08-15。取り込み元は `efso-document` の `to-be/idp/.claude/` 配下（read-only で参照）。
取り込み先は cc-marketplace の既存規範。条項 40 件を拾い、既存 21 件と突き合わせた。

着手は norm-refit の一括実装。台帳 [norm-refit 台帳](../norm-refit.md) の未解決課題から参照する。

## 結論

新規に採るのは 7 件、統合で減るのが 5 件、差し引き純増 2 件（21 → 23 件）。
最も価値が高い新規条項は 2 件で、どちらも既存 21 件のどれでも検出できない失敗を塞ぐ。

- 要約を返すツール（WebFetch 等）の回答は本文の取得ではない。引用・不在判断・重要な判断では全文を取る
- 自分たちの調査ドキュメントは、外部仕様を主張する裏付けにならない

## 確定した記法（ユーザー決定 2026-08-15）

1. 引用ブロック内の `"..."` は廃止する
2. 引用ブロック記法 `>` は引用・情報源・補足・GFM Alerts の 4 用途で使い続ける
3. 引用にラベルを付け、ラベル行に出典リンクを載せて出典行を廃止する

```markdown
> 引用: [Actions Limitations](https://auth0.com/docs/customize/actions/limitations)<br>
> Each execution of a trigger must complete in 20 seconds or less.
```

情報源ブロック内のネストした引用にはラベルを付けない。外側の出典に従属するため。
`>` ブロックの規則は「1 行目は必ずラベル」で一本化し、
ラベルのない `>` は用途限定の違反として grep で検出できる。

> [!NOTE]
> 以下の実文ドラフトはこの決定より前に作ったもので、単独引用が `> "..."` + 出典行の
> 3 パート形式のまま残っている。実装時にラベル形式へ直す。

## 採る新規条項 7 件

| 条項 | 内容 | 採る理由 |
| --- | --- | --- |
| 要約ツールの限界 | WebFetch 等の回答は本文ではない。引用を書くとき・不在を判断するとき・課金や制限値など影響の大きい情報を扱うときは全文を取得して読む | 取り込み元に実害の記録あり（開発ストアの課金有無を要約回答だけで結論づけた、2026-07-08） |
| エビデンスの適格性 | 外部仕様の裏付けは提供元の公式ドキュメント。自社の調査・設計ドキュメントは裏付けにならない | 既存に該当条項なし |
| 基準未満の事実の扱い | 適格性を満たせない事実は恒常ドキュメントに書かない。残すなら非公式と明示して別の置き場へ | 同上 |
| 要約のみの禁止 | 外部の仕様・制約を要約したら、根拠になった原文を引用で併記する。要約だけにしない | 要約が原文と乖離しても検出できない（非 verbatim 引用 6 件検出と同じ経路） |
| 実測と間接観察の峻別 | 直接観測（実測）と状況証拠からの推論（間接観察）を同格にしない。「確定」「確認済み」と書けるのは実測だけ | 既存「実測か推定かを付ける」に判定基準がない穴を埋める |
| 機能の実在確認と断言前の裏取り | 外部の機能名・API は公式ドキュメントで実在を確認する。「できない」と断言する前に確認し、消去法なら消した側を検算する | 生成文に実在しない機能名が混入する（取り込み元に事例あり） |
| 検索スニペットからの推測禁止 | 検索は参照先の発見に使い、内容は本文を取得して読む | 上記 2 件を支える前提 |

純増を 0 に抑えたい場合、最初に落とせるのは「リダイレクト後の最終 URL を使う」と
「検索スニペットからの推測禁止」。どちらも他条項から演繹できる度合いが高い。

見送った条項は 9 件（検証結果のラベル / TODO マーカー / 反映先の選定基準 / ADR ステータス整合 /
参照 skill に事実を持たせない / 403 サイト表と Chrome MCP 手順 / 参考リンクセクションの禁止ほか）。
本 domain の外か、環境固有か、既存条項に含意される。

## 既存との矛盾 6 件と処理

**引用の記法**: 取り込み元・既存とも `"..."`。ユーザー指示（2026-08-15）は引用専用記法。
`> "..."` は二重マークで冗長、情報源ブロック内の `"原文"` は地の文への埋め込みそのもの。
機械検算でも引用の終端を抽出器が決められない。→ `"..."` を廃止する。

**情報源ブロックに引用が必須か**: 取り込み元は必須、既存は要求なし。→ 取り込み元を採る。

**`※ 参照` の適用範囲**: 取り込み元は自プロジェクト内に限定、既存は無限定。
限定すると 5 記法の役割が排他になり、使い分けの判断基準が一意に決まる。→ 取り込み元を採る。
なお取り込み元にも内部矛盾がある（テンプレート側が外部標準仕様に `※` を使っている）。そちらは採らない。

**自社ドキュメントの扱い**: 既存 primary-sources-first は探索の起点として手元 repo を 1 番目に置く。
取り込み元は自社ドキュメントをエビデンスから外す。対象が違うので両立するが、
**統合実文では「調査の起点」と「主張の裏付け」を別条項に分けて書く**必要がある。
混ぜると「手元 docs を読んだから裏付け済み」という誤読を招く。

**検証結果のラベル**: 取り込み元は「合格」「確認済み」を結論に使わない。
既存 facet-review-norms は数値に「裏取り済み / 推定」のマーカーを付ける。
レイヤーが違う（結論文の書き方 / 数値のマーカー）。
→ 「マーカーは付けてよいが、挙動を述べた文を消してラベルだけにしない」と条件を明記する。

**既存側に残る鉤括弧引用 4 箇所**: ユーザー指示「既存の記述からも消す」の対象。

- `plugins/claude-user-communication/skills/html-communication/references/facet-review-norms.md` 49-51 行
  （verbatim 規範そのものが「」前提で書かれている）
- `plugins/japanese-text-writing/skills/japanese-text-writing/references/narrative-writing.md` 56 行
- `plugins/dotclaude/agents/dotclaude-claude-scanner.md` 102・155 行（出力テンプレート）
- `plugins/dotclaude/skills/cross-review/SKILL.md` 177 行（同型テンプレート）

## 実文ドラフト: core.md へ追加する節

```markdown
## 引用・出典・エビデンス

### 引用

- 引用は引用専用の記法で書く。markdown は引用ブロック (`>`)、HTML は `<blockquote>`。
  専用の記法が無い形式では markdown の記法をそのまま使う。
  地の文に鉤括弧やダブルクォートで引用文字列を埋め込まない
- 引用文は出典から文字列をコピーして貼る。記憶から再構成しない
- 中間を省くときは省略を明示する（`…（中略）…`）
- 字句を変える必要があるなら引用ではなく要約にする。引用の記法を外し、
  地の文で要約と分かる形で書く
- 要約だけを書いて原文の引用を省かない。外部の仕様・制約を要約したなら、
  その根拠になった原文を引用で併記する
- 引用の直後に出典を置く。出典は主張 1 件と対応が取れる粒度で付ける

### 出典

- 判断と数値には出典を付ける。「A を採用する」「B が必要」型の判断と、
  レート制限・TTL・レイテンシ・SLA・コストのような具体的な数値が対象
- 不確実なまま残す記述にも、判断の手がかりになる参照先を添える
- リンクを貼る前に参照先の中身を取得して確認する。確認するのは、URL が有効であることと、
  引用している主張が参照先に実際に書かれていることの 2 点
- リンク切れや内容の不一致が見つかったらリンクを貼らず、その旨を明記する
- 外部 URL はリダイレクト後の最終 URL を使う
- 出典を示せない権威付け（「専門家によると」「一般的に〜とされている」）は書かない。
  出典を示すか、文ごと削る
- リンク先のどこを根拠にしているかを本文に書く。文書全体へのリンクだけで済ませない

### エビデンスの適格性

- 外部の仕様・制約・挙動を述べる根拠は、提供元の公式ドキュメント（公式サイト、RFC 等）を使う。
  自分たちの調査ドキュメント・設計ドキュメントは、その主張の裏付けにはならない。
  それらへの参照は関連文書への参照として別に示す
- この適格性を満たせない事実は、満たさないまま恒常ドキュメントに書かない。
  残す価値があるなら、非公式な情報源であることを明示して、その事実に見合う置き場に記録する
- 外部の機能名・API・設定項目に言及するときは、公式ドキュメントで実在を確認する。
  生成した文章には実在しない機能名が混入する
- 「できない」「方法がない」と断言する前に確認する。
  消去法で方法を選ぶときは、消去した側が本当に不可能かを裏取りする

### 裏取りの手順

- 調査の起点は手元の一次情報（実装・docs・git 履歴）に置く。これは探索の順序であって、
  外部仕様の主張の裏付けとは別の話
- 検索結果のスニペットから内容を推測しない。検索は参照先の発見に使い、内容は本文を取得して読む
- 要約を返すツール（WebFetch 等）の回答は本文の取得ではない。取得が成功したことと、
  本文を読んだことは別に扱う。次の場合は本文（全文）を取得して自分で読む
    - 引用を書くとき。原文の文言そのものが要る
    - 「記載がない」という不在の判断をするとき。要約側の「見つからなかった」は不在の根拠にならない
    - 課金・制限値・期限など、判断への影響が大きい情報を扱うとき

### 実測と推定

- 直接観測した結果（実測）と、状況証拠からの推論（間接観察）を同格に扱わない。
  「確定」「確認済み」と書けるのは実測だけ。間接観察は推定と明示し、実測の確認先を残す
```

末尾の「実測と推定」は既存 core の「事実・意見・不確実性」節と重なるため、
実装時はそちらへ寄せて本節から落とす。

## 実文ドラフト: markdown-formatting.md の記法節

記法だけを定め、内容規範は core へ委譲する。引用そのものはラベルの無い引用ブロックで書き、
補足・情報源・Alerts は先頭のラベルで区別する。
補足ブロック・情報源ブロックの中で原文を引くときはネストした引用ブロックにする。

情報源ブロックの例:

```markdown
> 情報源: Shopify Webhook の配信制約<br>
> レスポンスは 5 秒以内が必須。失敗時は 4 時間以内に 8 回リトライし、8 回連続失敗で自動削除される。
>
> > Shopify retries the connection 8 times over the next 4 hours.
> > If there are 8 consecutive failures, then the webhook subscription is automatically deleted.
>
> 出典: [HTTPS Webhook subscription](https://shopify.dev/docs/apps/build/webhooks/subscribe/https)
```

使い分け表は 5 行のまま。1 行目を「外部文言のそのままの転記 = ラベル無しの `>` + `出典:`」に変える。
`※ 参照` の行に「同一プロジェクト内の参照先」という限定を入れる。
