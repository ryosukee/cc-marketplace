## 何を調べたか

2026-08-31 のセッション終盤で、明文の条項が 3 回続けて守られなかった。
前セッションはこれを 1 つの原因に帰したが、原因の検証をせずに次セッションへ送った
（ユーザー判断 2026-08-31「なぜ指示を無視してしまうのか。システムプロンプトにそういうバイアスがあるのか、
最近のモデルにそういうバイアスが入っているのか。調査から次のセッションでやろう」）。

調べたのは 3 つ。条項がコンテキストに載っていたか、規範の総量はどれだけか、条項どうしが競合していないか。

## 観測 1: 条項は 3 回とも載っていた

3 時点とも、破られた条項の実文がコンテキストに載っていた。載っていなかった時点は 0 件。

- `core.md` は 10:56:38 に全文 25,398 バイトが搭載された
- html-communication の SKILL.md は 11:16:47 に本文 565 行が搭載された
- コンパクションは 0 回、sidechain も 0 件なので、以後どちらも落ちていない

搭載からの距離は時点 1 が +33k〜212k トークン、時点 2 と 3 が +607k〜816k トークン
（セッション最大 952k）。ただし距離では説明しきれない。距離ゼロの同型事象が 2 件ある。
常時ロードの `.claude/rules/norm-refit-ops.md` の収集条項と、3 分前にロードした
retrospective skill の提示フォーマットで、どちらも同じ形で破られている。

差はテキストの有無ではなく、引きにいったかどうかにある。

## 観測 3: 同時に満たせない条項が 7 組ある

優先順位が明記されていて衝突にならない組が 9 件、条件で解消する組が 4 件。
残る 7 件は、どちらを採っても他方に反する。2026-09-01 のセッションで実際に 2 件を踏んでいる。

- 確認を 1 件ずつ出すか、1 つのフォームにまとめるか
- plugin の変更を main へ直接 push するか、PR にするか

## 観測 4: システムプロンプトに競合する指示がある

Opus 5 のセッションのシステムプロンプトに、条項を引き直すことと競合しうる指示が 3 件ある。

> When you have enough information to act, act. Do not re-derive facts already established in the conversation, re-litigate a decision the user has already made, or narrate options you will not pursue.

> Avoid unnecessary or excessive self-correction. Only correct an earlier statement in your user-facing text when the error would change the user's code, conclusions, or decisions.

> If you find an uncertainty mid-task, first do everything that doesn't depend on the answer

システムプロンプトには、user rule を参照せよという指示は無い。参照を促すのは user rule 自身になる。

## 否定できたこと

- 条項が載っていないから守れない（観測 1）
- 判定のきっかけが無いから引かない。入口の `rules/japanese-text-writing.md` は
  `paths` を持たない常時ロードで、「判定は書き出す直前に行う」を含む。きっかけは毎ターン載っている

## まだ検証していないこと

- 競合する指示が原因かどうか。存在は事実だが、相関も因果も測っていない
- モデル側のバイアスがあるかどうか。前セッションが挙げた 2 つ目の仮説
- 条項がロードされた状態で、その条項が振る舞いを変えているかどうか。
  repo の実測は「ロードされるか」を測ったもの（skill の description は無関係プロンプトで遵守 0/19、
  skill 発動時のみ 5/5）で、ロード後の遵守は測られていない。
  2026-09-01 に自然環境での観測を 1 件足した（[エイリアスの条項](./alias-clause-adherence.md)）。
  条項が届いた後の assistant のテキストターン 135 件のうち 37 件（27%）が破っている。
  対照条件が無いので「条項が振る舞いを変えていない」ことの証明にはならず、
  「載せただけでは止まらない」ことだけが言える

## 測る仕組みの案

`evals/` に `claude plugin eval` のハーネスがある。いまは skill の発動率を測るもので、
条項の遵守率を測る形には組み替えが要る。

- 条件 A: 汎用語を使いやすい課題文を渡し、`core.md` が載った状態で書かせる
- 条件 B: 同じ課題文を `core.md` 無しで書かせる
- 判定: 汎用語が指す実体が同じ節に書かれているかを grader が見る

A と B に差が出なければ、条項が振る舞いを変えていないことになる。
差が出れば、効いてはいるが足りない、という話に変わる。

コストは実測で 1 実行あたり約 $0.21・27 秒。2 条件 20 実行ずつなら約 $8.4・18 分（直列）。
この数値は eval README の実測値からの計算で、この設計での実測ではない。

未決のもの。課題文をどう選ぶか。grader が汎用語の実体を機械で判定できるか。
条件 B をどう作るか（`core.md` を外した状態を再現する手段が要る）。

観測 4 の競合を条件として操作できることが分かった（[システムプロンプトの実測](./system-prompt-survey.md)）。
`CLAUDE_CODE_ACT_DONT_REDERIVE=0` で 1 件目の指示を外せる。2 件目（自己修正の抑制）と
`# Delivering work` は強制 OFF ができないので、3 件を分離しては測れない。
